# MOCA 产品案例总览

> 定位：open-source portfolio project / simulated merchant operations scenario  
> 目标方向：AI 应用产品经理 / Agent 产品经理  
> 阅读对象：简历作品集、HR 初筛、非技术面试官快速理解  
> 说明：MOCA 是一个开源作品集项目，使用模拟商家运营场景和合成数据，不伪装成真实商用上线产品。

## 一句话介绍

MOCA 是一个面向电商 / 本地生活平台商家运营场景的 AI Agent 工作流产品，用于辅助客服和运营人员处理退款进度查询、规则咨询、补偿建议、高风险动作审批和处理过程追溯。

它不是普通聊天机器人，而是一个围绕“业务事实 + 政策证据 + 风险判断 + 人工审批 + 审计 trace”设计的 Agent 产品原型。

## 为什么做这个产品

在退款、补偿、投诉和工单处理场景中，一线客服经常需要同时完成几件事：

- 查订单、退款单、工单、物流等业务事实。
- 查平台规则、售后政策和操作 SOP。
- 判断用户诉求是否需要补偿、是否有风险、是否需要主管审批。
- 组织一段对用户可解释、可追溯、有证据支撑的回复。
- 在后续争议或复盘时说明“为什么当时这样处理”。

这些工作如果完全人工完成，容易出现处理慢、口径不一致、证据缺失、越权操作和复盘困难。MOCA 的产品目标是把这些分散动作组织成一个可控的 Agent 工作流，让 AI 可以提高处理效率，但不能绕过证据、权限和审批边界。

## 目标用户

| 用户角色 | 主要任务 | MOCA 提供的价值 |
| --- | --- | --- |
| 一线客服 | 查询退款进度、解释规则、生成回复草稿 | 减少查系统和查政策时间，提高回复一致性 |
| 客服主管 / 审核人员 | 审批补偿、高风险操作、复盘争议 case | 看清 AI 判断依据、风险原因和审批上下文 |
| 平台运营 | 梳理售后流程、发现规则执行问题 | 通过 trace 和 case 数据复盘流程缺口 |
| 商家支持团队 | 处理商家侧退款、补偿、申诉问题 | 用统一证据和规则减少沟通成本 |

## 核心场景

### 1. 查询退款进度

用户问：“订单 ORD-1001 的退款为什么还没到账？”

MOCA 应该识别这是退款排查场景，提取订单号，查询订单和退款单状态，再给出可解释的回复。例如：退款已提交银行通道，预计还需 1-3 个工作日到账；如果超过时限，可以建议下一步处理方式。

产品价值：把“查订单 + 查退款 + 组织解释”合并为一个可追溯流程。

### 2. 规则咨询 + evidence 引用

用户问：“超过 7 天还能申请退款吗？”

MOCA 应该检索相关平台政策，引用规则依据，再说明适用条件、例外情况和需要补充的信息。

产品价值：不是只给一个看似合理的答案，而是让回答有政策依据，降低幻觉和口径不一致。

### 3. 补偿建议

用户问：“这个用户等太久了，能不能给点补偿？”

MOCA 应该先查看订单、退款、工单和相关规则，再判断是否适合补偿、建议补偿类型或金额范围，并说明理由。

产品价值：把补偿从“经验判断”变成“事实 + 规则 + 风险”的结构化建议。

### 4. 高风险动作触发审批

用户说：“直接给这个订单退款并发券。”

MOCA 不应该直接执行高风险动作。它应该识别这是可能产生财务或权益影响的操作，生成动作草稿，并进入审批流程。

产品价值：AI 可以辅助准备操作，但不能绕过权限和人审。

### 5. Approval resume + trace 回放

主管审批后，MOCA 应该能够恢复原来的 Agent 流程，继续生成最终回复或动作草稿，并保留完整 trace。

产品价值：高风险动作不是一次性黑盒判断，而是有上下文、有审批记录、可回放、可复盘的流程。

## 产品方案

MOCA 的核心产品方案可以概括为：

```text
用户请求
  -> 安全预判断
  -> 会话上下文加载
  -> 意图识别与槽位判断
  -> 业务事实查询 / 政策检索
  -> 证据校验
  -> 建议生成
  -> 风险判断
  -> 审批或动作草稿
  -> 最终回复与 trace 记录
```

这个流程的重点不是“让 AI 尽量多做”，而是让 AI 在每一步都有清晰边界：

- 事实来自业务系统，不来自模型猜测。
- 规则来自政策知识库，不来自模型自由发挥。
- 记忆只能作为上下文提示，不能替代事实、证据或权限。
- 高风险动作必须进入审批，不允许普通聊天确认直接生效。
- 每次运行都保留 trace，方便解释和复盘。

## 关键产品决策

### 决策 1：不做通用聊天机器人

MOCA 聚焦商家售后运营，不追求覆盖所有问题。这样可以把意图、证据、审批和风险策略做得更清楚。

### 决策 2：高风险动作只生成草稿，不直接执行

退款、补偿、发券等动作可能带来资金和权益影响。即使 AI 判断合理，也必须经过审批或明确的人审流程。

### 决策 3：回答必须尽量绑定证据

规则咨询、补偿建议和行动建议都应该尽量绑定政策证据或业务事实。没有足够证据时，系统应该澄清、拒绝或转人工，而不是编造答案。

### 决策 4：普通聊天里的“同意 / 执行吧”不能算审批

真实审批必须来自可信审批入口，而不是用户在普通对话里说一句“同意”。这个设计用于防止越权和上下文伪造。

### 决策 5：trace 是产品能力，不只是技术日志

MOCA 的 trace 用于回答三个产品问题：

- AI 为什么这样判断？
- 引用了哪些业务事实和政策证据？
- 高风险动作是否经过正确审批？

## MVP 范围

### MVP 做什么

- 支持退款进度查询、规则咨询、补偿建议、客服回复草稿。
- 支持订单、退款单、工单、政策等模拟业务数据读取。
- 支持政策 evidence 引用和基本证据校验。
- 支持高风险动作进入审批，而不是直接执行。
- 支持运行 trace 和审批恢复。
- 使用合成数据和模拟场景，便于作品集演示。

### MVP 不做什么

- 不接入真实支付、退款、发券或外部履约系统。
- 不做真实商用多租户计费和运营后台。
- 不覆盖所有客服渠道和所有售后品类。
- 不把 AI 回复作为最终业务事实或政策权威。
- 不声称该项目已真实上线。

## 评测思路

MOCA 的评测不只看“回答像不像人”，而是看 Agent 是否遵守业务和安全边界。

| 评测维度 | 关注问题 |
| --- | --- |
| 意图识别准确率 | 是否能区分退款查询、规则咨询、补偿建议、高风险动作 |
| 槽位识别准确率 | 是否能识别订单号、退款单号、工单号、动作类型 |
| evidence 覆盖率 | 规则类回答是否能引用相关政策依据 |
| 幻觉控制 | 没有证据时是否能拒绝、澄清或降级 |
| 高风险拦截率 | 退款、补偿、发券等动作是否进入审批 |
| 审批绕过防护 | 普通聊天确认是否会被错误当成审批 |
| trace 完整性 | 是否能复盘关键节点、证据、风险和审批状态 |

## 作品集展示重点

这个项目主要展示以下产品经理能力：

1. **业务场景抽象能力**：把售后运营中的退款、规则、补偿、审批和复盘整理成可产品化的核心场景。
2. **AI Agent 行为设计能力**：定义 Agent 什么时候查询事实、什么时候检索证据、什么时候生成建议、什么时候必须澄清或审批。
3. **安全边界意识**：明确 AI 不能拥有业务事实、政策权威、审批权限和真实执行权。
4. **MVP 取舍能力**：先做可演示、可验证、边界清晰的 Agent 工作流，不急于接入真实外部执行。
5. **评测意识**：用 golden set、风险拦截、evidence 引用和 trace 完整性来判断 AI 产品是否可靠。

## 10 分钟演示结构

建议在作品集或面试中按这个顺序演示：

1. 用一句话说明 MOCA 不是聊天机器人，而是商家运营 Agent 工作流。
2. 演示“查询退款进度”：展示业务事实查询和最终解释。
3. 演示“规则咨询”：展示 evidence 引用。
4. 演示“补偿建议”：展示事实、政策和风险判断如何共同影响建议。
5. 演示“直接退款 / 发券”：展示高风险动作被拦截并进入审批。
6. 演示“审批恢复 + trace”：展示主管审批后流程如何恢复，以及如何复盘 AI 判断。

## 后续 Roadmap

如果继续产品化，可以优先考虑：

- 更完整的售后 case library 和 golden set。
- 运营 / 主管视角的 case 复盘页面。
- 审批工作台和风险原因可视化。
- 多意图任务的用户可见确认与分步执行。
- 客服质检和规则执行一致性分析。
- 从模拟 action draft 逐步演进到真实执行前的 outbox / reconciliation 设计。

## 总结

MOCA 想展示的不是“我做了一个能聊天的 AI”，而是：

> 我可以围绕真实业务场景，设计一个有证据、有权限、有审批、有评测、有复盘能力的 AI Agent 产品。

这也是它作为 AI 应用产品经理 / Agent 产品经理作品集项目的核心价值。
