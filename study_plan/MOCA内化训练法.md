# MOCA 内化训练法

> 解决你最核心的焦虑：**MOCA 大量代码是 Codex/Claude 写的，怎么从"AI 帮我写过"变成"我自己的工程能力"。**
> 这套方法贯穿 30 天，不是额外任务，而是嵌在每天"内化 2.5h"里的具体做法。

---

## 0. 核心判据：怎么算"真的懂了"，而不是"会复述"

每内化一个模块，用这 4 关自测。**过不了第 2 关就是还没懂，别自欺。**

| 关卡 | 问题 | 复述者（假懂） | 真懂者 |
|---|---|---|---|
| 第1关 复述 | 这个模块做什么？ | 能照着 README 说 | 能一句话说清 + 说清它**不做**什么 |
| 第2关 因果 | 为什么这么设计？ | 答不上，或答"AI 这么写的" | 能说出**这么设计解决了什么问题、不这么设计会怎样** |
| 第3关 修改 | 要改 X 需求，动哪里？ | 不知道从哪下手 | 能指出改哪个文件/函数、影响哪些下游 |
| 第4关 追问 | （面试官三连问）那如果…呢？ | 第二问就崩 | 能扛住"边界条件/失败处理/为什么不用另一种方案" |

**关键原则：面试官不会问"这是什么"，只会问"为什么"和"如果"。所以内化的重心是第 2、4 关，不是第 1 关。**

## 1. 七步内化法（每个核心模块走一遍）

针对一个模块（如审批状态机），按顺序做。一个核心模块约半天到一天。

### 第①步：盲讲（先别看代码）
打开模块前，先凭印象口述/写下："我以为这个模块是怎么工作的"。
→ 这一步暴露你的认知盲区。盲讲和真实代码的差距，就是你要补的。

### 第②步：定位骨架（rg，不要全读）
用 `rg` 找入口、主函数、关键数据结构，**只读骨架不读细节**。
```bash
# 例：审批模块
rg -n "class.*Approval|def.*approve|def.*decision" src/approvals/
rg -n "状态|state|status|transition" src/approvals/
```
→ 目标是画出"数据怎么流"，不是读懂每一行。4554 行的 agent 模块绝不能逐行读。

### 第③步：手画图（不许 AI 代画）
纸笔或 draw.io 画出：数据结构 + 流程/状态迁移 + 模块边界。
→ **这是内化的核心动作。** 你能画出来的，才是真进脑子的。画不出来的地方，就是没懂的地方，回到第②步。

### 第④步：手写伪代码（关键逻辑）
把最核心的那段逻辑（如状态迁移规则、interrupt/resume）用伪代码默写一遍，**合上源码写**。
```
# 伪代码示例（审批状态迁移）
收到 approval_request:
    若 action 风险等级 >= 阈值:
        状态 = PENDING_APPROVAL
        中断 graph，等待人审   # ← 为什么中断而不是轮询？
    收到 decision:
        若 approved: 绑定 action_snapshot_hash, 状态 = APPROVED
        若 rejected: 状态 = REJECTED, 记 event
        恢复 graph
```
→ 写完对照源码，**差异处就是你理解的偏差**，重点研究。

### 第⑤步：改一个小需求（动手验证）
给自己出一个小改动题，真的去改、去跑。例：
- "审批增加一个'超时自动拒绝'状态，怎么加？"
- "RAG 的引用要多返回一个 chunk 来源，改哪？"
→ 能改对 = 第3关过了。改的过程比读 10 遍代码都管用。

### 第⑥步：写测试（证明你懂边界）
给这个模块补 1-2 个 pytest 用例，**专测边界/失败路径**（不是 happy path）。
→ 能写出"什么情况会出错"的测试，说明你懂它的边界。这也是 JD 反复要的"可测试"。

### 第⑦步：讲成面试故事（费曼+沉淀）
用费曼学习法：假装给一个**不懂技术的人**讲这个模块，讲到对方能听懂。
然后压缩成 200-300 字面试稿，存进 `interview/`。
→ 讲不清楚 = 没懂。能讲到外行听懂 = 真懂。

## 2. 费曼复盘的具体模板（第⑦步用）

每个模块写一段，套这个结构：

```
【模块】审批状态机
【一句话】高风险动作（退款/发券）不直接执行，先进一个有明确状态和审批节点的流程。
【为什么需要】（业务语言）商家运营场景里，AI 建议错了直接执行会造成真金白银损失，
              所以高风险动作必须"人确认了才算数"。
【怎么实现】（技术语言，但克制）用状态机管理 request→pending→approved/rejected，
              审批时中断 graph 执行，人审后再恢复，审批结果绑定到 action 快照的 hash
              （防止审批后 action 被偷换）。
【我的设计判断】为什么用状态机不用简单 if-else：因为要支持中断/恢复、要可审计、
              要让审批结果成为"可信结果"而非普通模型输出。
【如果被追问】
  Q: 审批后 action 被改了怎么办？→ A: 绑定了 canonical hash，对不上就失效。
  Q: 为什么不直接执行？→ A: MVP 阶段刻意只生成 draft，真实执行是 defer 的 Phase 17。
  Q: 中断了状态丢了怎么办？→ A: LangGraph 的 checkpoint 持久化，可恢复。
```

## 4. 对付"AI 写的代码"的专门技巧

你的特殊处境：很多代码不是你写的。专门应对：

1. **读 `.planning/` 比读代码更高效。** MOCA 每个 phase 都有 PLAN/SUMMARY/RESEARCH/DISCUSSION-LOG。**这些文档记录了"为什么这么设计"**——正好是面试官追问的第 2 关。先读决策文档，再读代码，事半功倍。
   ```bash
   # 例：搞懂审批为什么这么设计
   cat .planning/phases/13-approval-state-machine/13-DISCUSSION-LOG.md
   cat .planning/phases/13-approval-state-machine/13-RESEARCH.md
   ```

2. **把 Codex/Claude 当面试官陪练。** 内化完一个模块，让 AI 扮演面试官追问你，看你能不能扛住。扛不住的地方回去补。

3. **"如果让我重写"测试。** 对每个 AI 写的模块问自己："不看代码，我能重写一个简化版吗？" 第三周的 LangGraph 重写、RAG 重写就是这个测试的正式版——**重写成功 = 彻底内化的铁证，也是面试最强证据**（"这个我自己重写过一遍"）。

4. **双 AI 协作本身就是面试故事。** 你用 Claude 设计+裁决、Codex 执行的工作流，是一个**非常加分的"AI 时代工程师"叙事**——证明你会用 AI 放大产出，又能把关质量。写进 STAR 故事（D25 已排）。

## 5. 红线：别掉进这些坑

- ❌ **逐行读完 4554 行 agent**——必崩，且没用。永远 rg 定位骨架。
- ❌ **跳过手画图直接看 AI 的图**——等于没内化。
- ❌ **只过第 1 关复述就以为懂了**——面试第二问就穿帮。
- ❌ **内化完不写面试稿**——一周后全忘，白做。
- ❌ **为了"做完 MOCA"去硬啃 16/17**——已决策 defer，那是时间黑洞。
