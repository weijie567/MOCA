## Spec Consistency Findings

- Implemented fact before this plan: Plan 03 may leave `respond` and `edit` as blocked/not implemented, and ordinary clarification already exists separately.
- Target contract: approval `respond` is trusted `needs_info`, not ordinary `clarification_gate`; `edit` supersedes old revision and reruns risk/snapshot before any action.
- MVP scope: trusted backend/API flows and tests. Full inbox UI/work queue richness remains out of scope.

## Architecture Alignment

Canonical owner package: `src/approvals`. `ApprovalService` owns revision lifecycle; `src/approvals/schemas.py` owns trusted command/result contracts; `src/db/models.py` owns version/hash/supersede fields.
Old-path strategy: `src.repositories.approval_repo` is not extended for `respond`, `attach_info`, or `edit`; Plan 13-07 deletes or quarantines legacy transition methods and blocks new imports.
Forbidden imports: routers and graph code may pass authenticated commands to `ApprovalService` but must not directly mutate approval tables or call legacy repository transition methods.
Boundary tests: Plan 13-07 static tests protect the owner boundary after these revision paths are added.
Non-overlap: Phase 13 owns trusted backend revision semantics; Phase 14 owns action draft/executor binding; Phase 15 owns replay enrichment and scanner enablement; Phase 16 owns memory; Phase 17 owns external execution.
Routers only pass authenticated commands and clarification/info payloads to service methods.

## Migration / Read-Switch / Rollback

This plan uses v2 fields from Plan 02: `clarification_request_id`, `superseded_by_request_id`, `revision`, `version`, hashes, status, `approval_decisions.response_text`, and `approval_decisions.edited_action_json`. Rollback is to reject `respond`/`edit` command types until the service path is restored; old approvals remain non-executable after supersede.

`attach_info` must leave exactly one active approval revision per `(tenant_id, run_id)`. If supplied info creates a new or revalidated revision, the old `needs_info` revision is marked `superseded` only after the replacement revision is durable; if the implementation updates in place, service tests must still prove stale old-version commands cannot decide or execute.

## Compatibility-Layer Disposition

| Path | Owner | Forbidden New References | Protection Test | Deletion/Gate |
|------|-------|--------------------------|-----------------|---------------|
| Ordinary chat clarification | Phase 11/12 ordinary flow | Cannot write approval_result or resume approval | `test_needs_info_resume.py` | Remains separate |
| Old approval revision after needs_info/edit | ApprovalService | Cannot route to action_draft | `old_revision_cannot_execute` test | Superseded in Phase 13 |
| Client-provided edited action as approval | ApprovalService | Cannot directly approve edited action | edit reroute tests | Must re-run risk/snapshot |

## Cross-Table Enforcement Row

Every `respond`, `attach_info`, or `edit` command validates the same request/level/assignment row chain as Plan 03 before mutating status or creating a replacement revision:
`decision -> assignment -> level -> request` with tenant/run/thread/revision/version matches.
