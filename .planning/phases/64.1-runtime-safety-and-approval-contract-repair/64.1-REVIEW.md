# Phase 64.1: Code Review Report

**Reviewed:** 2026-07-10T07:43:08Z
**Depth:** deep
**Files Reviewed:** 34
**Status:** issues_found

## Summary

The durable auto-action capability path is substantially hardened: issuance is backend-owned, verification binds the exact tenant/actor/run/merchant/action/payload/snapshot/risk/handler tuple, consumption is row-locked, the draft plus critical replay event share one savepoint, and exact retry is constrained to the already-bound draft identity. The approval decision contract also rejects stale and mismatched mutation inputs rather than defaulting missing integrity fields.

However, the phase is not clean. The highest-impact defect is outside the successful capability-consume path: `manual_review` and unknown action candidates are routed to `final_response`, then rendered and persisted as ordinary `completed` advice. This directly violates the locked D-02/D-05 boundary and can promote unproven action advice into completed conversation and memory state. Six additional warnings affect backend/frontend terminal parity, approval recovery, transaction lock ordering, per-turn safety-state hygiene, and SSE context monotonicity.

The focused backend, frontend, and Ruff suites are green, but the reviewed tests do not exercise the failing semantic combinations described below.

## Critical

### CR-01: `manual_review` and unresolved actions are laundered into ordinary completed responses and completed memory

**Files:** `src/agent/nodes/recommendation_generation.py:239-267`, `src/agent/nodes/risk_gate.py:216-257`, `src/agent/graph.py:70-89`, `src/agent/routing.py:177-191`, `src/agent/nodes/final_response.py:634-651`, `src/agent/nodes/final_response.py:1239-1259`, `src/api/routers/agent_runs.py:344-371`, `src/api/services/agent_run_memory.py:119-151`

**Confirmed path:**

1. Unknown, ambiguous, or schema-invalid candidates receive no executable action type and get `risk_signals=["manual_review_required"]`.
2. The deterministic risk owner maps unknown candidates, invalid/missing rules, and unmatched rules to `risk_disposition="manual_review"`, `risk_severity="medium"`, and `approval_required=False`.
3. With no executable `proposed_action`, `route_after_risk()` sends the state to `final_response`.
4. `project_action_draft_terminal()` does not apply because `_action_draft_terminal_expected()` only recognizes a proposed action on the non-approval path when the disposition is `allow`.
5. `_completed_response()` emits the recommendation as ordinary advice and only adds a risk warning when `approval_required` is true. The returned LLM projection hard-codes `final_status="completed"`.
6. `_project_run_terminal()` accepts that status, and `finalize_completed_agent_run_memory()` persists the assistant message and continues terminal memory writes because no failed action terminal applies.

A project-environment runtime probe reproduced the terminal projection exactly:

```text
route= final_response
terminal= {'response_text': '建议：launch rocket\n理由：do it', ..., 'final_status': 'completed'}
```

The same laundering applies to fail-closed risk fallbacks such as an unproven medium action after provider failure: the risk result says `manual_review`, but the final-response owner has no manual-review terminal branch for that risk disposition.

**Impact:** An action that the canonical resolver or deterministic risk authority explicitly refuses to prove executable can be presented as a successful recommendation, stored as a completed assistant message, and admitted to downstream memory. This breaks `.planning/phases/64.1-runtime-safety-and-approval-contract-repair/64.1-CONTEXT.md` D-02 and D-05 and undermines the phase's terminal/memory integrity objective.

**Coverage gap:** `tests/integration/test_phase64_1_runtime_safety_matrix.py:240-277` asserts only `manual_review`, route-to-final, and zero drafts. The unresolved-action matrix at `tests/integration/test_phase64_1_runtime_safety_matrix.py:289-306` asserts resolver/route/no-draft behavior but never checks final text, final status, persisted run state, or memory suppression.

**Fix:** Give `manual_review`/blocked/unresolved risk dispositions an explicit non-success terminal projection before the generic completed template. The graph, API/SSE/polling projection, and memory finalizer must consume the same authoritative terminal classification. Add end-to-end matrix cases for unknown/ambiguous/schema-invalid candidates and provider/config fallbacks asserting non-completed final status and zero completed-memory projection.

## Warnings

### WR-01: Polling and reconnect recovery render backend error terminals as completed assistant messages

**Files:** `frontend/src/hooks/useAgentRun.ts:215-255`, `frontend/src/hooks/useAgentRun.ts:268-323`, `src/api/routers/agent_runs.py:344-365`, `frontend/e2e/phase64_1-approval-safety.spec.ts:212-253`

Both `recoverRunStatus()` and `startPolling()` correctly normalize backend `final_status="error"` to hook status `failed`. But whenever `final_response` is non-null, they update the assistant message with `status: 'completed'` before considering the failed status. The backend intentionally persists a safe error response alongside `final_status="error"` for failed action-draft terminals, so this is a normal response shape rather than an impossible combination.

**Impact:** After SSE reconnect or approval-resume polling, the run state can be failed while its visible assistant message is styled/projected as completed. This violates D-13's backend/frontend terminal parity and can visually launder a draft/auth/audit failure.

**Coverage gap:** The Playwright draft-failure case covers an SSE `error` event with `error_message`; it does not cover polling/recovery returning `{final_status: "error", final_response: <safe failure text>}`.

**Fix:** Derive message status from the normalized terminal status first. Preserve the backend's safe `final_response` as message content, but set message status to `error` whenever the terminal status is failed/error. Add polling and reconnect regression tests for that exact response shape.

### WR-02: Active-run approval callbacks report success even when the submission failed or was not attempted

**Files:** `frontend/src/components/details/ApprovalTab.tsx:115-153`, `frontend/src/hooks/useAgentRun.ts:490-559`, `frontend/src/components/details/DetailsPanel.tsx:87-95`

For the active approval, `ApprovalTab.confirmDecision()` awaits `onApprove()` or `onReject()` and then unconditionally sets `审批决定已提交，正在同步运行状态。`. The hook callbacks return `Promise<void>` and handle stale detail, HTTP errors, missing/freshness preconditions, and network ambiguity by updating hook error state and returning normally; they neither throw nor return a success result. Therefore the component cannot distinguish success from failure and can immediately announce a successful submission after the hook rejected, skipped, or could not confirm it.

**Impact:** Stale, unauthorized, or ambiguous approval attempts can produce contradictory UI state and a false success announcement on a security-sensitive transition.

**Coverage gap:** Component tests do not exercise callback failure/early-return behavior. The Playwright flows open approvals from the list with no active-run `approvalId`, so they use the direct `decideApproval()` branch rather than the callback branch wired by `DetailsPanel`.

**Fix:** Make active callbacks return an explicit discriminated result (success/stale/ambiguous/error) or throw a typed error. Only show success after a confirmed successful result; route stale and ambiguous results through the same component state machine used by direct decisions.

### WR-03: Approval reads take row locks and create a Level-to-Request versus Request-to-Level deadlock order

**Files:** `src/approvals/service.py:187-227`, `src/approvals/service.py:235-267`, `src/approvals/service.py:296-339`, `src/approvals/service.py:347-366`, `src/approvals/repository.py:35-57`, `src/api/routers/approvals.py:112-167`, `src/api/routers/approvals.py:222-258`

`get_decision_context()` is used by GET/list and by the decision endpoint's preflight. It calls `lock_current_level()`, whose query uses `SELECT ... FOR UPDATE`. The decision endpoint therefore locks Level during preflight and then enters `decide()`, which locks Request and then Level. In contrast, `attach_info()` and `expire_due_request()` lock Request and then Level.

Under concurrency, decision can hold Level while waiting for Request as expiry/info holds Request while waiting for Level. PostgreSQL must abort one transaction as a deadlock. Read-only GET/list calls also hold unnecessary row locks and can delay decision workers; list locks each pending level sequentially.

**Fix:** Use a non-locking decision-context projector for list/get/SSE. For mutations, load and validate the latest context inside one transition service method with one consistent Request -> Level -> Assignment lock order. Add a PostgreSQL concurrency regression covering decision versus expiry/info, not only single-row capability consumption.

### WR-04: Query-first ambiguity recovery cannot observe a decision that actually committed

**Files:** `src/approvals/service.py:208-227`, `src/approvals/service.py:422-449`, `src/api/routers/approvals.py:222-240`, `frontend/src/components/details/ApprovalTab.tsx:141-153`, `frontend/src/hooks/useAgentRun.ts:500-557`, `frontend/e2e/phase64_1-approval-safety.spec.ts:81-104`, `frontend/e2e/phase64_1-approval-safety.spec.ts:200-210`

The recovery contract says an ambiguous POST must query current state rather than replay. But `get_decision_context()` only selects a pending level and pending assignment. A successful approve changes request, level, and assignment to `approved`; the subsequent GET therefore raises `approval_conflict` instead of returning the terminal approval record. The GET router does not map that service exception locally. Both frontend recovery paths issue the GET but discard its result, so even a usable terminal projection would not currently reconcile component state.

The Playwright ambiguous-submit mock hides the mismatch by returning the same pending detail after the aborted POST; it never simulates “server committed, response lost.”

**Impact:** The principal network-ambiguity case remains permanently “unknown” even though the server has authoritative terminal state, encouraging manual refresh and increasing duplicate-decision pressure.

**Fix:** Let GET return the scoped approval record for terminal states, with `decision_context=null` or a separate non-decidable terminal projection. Map service conflicts to stable API errors, consume the recovery GET result in both frontend paths, and add committed-but-response-lost tests asserting no replay and successful terminal reconciliation.

### WR-05: New ephemeral safety fields are not reset at turn ingress

**Files:** `src/agent/state.py:108-114`, `src/agent/nodes/receive_request.py:140-230`, `src/agent/nodes/recommendation_generation.py:239-305`, `src/agent/routing.py:1028-1064`, `src/agent/routing.py:1143-1152`

Phase 64.1 adds `canonical_action` and `risk_signals` to checkpointed `AgentState`, adjacent to fields documented as ephemeral per-turn state. `receive_request()` resets `recommendation_draft`, `risk_assessment`, `proposed_action`, and `auto_action_capability`, but it never resets either new field. Recommendation success overwrites `canonical_action`, but only unresolved candidates emit `risk_signals`; recognized candidates do not clear a prior signal. The validation-failure return emits neither field. Routing then consumes both values to decide whether to enter claim verification and risk gating.

**Impact:** A previous turn's unresolved action/manual-review signal can survive into a new turn and influence its route, especially across recognized-action and recommendation-error paths. This violates the typed ephemeral safety-projection boundary and makes behavior checkpoint-history-dependent.

**Fix:** Reset both fields at turn ingress and emit authoritative empty/`None` values on every recommendation exit path. Add a two-turn checkpoint regression: unresolved/manual-review first turn followed by recognized, no-action, and recommendation-failure second turns.

### WR-06: SSE decision contexts are accepted by run id only, without immutable-identity or monotonic-version checks

**Files:** `frontend/src/hooks/useAgentRun.ts:345-397`, `frontend/src/lib/api.ts`, `.planning/phases/64.1-runtime-safety-and-approval-contract-repair/64.1-UI-SPEC.md:77-78`

The hook replaces cached approval context whenever the incoming payload parses and `incomingContext.run_id === runId`. It does not compare `tenant_ref`, `approval_id`, `thread_id`, `level_id`, `assignment_id`, revision, or request/level/assignment versions. The locked UI contract explicitly requires identical immutable identity and a newer revision/version before replacement.

**Impact:** A delayed or replayed same-run SSE event can overwrite a newer GET/detail context, or a malformed same-run event can switch approval/assignment identity. The next decision does perform a latest GET, which limits backend authorization impact, but the active context, displayed hashes, button state, and selected approval can still regress or drift.

**Fix:** Centralize a context replacement predicate that requires exact immutable identity and monotonic revision/versions, rejecting older, equal-but-conflicting, or cross-identity payloads. Cover stale same-run events arriving after a newer detail fetch and cross-assignment/level events.
