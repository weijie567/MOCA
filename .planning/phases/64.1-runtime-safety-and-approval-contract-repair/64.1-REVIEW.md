## Warnings

### WR-01: Approval resume still lets action-draft shape override an authoritative manual-review/refusal terminal

**Files:** `src/api/routers/approvals.py:14`, `src/api/routers/approvals.py:368-401`, `src/agent/routing.py:148-163`, `src/api/services/agent_run_memory.py:119-136`, `src/agent/trace.py:366-405`

The normal AgentRun paths now call `project_run_terminal()`, which correctly gives an already-rendered `manual_review`, `refused`, or `error` response precedence over stale action-shaped fields. The approval-resume path does not. `_resume_graph_after_decision()` still calls `project_action_draft_terminal(final_state)` directly, then persists only `completed` or generic `error` via `update_agent_run_status()`.

A project-environment probe using the same state reproduced the disagreement for both authoritative statuses:

```text
run terminal: manual_review / refused, error_code=CLAIM_TERMINAL
approval-resume action-only terminal: error,
  error_code=ACTION_DRAFT_TERMINAL_FAILED,
  reason_code=draft_identity_invalid
```

An approval-resumed graph state containing an authoritative claim/evidence non-allow terminal plus stale `approval_result`/`action_draft`/`draft_outcome` therefore gets different DB status, safe response, lifecycle reason, and replay status depending on whether it completed through AgentRun streaming or the approval router. Memory independently refuses the write, so this does not launder success, but terminal authority/parity remains broken.

**Coverage gap:** The new precedence tests drive `_project_run_terminal()` through AgentRun SSE/DB/memory only. No approval-resume test returns an explicit `manual_review` or `refused` final response with stale action-shaped state.

**Fix:** Make `_resume_graph_after_decision()` consume `project_run_terminal()` for final status/message/reason/error projection, while retaining `project_action_draft_terminal(..., require_action=True)` only where a valid draft is specifically required. Add approval-resume DB/lifecycle/replay tests for manual-review and refusal with stale draft fields.

### WR-02: A newer SSE context can be submitted even though ApprovalTab still shows the older reviewed detail

**Files:** `frontend/src/hooks/useAgentRun.ts:404-417`, `frontend/src/hooks/useAgentRun.ts:644-667`, `frontend/src/components/details/ApprovalTab.tsx:144-165`, `frontend/src/components/details/ApprovalTab.tsx:195-211`, `frontend/src/components/details/DetailsPanel.tsx:90-99`

The hook and ApprovalTab own separate decision-context snapshots. ApprovalTab loads and displays its own `activeApproval` detail. For the active approval it does not pass that frozen context to the callback; it calls `onApprove()`/`onReject()` without a binding. Meanwhile, a same-identity strictly-newer SSE event replaces the hook's independent `approvalContext` and marks it fresh. On click, the hook GETs and submits its newer context if that GET is exact, even when ApprovalTab is still rendering the older action/risk/version snapshot.

This is a review/TOCTOU failure rather than a backend authorization bypass: the server validates the submitted binding, but the user may authorize a changed revision or proposed-action display that they never re-reviewed. The iteration-2 test only covers “hook cached old context, GET returns newer”; it does not cover “ApprovalTab displays old context, hook already accepted newer SSE.”

**Fix:** Establish one decision-context owner. Prefer passing the exact context displayed/frozen by ApprovalTab into the active callback and require the hook's authoritative GET to be exact to that caller-supplied snapshot. Alternatively, propagate newer SSE replacement into ApprovalTab as an invalidation that forces a visible detail refresh before buttons re-enable. Add an integrated component/hook test: load detail V1, receive SSE V2, click approve, assert no POST until V2 is fetched and explicitly re-reviewed.

### WR-03: Recoverable approval resume is not single-flight, so concurrent identical retries can invoke the graph more than once

**Files:** `src/api/routers/approvals.py:57-58`, `src/api/routers/approvals.py:279-304`, `src/api/routers/approvals.py:538-572`, `src/api/routers/approvals.py:584-609`, `tests/test_approval_api.py:557-726`

The explicit Console path now freezes one byte-identical body, never auto-replays it, and requires a second confirmation. The sequential backend regression also proves one durable `ApprovalDecision` and, for its completed-event failure scenario, one graph invocation.

Backend recovery is still raceable. `attempted` is included in `RESUME_INCOMPLETE_STATUSES`, so `_recoverable_resume_retry_result()` accepts an in-flight attempt. `_record_resume_completed_event_once()` locks the request but returns `False` for `attempted`; `_run_resume_lifecycle()` then appends another attempted event and commits, releasing the lock before `graph.ainvoke()`. A second identical request can therefore observe the first attempted event, follow the same branch, commit its own attempted event, and invoke the graph concurrently.

The decision row remains singular, but graph-side persistence, interrupts, trace/memory finalization, or future authorized handlers can run more than once. Current exact-retry tests are sequential and do not exercise two simultaneous recovery requests.

**Fix:** Add a durable single-flight resume-attempt identity/lease under the ApprovalRequest lock. Treat a live `attempted` attempt as conflict/in-progress; only `failed` or an explicitly stale/abandoned attempt may acquire a new lease. Record completion/failure against that attempt identity. Add a PostgreSQL/HTTP concurrency regression that sends two identical recovery POSTs and proves one `ApprovalDecision`, one active graph invocation, and stable second-request reconciliation.
