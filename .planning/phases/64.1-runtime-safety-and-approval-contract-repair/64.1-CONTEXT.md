# Phase 64.1: Runtime Safety And Approval Contract Repair - Context

**Gathered:** 2026-07-10
**Status:** Ready for planning

<domain>
## Phase Boundary

本 phase 修复 recommendation generation、claim verification、deterministic risk、approval API/SSE/frontend、auto-allowed action draft 与 final response 之间已确认的跨层安全断点。目标是让每一个 actionable recommendation 在进入 action draft 或成功终态前，都经过 canonical action normalization、确定性风险判定、可信授权与可审计的失败传播。

本 phase 不重做 Phase 66 的通用 operation/tool gateway，不承担 Phase 64.2 的 evidence/replay/memory identity，不承担 Phase 69 的 LLM provider/model gateway，也不新增生产外部副作用 executor。

</domain>

<decisions>
## Implementation Decisions

### Canonical action and routing
- **D-01:** actionable recommendation 是否进入 material-claim、risk、approval/action 路径，只能由共享的 canonical action taxonomy/normalizer 决定；禁止继续使用 node-local 中英文关键词集合充当安全路由权威。
- **D-02:** 未识别、歧义或 schema-invalid 的 action candidate 必须 fail closed，不得静默降级为普通成功建议或绕过 `risk_gate`。
- **D-03:** 兼容已有中英文表达，但兼容逻辑必须收敛到共享边界；planner 需要明确旧 producer/caller 的迁移与防漂移测试。

### Deterministic risk authority
- **D-04:** high/medium/low 风险规则由一个后端确定性模型/registry 负责；LLM 输出只能提供受控输入或解释，不得成为降低风险等级的权威。
- **D-05:** timeout、unavailable、parse/schema failure、unknown action/rule 与配置缺失均 fail closed 到 manual review 或 required approval；尤其不得让 medium-risk rule 在 fallback 中消失并变成 low/auto-allowed。
- **D-06:** Phase 63 已建立的 safety taxonomy/risk vocabulary 是语义基础；本 phase 修复 runtime evaluation parity，不另建一套重复风险词表。

### Versioned approval decision contract
- **D-07:** approval list/get/SSE/decide 使用一个 versioned decision-context contract，完整返回前端构造决定请求所需的 `decision_type`、request/level/assignment/revision/lifecycle versions、payload/snapshot hashes 和必要 integrity refs。
- **D-08:** 前端不得猜测、补造或从展示文字反推安全字段；backend/API schema 与 frontend TypeScript type/serializer 必须成对验证。
- **D-09:** stale revision、tenant/run mismatch、assignment/level mismatch、payload/snapshot hash mismatch、unsupported decision type 一律 fail closed，并保持 no-existence-leak 与稳定错误语义。

### Narrow auto-action capability
- **D-10:** auto-allowed draft 只能使用 server-minted、短生命周期、不可扩权的 capability/binding；至少绑定 trusted tenant、actor、run、canonical action、action payload hash、risk decision/ref、merchant scope 与唯一允许的 draft handler。
- **D-11:** capability 只授权 durable draft creation，不授权通用工具调用或生产外部副作用；不得复用客户端 permissions、planner-visible tool permissions 或宽泛 server permission 代替它。
- **D-12:** approval-resume 与 normal auto-allow 可以共享底层 action-draft invariant，但授权来源必须可区分、可审计、不可互换。

### Failure and verification semantics
- **D-13:** action-draft 创建失败、授权验证失败或关键 audit persistence 失败时，不得继续投影 successful final response/completed terminal status；必须形成稳定、可测试的失败或人工处理路径。
- **D-14:** 规划必须拆成多个依赖有序 plan，至少覆盖 canonical action/routing、deterministic risk、approval contract、bounded capability/draft failure，以及端到端 safety matrix/安全验证；不得写成一个跨所有 boundary 的大 plan。
- **D-15:** 验证以 backend contract/integration/graph tests 与 frontend contract tests 为主，测试入口统一使用 `UV_CACHE_DIR=/tmp/uv-cache uv run pytest ...` 或项目 `.venv`；frontend 使用仓库既有 npm/Vitest/Playwright 入口。

### the agent's Discretion
- 在不改变上述 authority、fail-closed 与 scope boundary 的前提下，具体模块名、Pydantic model 拆分、registry 存放位置、migration 分批方式与测试文件分组由 researcher/planner 基于当前源码决定。

</decisions>

<code_context>
## Existing Code Insights

### Reusable Assets
- `src/approvals/schemas.py`: already defines versioned snapshot/proposed-action/auto-allowed binding and strict `ApprovalDecisionCommand`; extend or consolidate instead of creating unrelated DTO families.
- `src/approvals/snapshot_service.py` and `src/common/canonical_hash.py`: existing canonical payload/snapshot hashing must remain the single integrity path.
- `src/approvals/service.py`: existing decision-context and fail-closed hash validation are natural service boundaries for the repaired API contract.
- Phase 63 taxonomy/registry: reuse canonical risk vocabulary and rule ownership rather than recreating local sets.

### Established Patterns
- Pydantic schemas own backend contracts; frontend keeps explicit TypeScript API/SSE types.
- Agent routing uses named graph nodes and strict state projections; authorization must come from trusted server context, not LLM or client-controlled state.
- Approval/action invariants are bound by exact tenant/run/action payload/safety snapshot identity and immutable revisions.
- Demo action behavior stops at durable draft creation; external execution remains out of scope.

### Integration Points
- Recommendation/action normalization feeds material claim generation and `route_after_claim_verify`.
- Deterministic risk output feeds snapshot creation, approval plan or trusted auto-allow binding.
- Approval request projections feed list/get/SSE and the frontend decide request builder.
- Trusted approval-resume and auto-allowed paths converge only at a narrowly authorized action-draft service/tool boundary.
- Draft failures must propagate through graph state, run status, SSE/API projection, and final-response suppression.

</code_context>

<specifics>
## Specific Ideas

- 采用“LLM 将自然语言转为受控 schema，后端安全执行/判定”的架构原则；LLM 不持有 risk downgrade、permission 或 action execution authority。
- Safety matrix 至少覆盖中英文 action variants、unknown/ambiguous action、medium-risk fallback、LLM timeout/invalid schema、stale approval revision、hash mismatch、capability replay/cross-scope misuse、draft failure 与 successful-final suppression。

</specifics>
