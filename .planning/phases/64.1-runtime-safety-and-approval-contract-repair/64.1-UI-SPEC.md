# Phase 64.1 — UI Design Contract

> Phase 64.1 是审批安全契约修复，不是视觉重设计。本合同锁定 Agent Console 的 approval list/get/SSE/decide 类型、请求构造、失败状态与可访问性；现有深色 Console 视觉系统保持不变。

---

## Design System

| Property | Value |
|----------|-------|
| Tool | none（沿用仓库内现有组件） |
| Preset | not applicable |
| Component library | 仓库内 `components/ui`（Radix-style primitives） |
| Icon library | `lucide-react`（仅复用现有图标语义，不为本 phase 增加装饰图标） |
| Font | Inter, system-ui, sans-serif |

### Preservation Boundary

- 保留现有 Agent Console 三栏/详情面板布局、深色主题、Card、Badge、Button、Dialog、Textarea 与 Tabs 组件。
- 保留 Approval tab 作为主入口；不新增审批中心页面、不改变导航、不引入新组件库。
- 允许的 UI 改动仅限：审批数据刷新、状态/错误提示、按钮 enablement、确认对话框文案与必要的字段展示。
- 不展示或允许编辑 integrity hash、version、assignment/level id；它们是 opaque safety fields，只由 typed response 保存并原样提交。

## Approval Decision Contract

### One Versioned Frontend Type

list、get 与 `approval_required` SSE 必须投影同一个 `ApprovalDecisionContextV1`。字段名以 backend JSON snake_case 为准，不在 serializer 中改名、猜测或从展示文字重建。

```ts
type ApprovalDecisionType =
  | 'accept'
  | 'approve'
  | 'edit'
  | 'respond'
  | 'reject'
  | 'ignore'

interface ApprovalDecisionContextV1 {
  schema_version: 'approval_decision_context.v1'
  approval_id: string
  tenant_ref: string
  run_id: string
  thread_id: string
  status: string
  allowed_decision_types: ApprovalDecisionType[]
  level_id: string
  assignment_id: string
  request_version: number
  level_version: number
  assignment_version: number
  revision: number
  action_payload_hash: string
  safety_snapshot_ref: string
  safety_snapshot_hash: string
  proposed_action: Record<string, unknown>
  risk_level: string
  risk_rule_ref: string | null
  risk_reason: string | null
  expires_at: string
  created_at: string
}
```

- `GET /approvals` 的每一项、`GET /approvals/{id}` 的 data、SSE `approval_required.payload.decision_context` 必须满足同一 runtime validator；缺字段、错误 schema version、空 hash 或非法 version 均视为不可决定（non-decidable）。
- `approval_id`、`tenant_ref`、`run_id`、`thread_id`、`level_id`、`assignment_id`、versions、revision、hashes 与 refs 是不可变 decision binding。前端不得用当前 run、登录用户、旧 SSE payload 或默认值补齐缺失字段。
- SSE 只可用相同 identity 且更新 revision/version 的 context 替换缓存；旧 revision、不同 run/tenant/assignment/level 的事件不得覆盖 active context。
- 列表用于发现候选项；用户选中后必须以 get 返回的最新完整 context 为提交依据。若 get 尚未完成，决定按钮保持禁用。

### Exact Decide Request Construction

```ts
interface ApprovalDecideRequestV1 {
  decision_type: ApprovalDecisionType
  expected_request_version: number
  expected_level_version: number
  expected_assignment_version: number
  expected_revision: number
  action_payload_hash: string
  safety_snapshot_hash: string
  reason?: string
  edited_action?: Record<string, unknown>
  response_text?: string
}
```

`POST /approvals/{approval_id}/decide` 的构造规则：

1. URL id 只取当前最新 `ApprovalDecisionContextV1.approval_id`。
2. `decision_type` 必须来自用户点击动作，且存在于 `allowed_decision_types`；现有“批准”映射为 backend 接受的 `approve`，“驳回”映射为 `reject`。禁止继续发送旧字段 `decision`。
3. 四个 `expected_*` 与两个 hash 必须从同一个 context snapshot 原样拷贝；不得跨 list/get/SSE context 混拼。
4. `reason`：reject 必填并 trim 后非空；approve 可不传。禁止固定英文批准理由替代用户输入或协议字段。
5. 本 phase Console 不新增 edit/respond UI；即使后端 allowed list 包含它们，也不显示对应按钮。API serializer 仍以 discriminated union 支持未来调用方，`edit` 必须带 `edited_action`，`respond` 必须带 `response_text`。
6. 提交开始即冻结 context snapshot、禁用两个按钮并防重复提交；响应完成前 list/SSE 更新不得改变本次 request body。
7. 成功后清除冻结 snapshot，重新 get/list 并由 run polling/SSE 驱动后续状态；不得仅靠 optimistic UI 宣告 action 已执行或 run 已成功。

### SSE Integration

- `approval_required` 事件必须携带完整 `decision_context`，同时保留用于 timeline 展示的 `approval_id`、`risk_level`、`proposed_action`；展示字段不得成为 decide request 的来源。
- `useAgentRun` 以当前 `run_id` + generation guard 接收 context；旧 run、reset/new conversation 之前的 callback 一律忽略。
- malformed 或不完整的 approval context 不得被静默忽略后继续显示可批准状态：timeline 保留“需要审批”，Approval tab 显示“审批信息不完整，请刷新”，决定按钮禁用。
- stream disconnect 不清除已显示的审批事实，但把 context 标为需重新验证；重新连接或 get 校验成功前禁止提交。

## Interaction States

| State | Trigger | UI behavior | Available action |
|-------|---------|-------------|------------------|
| Loading list | Approval tab 打开/刷新 | 保留 Card 结构，显示“正在加载待审批项…”；不显示空态 | 无 |
| Empty | list 成功且 `total=0` | “当前没有待处理审批” | 刷新/继续当前对话 |
| Loading detail | 选择列表项或收到 approval SSE | 显示选中项摘要，详情区显示加载态 | 不可批准/驳回 |
| Ready | get/context validator 通过、status pending、未过期、有允许动作 | 显示 action 与 risk，按钮按 allowed types 启用 | 批准或驳回 |
| Submitting | 确认提交后 | 对话框与两个主按钮 disabled；按钮文案“提交中…” | 无，防双击 |
| Success | decide API 成功 | 关闭确认框，显示“审批决定已提交，正在同步运行状态”；刷新 list/get | 等待 SSE/polling |
| Stale | revision/version stale 或服务返回稳定 stale code | 不重放旧请求；关闭确认框，显示“审批已更新，请查看最新内容后重新决定”；自动 get 一次 | 重新审阅，用户再次确认 |
| Binding mismatch | tenant/run/assignment/level/hash mismatch | fail closed；清除 active decidable context，保留通用错误，不展示资源是否存在 | 返回列表/刷新；不可重试原 body |
| Unsupported decision | 点击动作不在 allowed list 或服务拒绝 | 不发送或不自动替换 decision type；提示“此审批当前不支持该决定，请刷新” | 刷新 |
| Expired/non-pending | expires_at 已过或 status 不再 pending | 状态 Badge 更新，按钮禁用 | 刷新/选择其他项 |
| Load/network failure | list/get 请求失败 | 保留上次展示摘要但标记不可决定；显示“审批信息加载失败，请重试” | 重试加载 |
| Decide network ambiguity | POST 断线/超时，不知是否落库 | 不自动重发；提示“提交结果未确认，正在查询最新状态”并 get | 查询确认后再决定 |
| Draft/runtime failure | 决定后 action draft/关键 audit 失败，run 进入 failed/manual path | timeline 与消息区显示失败/需人工处理；不得展示 completed 或成功执行文案 | 重试新查询或联系管理员 |
| No permission | 当前角色无审批权限 | 沿用只读权限 Card；隐藏 risk/action 敏感详情与决定按钮 | 切换授权角色 |

### Error Semantics

- no-existence-leak：404、跨 tenant/run/scope mismatch 等面向前端统一为“审批不可用或已更新”，不得提示其他 tenant、actor、merchant 或资源是否存在。
- 错误代码用于稳定分支，服务端 message 仅作为受控补充；不得把原始 exception、hash、内部 id binding diff 输出给用户。
- stale 与未知提交结果可恢复但必须重新读取；integrity mismatch 不得自动重试或沿用旧 context。
- Approval tab 的 `loadError` 与 run-level `error` 分开：列表加载失败不能把整个 run 错标为 failed；draft/runtime failure 则必须反映到 run terminal state。

## Copywriting Contract

| Element | Copy |
|---------|------|
| Primary CTA | 批准 |
| Secondary destructive CTA | 驳回 |
| Approve confirmation | 确认批准此操作？系统将创建已授权的操作草稿；本页面不会直接执行生产外部操作。 |
| Reject confirmation | 确认驳回此操作？请填写驳回原因。 |
| Empty state heading | 当前没有待处理审批 |
| Loading error | 审批信息加载失败，请重试。 |
| Incomplete contract | 审批信息不完整，请刷新后再决定。 |
| Stale state | 审批已更新，请查看最新内容后重新决定。 |
| Binding/integrity failure | 审批不可用或已更新，请返回列表并刷新。 |
| Unknown submission | 提交结果未确认，正在查询最新状态。请勿重复提交。 |
| Success pending resume | 审批决定已提交，正在同步运行状态。 |
| Draft failure | 操作草稿创建失败，本次运行未完成。请重试或联系管理员。 |

禁止使用“批准后将立即执行”“操作已成功执行”等超出 durable draft boundary 的文案。

## Accessibility

- 列表项使用可聚焦 button，并以 `aria-pressed` 或 `aria-current` 表示当前选择；不能只靠 cyan border 区分。
- 每个风险 Badge 同时显示文字（高/中/低或受控 fallback），颜色不是唯一信息来源。
- 加载、提交成功、stale、network ambiguity 与失败消息放入合适的 `aria-live` region；普通状态 `polite`，阻止决定的 integrity/draft failure 使用 `assertive`。
- 确认 Dialog 打开时焦点进入标题/首个可操作控件，关闭后回到触发按钮；Escape 与“取消”均不提交。
- reject Textarea 必须有可见 label 或 `aria-label`、错误说明和 `aria-describedby`；空白 reason 时除禁用确认按钮外还提供文本原因。
- 所有决定按钮维持现有 `min-h-11`（44px）点击目标；disabled 与 submitting 状态除视觉变化外设置原生 `disabled`/`aria-disabled`。
- 键盘用户可完成列表选择、审阅、打开确认、取消与提交；focus ring 使用现有 `--ring` token，不移除 outline。
- hash 与内部 integrity refs 默认不进入可访问树，避免无意义朗读及敏感实现信息泄露。

## Verification Contract

- Frontend API contract tests：list/get/SSE 三来源均解析同一 v1 type；缺任一 binding 字段时 fail closed。
- Serializer tests：approve/reject exact JSON keys；确认无 `decision` 旧字段、无默认 version/hash、无跨 context 混拼。
- Hook/component tests：stale run/SSE 忽略、detail 未验证时按钮禁用、double-submit 被阻止、stale 自动刷新但不自动重放、network ambiguity 查询状态。
- Component accessibility tests：dialog focus、live region、list selected semantics、reject reason label/error、按钮 disabled。
- Playwright：等待审批 → 选择最新 detail → reject/approve confirmation → 成功同步；另覆盖 stale revision 与 draft failure 不出现成功终态。
- Backend/frontend fixture 使用同一 `approval_decision_context.v1` JSON；API schema 或 TypeScript type 漂移必须使测试失败。
- Frontend 验证使用仓库既有 `npm test`、`npm run build`、`npm run e2e`；涉及 backend 的验证必须使用 `UV_CACHE_DIR=/tmp/uv-cache uv run pytest ...`，禁止裸 pytest。
