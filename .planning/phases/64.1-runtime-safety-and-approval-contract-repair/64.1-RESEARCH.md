# Phase 64.1 Research: Runtime Safety And Approval Contract Repair

**Researched:** 2026-07-10  
**Status:** Complete  
**Scope:** 仅为 Phase 64.1 规划提供仓库事实；不把 `docs/contract-spec.md` 的目标态误写为已实现事实。

## Executive Summary

Phase 64.1 不是单点 bug fix，而是五个有依赖顺序的安全边界修复：canonical action/routing、deterministic risk、versioned approval decision context、server-minted bounded draft capability、terminal/failure propagation 与端到端验证。当前代码已具备 Phase 63 taxonomy、canonical hash、snapshot、approval lifecycle、demo draft 等可复用基础，但各层尚未形成一个闭合的授权链。

最直接的已确认缺陷如下：

1. recommendation node 仍以本地英文 token 集合和 substring 判断 actionable；中文或未知表达可只生成 policy claim，随后从 `route_after_claim_verify` 落到普通 `final_response`（`src/agent/nodes/recommendation_generation.py:34-40,598-664`; `src/agent/routing.py:855-869`）。
2. risk fallback 只做 high-rule match，否则直接取第一条 low rule；`rules/risk_rules.yaml` 明明有 medium group，但 fallback 完全不评估它（`src/agent/nodes/risk_gate.py:129-150,1101-1134`; `rules/risk_rules.yaml:5-31`）。LLM timeout/schema failure 因而可能把 medium action 降到 low/allow（`src/agent/nodes/risk_gate.py:1244-1287`）。
3. 后端 decide body 要求 decision type、四个 lifecycle version 和两个 hash（`src/api/schemas/approvals.py:10-22`），但 frontend 只发送 `{decision, reason}`，且字段名是 `decision`（`frontend/src/lib/api.ts:172-180`）。list response 的 TS type 又没有这些字段（`frontend/src/lib/api.ts:10-25`）。
4. `AutoAllowedActionBindingV1` 已绑定 tenant/run/merchant/hash/risk/evidence，但没有 actor、canonical action、expiry、nonce/capability identity、唯一 handler（`src/approvals/schemas.py:63-80`）。它由 risk node 直接构造并放入 graph state（`src/agent/nodes/risk_gate.py:734-763,859-899`），属于 durable binding，不是 server-minted、短生命周期、不可跨 handler 使用的 capability。
5. action node 已把工具错误投影为 error trace（`src/agent/nodes/action_draft.py:196-222,564-570`），但 graph 无条件从 `action_draft` 进入 `final_response`（`src/agent/graph.py:375`），final response 的默认尾路仍写 `final_status: completed`（`src/agent/nodes/final_response.py:1219-1239`）。因此 draft failure 可以被包装进成功文本/成功终态。

## Planning Inputs And Boundaries

- Roadmap 目标：所有 actionable recommendation 在 draft 或成功终态前完成 normalization、deterministic risk、authorization、audit；success criteria 明确要求 unknown/malformed/stale/hash mismatch/draft failure fail closed（`.planning/ROADMAP.md:116-135`）。
- Context 决策 D-01..D-15 是本 phase 的锁定约束，尤其禁止 node-local keyword 作为安全权威，禁止 LLM 降级风险，禁止客户端猜安全字段，并要求至少五个有序 plan（`.planning/phases/64.1-runtime-safety-and-approval-contract-repair/64.1-CONTEXT.md`）。
- 复用 Phase 63 的 `src/agent/safety/taxonomy.py`。该模块已经定义 canonical action resolution、`low|medium|high` 与 `allow|approval_required|manual_review|blocked` vocabulary，并对 unknown/default 采用 medium/manual-review 语义（`src/agent/safety/taxonomy.py:110-111,368-386`）。本 phase 不再造一套风险词表。
- 不做 Phase 66 的 general operation/tool gateway；仅修 recommendation 到唯一 demo draft handler 的 action contract。不开 production executor。
- 不做 Phase 64.2 evidence/replay/memory identity；只携带/校验本 phase 授权所必需的 existing refs/hashes。
- 不做 Phase 69 LLM gateway；只确保当前 LLM timeout/unavailable/invalid output 的 runtime safety fallback 正确。

## 1. Canonical Action And Routing

### Current implementation

- `_ACTIONABLE_RECOMMENDATIONS` 是 recommendation node 私有集合，只有 `issue_coupon`, `approve_refund`, `full_refund`, `partial_refund`, `compensation`（`src/agent/nodes/recommendation_generation.py:34-40`）。
- `_is_actionable_recommendation` 对任意值做 `casefold()` 后 substring 搜索（`src/agent/nodes/recommendation_generation.py:662-664`）。这既漏中文/alias/结构化 action，也可能把包含 token 的非 action 文本误判。
- action claim 只有该函数为 true 时才生成（`src/agent/nodes/recommendation_generation.py:598-642`）；risk hints 同样复用该判断（`src/agent/nodes/recommendation_generation.py:649-659`）。
- 后续路由本身较严格：claim bundle 必须 continue 且 verified/not_required，verified action recommendation 或 risk signal 才进 risk gate（`src/agent/routing.py:855-869,918-930`）。问题在于上游未生成 action claim 时，这个严格路由看不到 action。
- action draft 已使用 `resolve_action_text` 并拒绝无 executable type（`src/agent/nodes/action_draft.py:511-527`），但 normalization 发生得太晚，无法保护 material-claim 与 risk routing。

### Planning direction

建立共享 canonical action candidate schema/normalizer，输出至少：canonical action id/type、match kind、disposition、schema validity、原始输入/alias provenance。recommendation producer 在生成 material claims 前调用；routing、risk、snapshot/action draft 只消费 canonical output。unknown/ambiguous/schema-invalid candidate 必须生成可验证的 action claim 或显式 safety block，并进入 manual-review/approval-required 路径，不能作为普通建议 completed。

迁移必须覆盖 recommendation generation、routing helpers、risk gate 与 action draft 的重复判断，并增加 architecture drift test，禁止这些节点重新出现 actionable keyword set。Phase 66 才统一所有 operation contracts；此处只处理 Phase 64.1 action taxonomy 的窄边界。

## 2. Deterministic Risk Authority

### Current implementation

- rules 文件已有 high、medium、low 三组（`rules/risk_rules.yaml:5-31`）。
- `_deterministic_rule_match` 只迭代 `high_risk`（`src/agent/nodes/risk_gate.py:129-150`）。正常 LLM path 也只允许 high rule 覆盖 LLM（`src/agent/nodes/risk_gate.py:1194-1209`）；medium 仍取决于 LLM。
- `_fallback_risk` 对 no-action 特判 low/allow；否则 high match；再否则直接 low/allow（`src/agent/nodes/risk_gate.py:1101-1134`）。
- structured output 连续失败后调用该 fallback 并继续 `_attach_snapshot_binding`（`src/agent/nodes/risk_gate.py:1244-1287`），因此 timeout/parse failure 不是 fail-closed。
- `_load_risk_rules` 没有 schema/absence guard，配置缺失可能直接抛出而不是产出稳定 manual-review decision（`src/agent/nodes/risk_gate.py:94-96,1137-1145`）。

### Planning direction

把 deterministic evaluator/registry 作为唯一 severity/disposition authority：按 canonical action 和受控 business inputs 完整评估 high/medium/low；LLM 只可补 explanation/受控 signals，最终结果只能保持或升级 deterministic severity，不能 downgrade。unknown action/rule、配置缺失/invalid、LLM unavailable/timeout/schema failure 均生成稳定 `medium + manual_review`（或 policy 明确的 stronger approval/blocked）结果；不得创建 auto-allow capability。

风险 decision 要继续使用 `RiskDecisionV1` 和已有 config/policy version、hash/snapshot 路径（`src/agent/nodes/risk_gate.py:624-644`），避免另起 DTO。需对 rules YAML 增加启动/单测级 schema validation，明确 rule precedence、无匹配行为和 duplicate/conflicting rule 行为。

## 3. Approval Backend/API/SSE/Frontend Contract Parity

### Current implementation

- backend `DecideRequest` 是 strict `extra=forbid`，且要求 `decision_type`, request/level/assignment/revision versions、action/snapshot hashes（`src/api/schemas/approvals.py:10-36`）。
- service command 具有同一组字段（`src/approvals/schemas.py:147-177`）；router 逐字段构造 command（`src/api/routers/approvals.py:120-139`）。service 对 request、level、assignment versions 做并发校验（`src/approvals/service.py:208-228`），hash mismatch 被映射为 stable conflict（`src/api/routers/approvals.py:955-964`）。这些应保留。
- `ApprovalResponse` 只返回 revision/request version，没有 level id/version、assignment id/version、allowed decision types/decision-context schema version（`src/api/schemas/approvals.py:51-82`）。`_to_response` 同样无法补齐（`src/api/routers/approvals.py:974-1010`）。
- approval-required SSE payload 实际已有 expected versions、hashes 和 allowed decision types（`src/api/routers/agent_runs.py:848-885`），但 frontend event type 只声明少量 optional approval fields，UI/decision builder 没消费完整 context。
- frontend list record 缺所有 decision context 字段，`decideApproval` 只发错误形状 `{decision, reason}`（`frontend/src/lib/api.ts:10-25,172-185`）。hook 与 ApprovalTab 都直接调用这个 helper（`frontend/src/hooks/useAgentRun.ts:480-534`; `frontend/src/components/details/ApprovalTab.tsx:123-134`）。

### Planning direction

定义一个 versioned `ApprovalDecisionContextV1`，由 service 组装并由 list/get/SSE 共用；字段至少含 schema version、decision type choices、request/level/assignment ids+versions、revision、action payload hash、snapshot ref/hash、必要 integrity refs、run/thread/tenant-safe identity。`ApprovalResponse` 可嵌套该 context，避免三个投影各自复制。

前端用对应 TS type 和一个 serializer 构造 `DecideRequest`；不得从展示文本、risk label 或当前 UI state猜字段。SSE context 只作即时 UX，list/get 是 refresh/reconnect 后的权威恢复入口。所有 unsupported decision、stale version、tenant/run/assignment/level/hash mismatch 应以稳定 404/403/409 语义 fail closed；跨租户查找继续采用 no-existence-leak 404。

## 4. Narrow Server-Minted Auto-Action Draft Capability

### Current implementation and gap

- 当前 auto binding 已含 tenant/run/merchant、payload+snapshot hashes、risk ref、idempotency、facts/evidence（`src/approvals/schemas.py:63-80`），并在 action node 和 ActionService 两层校验 snapshot/tenant/run/binding（`src/agent/nodes/action_draft.py:286-325,444-493`; `src/actions/service.py:217-298`）。这是很好的 invariant 基础。
- 但 binding 不含 actor、canonical action、handler、issued/expiry、nonce/key id/signature 或 durable capability record；risk node 可直接构造它（`src/agent/nodes/risk_gate.py:734-763`）。它不能证明“server minted”、不能限制 lifetime/replay，也不能阻止同一 binding 被带到其他未来 handler。
- action node 通过普通 `ToolPlatform.invoke` 调用 `create_coupon_grant_draft`（`src/agent/nodes/action_draft.py:529-595`）；capability 目前没有成为 tool/service boundary 的显式授权输入。

### Planning direction

将 auto-allowed binding 升级/包裹成 server-minted capability。最小绑定：trusted tenant、actor、run、canonical action、payload hash、snapshot hash/ref、risk decision ref+disposition、merchant scope、唯一 handler=`create_coupon_grant_draft`、issued_at/expires_at、nonce/capability ref、schema/key version。mint 只能在 deterministic evaluator 已确认 allow、snapshot persisted 且 trusted server context 存在时发生。

验证应放在 action service/draft handler boundary，而非只在 graph node。验证失败、过期、重放到不同 run/tenant/actor/merchant/action/payload/handler 必须 no draft。capability 只授权 durable demo draft，不写入/扩大 `TrustedContext.permissions`，不授权一般 ToolPlatform 操作，不授权生产副作用。approval resume 继续用 `TrustedApprovalResultV1`；两条路径共享 payload/snapshot/merchant/draft invariants，但 audit authorization source 必须区分 `approval` 与 `auto_allow_capability`。

## 5. Draft Failure And Terminal Propagation

### Current implementation

- executor 将非成功/异常统一成 safe ToolResult error（`src/tools/executors/action.py:59-105`）；ActionService 捕获未知异常返回 `DRAFT_CREATION_FAILED`（`src/actions/service.py:206-215`）。
- action node 在 tool failure 时生成 `action_result.status=error` 和 error trace（`src/agent/nodes/action_draft.py:196-222,564-570`）。
- graph 固定 `action_draft -> final_response`（`src/agent/graph.py:375`）。final response 对 approved-but-draft-failed 仅生成一段文字（`src/agent/nodes/final_response.py:1035-1043`），随后默认 projection 仍是 `final_status=completed`（`src/agent/nodes/final_response.py:1219-1239`）。

### Planning direction

新增 action-draft 后置路由或统一 terminal guard：只有 validated `DraftOutcomeV1.status=not_executed_demo` 且 durable draft id 存在，才允许 completed success。tool error、invalid response/outcome、capability/auth failure、critical audit persistence failure必须进入稳定 error/manual-handling terminal，清空/抑制 success final response，且 DB run status、SSE final event、API polling projection一致。不要把“给用户一段失败说明”误当 completed success。

approval resume router 也必须复用同一 guard；当前 `_run_approved_resume` 已根据 `node_errors`/missing response 设置 error，但需要覆盖 action_result failure、draft outcome invalid 和 audit failure，而不能仅依赖 node_errors（`src/api/routers/approvals.py:327-377`）。

## Recommended Plan Decomposition

按项目 PLAN 粒度硬约束，建议至少 5 个编号 plan：

1. **64.1-01 Canonical Action Contract And Routing** — shared schema/normalizer、producer migration、claim/routing fail-closed、中文/英文/unknown tests。仅建立 action identity，不改 general tool gateway。
2. **64.1-02 Deterministic Risk Registry And Fail-Closed Fallback** — 完整 high/medium/low evaluator、rule config validation、LLM non-authority、snapshot/risk decision parity。依赖 01。
3. **64.1-03 Versioned Approval Decision Context** — service DTO、list/get/SSE/API parity、frontend type/serializer/UI/hook、stale/hash/scope contract tests。可在 02 后与 04 部分并行，但最终 integration 依赖 canonical risk output。
4. **64.1-04 Bounded Auto-Allow Capability And Draft Terminal Guard** — server mint/verify、handler binding、expiry/replay/scope checks、approval-vs-auto authorization audit source、draft failure propagation。依赖 01-02；approval resume integration 依赖 03。
5. **64.1-05 End-to-End Safety Matrix And Drift/Security Gates** — backend graph/API/SSE + frontend contract tests、architecture drift guards、threat verification、docs/debt/validation artifacts。依赖 01-04。

若 planner 发现 04 同时跨 capability persistence/cryptographic mint 与 terminal orchestration 两个 ownership boundary，应拆成 04 capability、05 terminal propagation、06 safety matrix，而不是合并成大 plan。

## Validation Architecture

### Test layers

1. **Pure contract/unit tests**
   - canonicalizer table: canonical English、Chinese aliases、case/spacing、ambiguous、unknown、schema-invalid；assert canonical id + disposition，不只 assert boolean。
   - deterministic risk table: each high/medium/low rule、precedence、missing/invalid YAML、unknown action/rule、LLM timeout/invalid schema；assert no downgrade and no auto capability on fallback.
   - Pydantic/TS decision context parity: required keys、literal decision types、schema version、extra/missing rejection。
   - capability verifier: expiry、nonce replay、wrong tenant/actor/run/action/payload/snapshot/merchant/handler/risk disposition。

2. **Node/graph integration tests**
   - extend `tests/agent/test_nodes/test_recommendation_generation.py`, `tests/agent/test_nodes/test_risk_gate.py`, `tests/test_graph_routing.py`, `tests/agent/test_graph.py`.
   - full path cases: canonicalize -> material action claim -> claim verified -> deterministic risk -> approval or trusted auto allow -> draft.
   - negative path must assert both `no ActionDraft row` and `no completed final_response`.

3. **Approval/service/API/SSE integration tests**
   - extend `tests/approvals/test_service_transitions.py`, `tests/test_approval_api.py`, `tests/test_approval_integration.py`, `tests/test_agent_runs_api.py`.
   - list/get/SSE return equivalent decision context; decide round-trip succeeds from returned context.
   - stale revision/version, assignment/level mismatch, tenant/run/hash mismatch, unsupported decision all stable fail-closed; cross-tenant remains no-existence-leak.
   - reconnect test: frontend can recover from list/get without relying on old SSE event.

4. **Action boundary tests**
   - extend `tests/actions/test_phase34_action_draft_bindings.py`, `tests/actions/test_action_draft_v2.py`, `tests/architecture/test_action_draft_boundaries.py`.
   - capability can invoke only the draft handler and cannot broaden tool permissions; replay/cross-scope misuse yields zero durable drafts.
   - injected store/audit/tool failure yields error/manual terminal, no final success event, no completed AgentRun.

5. **Frontend tests**
   - extend `frontend/src/hooks/useAgentRun.test.ts` and add/extend API/ApprovalTab tests.
   - assert exact JSON request body uses `decision_type` and echoed context fields; no inferred defaults.
   - stale conflict preserves safe UI state and refetches context; malformed/missing context disables decision rather than sending partial body.

6. **Architecture drift guards**
   - no node-local actionable keyword authority in recommendation/routing/risk/action nodes.
   - one backend decision-context model feeds list/get/SSE.
   - no direct `action_draft -> successful final` without terminal guard.
   - only declared mint service creates auto capability; only draft handler accepts it.

### Required safety matrix

| Case | Expected route/terminal | Draft invariant |
|---|---|---|
| canonical English/Chinese low action | deterministic allow -> valid capability -> draft -> completed demo | exactly one durable draft |
| medium action | approval/manual review | none before trusted decision |
| high action | approval required | none before trusted decision |
| unknown/ambiguous/schema-invalid action | manual review/error, never ordinary completed advice | none |
| LLM timeout/unavailable/invalid schema | deterministic severity or medium/manual fallback | no auto draft unless deterministic allow independently proven |
| stale revision/version or hash mismatch | 409/closed; no resume | none |
| cross tenant/run/actor/merchant/handler capability | authorization failure | none |
| expired/replayed capability | stable closed response; idempotent same-use behavior explicitly specified | no new draft |
| draft store/tool/audit failure | error/manual terminal; no success SSE/final | none or rolled-back partial row |

## Security Threats And Required Mitigations

| Threat | Current exposure | Required mitigation/test |
|---|---|---|
| Action-routing bypass | 中文/未知 action 未生成 action claim，可能跳过 risk | shared canonicalizer；unknown/ambiguous fail closed；multilingual matrix |
| Risk downgrade | medium rules absent from fallback；LLM controls medium/low | deterministic full registry；LLM cannot lower severity；timeout/config-failure tests |
| Client-forged decision context | frontend currently sends partial/wrong payload; future temptation to default fields | server-returned versioned context + exact echo; forbid defaults/inference |
| TOCTOU/stale approval | lifecycle/hash values can change between render and decide | atomic service checks of request/level/assignment/revision/hashes; 409 tests |
| Cross-tenant existence leak | approval lookup/scope errors can reveal ids | tenant-scoped lookup and stable 404; explicit cross-tenant tests |
| Capability confused deputy | current binding has no actor/action/handler/expiry | bind all dimensions; verify at draft service; unique handler allowlist |
| Capability replay | current durable binding has idempotency but no explicit expiry/nonce | short TTL + nonce/ref + durable consumption/idempotency semantics; replay tests |
| Permission broadening | normal ToolPlatform context could be mistaken for capability | capability must not mutate general permissions; handler-specific verifier and architecture guard |
| Payload substitution | action normalized after snapshot or payload changes after approval | canonicalize before hash/snapshot; recompute canonical hash at trust boundary |
| Success laundering | draft failure reaches default completed final response | terminal guard across graph, API, DB, SSE; failure injection tests |
| Audit omission | critical mint/consume/draft audit persistence may fail silently | transactional/explicit fail-closed audit requirement; no completed terminal without audit evidence |

## Open Design Decisions For Planner

- Capability 可以是 signed envelope 或 durable DB record + opaque ref；两者都必须满足 server mint、expiry/replay、key/schema version 与 handler binding。planner 应根据现有 DB/migration 面选择，不得退回 graph-state plain dict 即可信。
- Unknown action 的 terminal 可选 `manual_review` 或 required approval，但必须稳定、可审计且不能创建 draft/成功完成；与 Phase 63 taxonomy 的 default resolution 保持一致。
- Critical audit persistence 的原子边界需依据现有 `ActionDraftStore`/event transaction 行为细化。若 event emission 当前不与 draft 同事务，plan 必须明确 rollback 或 pending-reconciliation 状态，不能把失败吞掉。
- Approval context 是嵌套对象还是 flat compatibility projection 可由 planner 决定；唯一要求是 backend canonical model 单一来源，frontend 不猜字段，并给兼容迁移和 drift test。
