## 1. System Classification

**System Type:** Hybrid (RAG + Stateful Agent Workflow)

**Description:**
A refund operations assistant that accepts merchant/support agent questions about refund issues, orchestrates an 8-node LangGraph state machine to identify intent, load business context via read-only tools, retrieve policy evidence from a vector knowledge base, generate evidence-cited recommendations with risk labeling, and persist execution traces and multi-turn memory. "Good" means every business conclusion cites specific policy evidence, insufficient evidence triggers explicit refusal, and the full execution path is auditable by run_id.

**Critical Failure Modes:**
1. Policy fabrication — generating refund advice citing non-existent rules (defended by citation validator)
2. Evidence-insufficient false confidence — outputting definitive conclusions when retrieval returns low-confidence or no results
3. Cross-turn context contamination — applying previous turn's order data to a different order in the same thread
4. Trace incompleteness — producing a response without recording all nodes traversed and tools called
5. Permission bypass — returning data from a tenant/user the caller has no access to

## 1b. Domain Context

> Researched by `gsd-domain-researcher`. Grounds the evaluation strategy in domain expert knowledge.

**Industry Vertical:** E-commerce platform operations / Customer service tooling

**User Population:** 商家运营人员（merchant operators）和平台客服专员（platform support agents）。用户不是终端消费者，而是处理退款纠纷、查询退款规则、提交补偿建议的内部业务人员。使用场景：工作台内嵌工具，单次会话处理一个退款问题，多轮对话补充信息。

**Stakes Level:** High

**Output Consequence:** 客服专员或商家运营人员根据系统给出的处理建议直接决定退款处理方式——批准、驳回或上报审批。错误建议会导致：不该退的款被退（直接财务损失）、该退的款被拒（客户投诉升级、平台信誉受损）、风险动作未被识别（绕过审批流程）。Phase 3 输出为只读建议，但建议质量直接影响 Phase 4 审批决策的输入质量。

### What Domain Experts Evaluate Against

**Dimension: 规则引用的可追溯性（Policy citation traceability）**
Good（专家会接受）: 回答明确引用具体规则文档的 doc_id 和 chunk_id，并附上规则段落摘要，例如"根据 policy_refund_timeout / chunk_003：超过 7 天自动退款窗口的订单需人工审核"。
Bad（专家会标记）: 回答给出处理建议但未引用任何规则来源，或仅说"根据平台规则"而不指向具体文档。
Stakes: Critical
Source: 客服运营实践——无来源的退款建议无法被审批人核实，且在纠纷升级时无法举证；参考 Air Canada 案例：AI 给出无授权退款承诺导致法律责任（agentmodeai.com, 2024-2025）

---

**Dimension: 证据不足时的拒绝行为（Evidence-insufficient refusal）**
Good（专家会接受）: 当检索结果低于置信阈值时，系统明确说明"当前知识库中未找到支持该判断的规则依据"，并列出缺失的信息项和建议的补充步骤，不给出确定性结论。
Bad（专家会标记）: 系统在证据不足时仍输出"通常可以退款""应该符合补偿条件"等模糊确定性表述，或用自然语言掩盖证据缺失。
Stakes: Critical
Source: REQUIREMENTS.md AGNT-08、RAG-06；生产部署失败模式研究——"confident wrong answers"是客服 LLM 最常见的高危失败模式（Towards AI, 2024）

---

**Dimension: 意图识别的准确性（Intent routing accuracy）**
Good（专家会接受）: 系统正确区分"规则问答（policy_qa）""退款排障（refund_troubleshooting）""补偿建议（compensation_suggestion）""审批请求（approval_request）"，并路由到对应处理流程；对 unknown 意图明确说明无法处理。
Bad（专家会标记）: 将退款排障问题误识别为规则问答，导致系统只检索规则而不加载订单数据；或将需要审批的补偿请求识别为普通问答，跳过风险标记。
Stakes: High
Source: REQUIREMENTS.md AGNT-01；客服系统实践——意图误分类是工单路由错误的首要原因，直接影响后续所有节点的输出质量

---

**Dimension: 执行轨迹的完整性（Execution trace completeness）**
Good（专家会接受）: 每次响应附带 trace_summary，包含 run_id、经过的节点列表、调用的工具名称、引用的证据数量、风险等级和最终状态；审批人或主管可通过 run_id 回溯完整处理过程。
Bad（专家会标记）: 响应只有自然语言结论，无法判断系统经过了哪些步骤、调用了哪些数据、依据了哪些规则；或 trace 存在但节点记录不完整（缺少工具调用记录或证据引用）。
Stakes: High
Source: REQUIREMENTS.md AGNT-06、SAFE-06；电商平台运营实践——退款纠纷审计要求完整操作记录，不可追溯的 AI 建议在内部审查中等同于无效建议

---

**Dimension: 风险等级标记的一致性（Risk level labeling consistency）**
Good（专家会接受）: 相同类型的退款场景（金额、原因、商家等级相同）在不同会话中得到相同的风险等级标记（low/medium/high），标记依据可追溯到 risk_rules.yaml 中的具体规则。
Bad（专家会标记）: 同一类型的退款申请在不同运行中得到不同风险等级，或风险等级与实际业务规则不符（高金额补偿被标记为 low risk）。
Stakes: High
Source: REQUIREMENTS.md SAFE-01；平台风控实践——风险标记不一致会导致审批流程被绕过或被过度触发，两者都会造成运营损失

### Known Failure Modes in This Domain

**1. 规则幻构（Policy fabrication）**
系统在知识库中没有相关规则时，仍生成听起来合理的退款政策描述。在电商退款场景中，这表现为：引用不存在的"7天无理由退款延期条款"、编造特定商家类别的补偿标准、或将过期规则当作现行规则引用。Air Canada 案例（2024）是最典型的生产事故：AI 给出了平台实际政策不支持的退款承诺，最终导致法律责任。本系统通过 citation validator 二次校验 doc_id/chunk_id 存在性来防御此模式。

**2. 跨轮上下文污染（Cross-turn context contamination）**
在多轮对话中，前一轮加载的订单数据或检索到的规则被错误地应用到后一轮不同订单的问题上。表现为：用户在第二轮询问另一个订单时，系统仍基于第一轮的 order_id 给出建议，但未明确说明数据来源。这在退款场景中会导致错误的金额判断或错误的规则适用。

**3. 置信度虚高（Overconfident low-evidence response）**
检索到的规则与当前问题相关性较低（score 接近阈值），但系统仍以确定性语气输出建议，未降低置信度表述。在退款排障场景中，这表现为：订单状态异常但规则库中没有精确匹配的处理规程，系统却给出"建议直接退款"而非"证据不足，建议人工确认"。Klarna 案例（2024-2025）显示，这类质量退化在规模化部署后会导致客诉率上升和人工接管成本增加。

**4. 意图-数据不匹配（Intent-data mismatch）**
系统正确识别了意图，但加载的业务上下文与意图不匹配。例如：识别为退款排障，但 get_order 返回 ORDER_NOT_FOUND，系统未正确处理这一状态，仍尝试生成基于空数据的建议。或：用户提问涉及退款单，但系统只调用了 get_order 而未调用 get_refund_case，导致建议缺少关键退款状态信息。

### Regulatory / Compliance Context

本系统为内部工具（商家运营和平台客服使用），不直接面向终端消费者，因此部分消费者保护法规不直接适用。以下约束与本部署上下文直接相关：

**中国《生成式人工智能服务管理暂行办法》（2023，CAC）**
若系统输出内容对外公开或间接影响消费者决策，需满足 AI 生成内容标注要求（2025年9月起强制执行显式和隐式标注）。Phase 3 为内部工具，当前不触发此要求，但 Phase 5 前端上线前需评估是否需要标注。

**中国《电子商务法》第49条——平台退款义务**
平台对退款处理时限有法定要求。AI 系统给出的退款建议若被客服专员直接执行，需符合法定时限。系统的 risk_rules.yaml 配置应包含时限相关规则，确保建议不违反法定退款窗口。

**数据安全与个人信息保护（PIPL，2021）**
系统处理订单数据、用户 ID、退款金额等个人信息。tenant_id 隔离和权限校验（SAFE-08）是满足 PIPL 数据最小化和访问控制要求的关键控制点。执行 trace 不得暴露用户隐私字段（D-05e 已明确）。

**审计日志留存**
电商平台退款操作通常需要保留完整操作记录以备监管查询。SAFE-06 要求的完整审计日志（agent_runs + agent_steps）满足此要求。

## 2. Framework Decision

**Selected Framework:** LangGraph

**Version:** langgraph >=0.4.0, langgraph-checkpoint-postgres >=2.0.0

**Rationale:**
Phase 3 requires a stateful agent workflow with deterministic graph routing, per-node checkpointing for multi-turn memory, full execution trace persistence, and human-in-the-loop readiness (Phase 4). LangGraph is the only framework that provides native Postgres-backed checkpointing at every node, time-travel debugging, and a graph mental model that maps directly to the 8-node architecture defined in CONTEXT.md D-04. The project uses Python + FastAPI, and LangGraph's async-first design integrates cleanly with the existing async stack.

**Alternatives Considered:**

| Framework | Ruled Out Because |
|-----------|------------------|
| CrewAI | No fine-grained per-node checkpointing; coarse error handling; no deterministic graph routing — relies on LLM-driven task delegation |
| LlamaIndex | RAG-first framework — agent orchestration is secondary; no built-in stateful workflow graph or checkpointer |
| LangChain (chains only) | No graph-based state machine; no per-node persistence; would require building custom checkpointing on top |
| OpenAI Agents SDK | Vendor lock-in to OpenAI models; no persistent state management; project uses GLM-5.1 via DashScope |

**Vendor Lock-In Accepted:** Partial — LangGraph depends on LangChain ecosystem (langchain-core, langchain-openai), but the LLM client uses the OpenAI-compatible interface which can point to any provider. The checkpointer is Postgres-standard. Migration cost is moderate (graph structure is portable, node functions are plain Python).

### Entry Point Pattern
```python
"""
Minimal runnable entry point for the MOCA refund agent.
GLM-5.1 via DashScope OpenAI-compatible endpoint.
Deterministic routing: nodes hardcode tool call order, no LLM function calling for routing.
"""
import asyncio
import os
from typing import Optional
from typing_extensions import TypedDict

from langgraph.graph import StateGraph, START, END
from langgraph.checkpoint.postgres.aio import AsyncPostgresSaver
from langchain_openai import ChatOpenAI

llm = ChatOpenAI(
    model="glm-5.1",
    openai_api_key=os.environ["DASHSCOPE_API_KEY"],
    openai_api_base="https://dashscope.aliyuncs.com/compatible-mode/v1",
    temperature=0.0,
    max_tokens=1024,
)

class AgentState(TypedDict):
    thread_id: str
    tenant_id: str
    user_id: str
    last_intent: Optional[str]
    user_query: str
    current_intent: Optional[str]
    final_response: Optional[str]

async def receive_request(state: AgentState) -> dict:
    return {}

async def classify_intent(state: AgentState) -> dict:
    return {"current_intent": "policy_qa"}

async def final_response_node(state: AgentState) -> dict:
    return {"final_response": "处理完成。"}

async def build_graph(db_uri: str):
    async with AsyncPostgresSaver.from_conn_string(db_uri) as checkpointer:
        await checkpointer.setup()

        builder = StateGraph(AgentState)
        builder.add_node("receive_request", receive_request)
        builder.add_node("classify_intent", classify_intent)
        builder.add_node("final_response", final_response_node)

        builder.add_edge(START, "receive_request")
        builder.add_edge("receive_request", "classify_intent")
        builder.add_edge("classify_intent", "final_response")
        builder.add_edge("final_response", END)

        graph = builder.compile(checkpointer=checkpointer)

        config = {"configurable": {"thread_id": "thread-001"}}
        result = await graph.ainvoke(
            {"user_query": "我的退款为什么还没到账？", "thread_id": "thread-001",
             "tenant_id": "t1", "user_id": "u1"},
            config,
        )
        print(result["final_response"])

if __name__ == "__main__":
    asyncio.run(build_graph("postgresql://postgres:postgres@localhost:5432/moca"))
```

### Key Abstractions

| Concept | What It Is | When You Use It |
|---------|-----------|-----------------|
| `StateGraph` | Graph builder; nodes are Python functions, edges define execution order | Define the 8-node refund workflow; compile once at startup |
| `TypedDict` state | Typed dict as single source of truth passed between nodes | Split into `persistent_memory` + `ephemeral_context` fields per D-07 |
| `AsyncPostgresSaver` | Postgres-backed checkpointer; persists full state after every node | Compile the graph with it to get cross-turn memory and time-travel |
| `RetryPolicy` | Per-node retry config attached at `add_node()` time | Attach to LLM-calling nodes for transient failure recovery |
| `add_conditional_edges` | Routes to different next nodes based on a function of state | Phase 4 approval branching; Phase 3 uses only `add_edge` |

### Common Pitfalls

1. **Calling `checkpointer.setup()` every request.** `setup()` runs DDL migrations. Call once at startup, not per-request — causes lock contention on the checkpoints table.
2. **Mixing sync and async node functions.** LangGraph's async runner expects all nodes to be `async def`. A single sync node silently blocks the event loop.
3. **Storing full business objects in persistent state.** Checkpointer serialises entire state to Postgres on every node. Store only reference IDs; reload data each turn (D-07c).
4. **Forgetting `thread_id` in config dict.** Without `{"configurable": {"thread_id": "..."}}`, LangGraph creates a new thread every call — no memory loaded or saved.
5. **Using `llm.with_structured_output()` without testing GLM-5.1 compatibility.** DashScope may not support OpenAI's `response_format: json_object` identically. Test in isolation; fall back to prompt-based JSON + `json.loads()` + Pydantic validation.

## 4. Implementation Guidance

**Model Configuration:**


Use `temperature=0.0` for all classification and recommendation nodes.

**Core Pattern:**

Deterministic routing (D-02): every edge is a fixed `add_edge`. The LLM is called only inside nodes for NLU tasks (intent classification, slot extraction, recommendation generation). No LLM function calling for routing.

```python
from contextlib import asynccontextmanager
from langgraph.graph import StateGraph, START, END
from langgraph.checkpoint.postgres.aio import AsyncPostgresSaver
from langgraph.types import RetryPolicy

from .state import AgentState
from .nodes import (receive_request, classify_intent, extract_slots,
    load_business_context, retrieve_policy_evidence,
    generate_recommendation, assess_risk_and_approval, final_response)

_llm_retry = RetryPolicy(max_attempts=2)  # 1 retry = 2 total attempts per D-10a

def _build(checkpointer: AsyncPostgresSaver):
    builder = StateGraph(AgentState)
    builder.add_node("receive_request", receive_request)
    builder.add_node("classify_intent", classify_intent, retry_policy=_llm_retry)
    builder.add_node("extract_slots", extract_slots, retry_policy=_llm_retry)
    builder.add_node("load_business_context", load_business_context)
    builder.add_node("retrieve_policy_evidence", retrieve_policy_evidence)
    builder.add_node("generate_recommendation", generate_recommendation, retry_policy=_llm_retry)
    builder.add_node("assess_risk_and_approval", assess_risk_and_approval)
    builder.add_node("final_response", final_response, retry_policy=_llm_retry)

    builder.add_edge(START, "receive_request")
    builder.add_edge("receive_request", "classify_intent")
    builder.add_edge("classify_intent", "extract_slots")
    builder.add_edge("extract_slots", "load_business_context")
    builder.add_edge("load_business_context", "retrieve_policy_evidence")
    builder.add_edge("retrieve_policy_evidence", "generate_recommendation")
    builder.add_edge("generate_recommendation", "assess_risk_and_approval")
    builder.add_edge("assess_risk_and_approval", "final_response")
    builder.add_edge("final_response", END)

    return builder.compile(checkpointer=checkpointer)

@asynccontextmanager
async def agent_graph_lifespan(db_uri: str):
    async with AsyncPostgresSaver.from_conn_string(db_uri) as checkpointer:
        await checkpointer.setup()
        graph = _build(checkpointer)
        yield graph
```


**State Management:**

State split into two logical layers within a single `TypedDict` (D-07). Persistent fields survive across turns via checkpointer. Ephemeral fields are reset at the start of each turn in `receive_request`.

The checkpointer serialises the full `AgentState` after every node. Only `persistent_memory` fields carry meaningful cross-turn data; `ephemeral_context` fields are overwritten each turn.

**Context Window Strategy:**

- Evidence budget: cap at 5 chunks (~400 tokens each = ~2000 tokens). Take top-5 by confidence score.
- Business context: summarise to key fields only (~500 tokens).
- Total prompt budget for `generate_recommendation`: system (~300) + business (~500) + evidence (~2000) + query (~200) + output buffer (1024) = ~4024 tokens.
- Do not accumulate `messages` history across turns. Each node builds its own prompt from structured state fields.

## 4b. AI Systems Best Practices

> Cross-cutting patterns for LangGraph + Hybrid RAG + Stateful Agent.

### Structured Outputs with Pydantic

Every LLM call produces a structured output. Define a Pydantic model per node, bind with `.with_structured_output()`, retry once on `ValidationError` with schema error fed back.

```python
from pydantic import BaseModel, Field
from typing import Literal, Optional

class IntentResult(BaseModel):
    intent: Literal["policy_qa", "refund_troubleshooting",
                    "compensation_suggestion", "approval_request", "unknown"]
    confidence: float = Field(ge=0.0, le=1.0)
    reasoning: str

class SlotExtractionResult(BaseModel):
    order_id: Optional[str] = None
    refund_case_id: Optional[str] = None
    ticket_id: Optional[str] = None
    merchant_id: Optional[str] = None
    issue_type: Optional[str] = None

class RecommendationDraft(BaseModel):
    recommended_action: str
    reasoning_summary: str
    evidence_refs: list[str] = Field(min_length=1)
    confidence: float = Field(ge=0.0, le=1.0)
    risk_level: Literal["low", "medium", "high"]
```

Retry pattern inside a node:

```python
async def classify_intent(state: dict) -> dict:
    structured_llm = llm.with_structured_output(IntentResult)
    messages = [
        {"role": "system", "content": CLASSIFY_INTENT_SYSTEM},
        {"role": "user", "content": state["normalized_query"] or state["user_query"]},
    ]
    last_error = None
    for attempt in range(2):
        try:
            result = await structured_llm.ainvoke(messages)
            return {"current_intent": result.intent,
                    "llm_outputs": {"classify_intent": result.model_dump()}}
        except (ValidationError, ValueError) as e:
            last_error = str(e)
            if attempt == 0:
                messages.append({"role": "assistant", "content": "[invalid output]"})
                messages.append({"role": "user", "content": f"Validation failed: {last_error}. Respond with valid JSON."})
    return {"current_intent": "unknown",
            "node_errors": [{"node": "classify_intent", "error": last_error, "retry_count": 2}]}
```

If `with_structured_output` is unreliable with GLM-5.1, fall back to: prompt for JSON → `llm.ainvoke()` → `json.loads()` → `Pydantic.model_validate()`.

### Async-First Design

Every node must be `async def`. Never call `asyncio.run()` inside a node — FastAPI already runs an event loop.

Phase 3 uses `await graph.ainvoke(...)` (no streaming). Phase 5 will switch to `async for chunk in graph.astream(...)`.

`AsyncPostgresSaver` must be used as an async context manager — do not instantiate outside a lifespan context.

### Prompt Engineering Discipline

- System prompts: English, fixed, stored in `src/agent/prompts.py`. No dynamic content in system prompts.
- User messages: dynamically constructed from structured state fields.
- Few-shot: inline 2-3 examples only for `classify_intent` (edge cases). No dynamic few-shot retrieval in Phase 3.
- Always set `max_tokens=1024` explicitly.

### Context Window Management

- RAG evidence: truncate to top-5 chunks by confidence before building prompt. Never truncate mid-chunk.
- If zero chunks returned: return `{"recommended_action": "insufficient_evidence"}` without LLM call.
- Multi-turn: no `messages` accumulation. Each turn builds fresh prompts from structured state.
- Checkpointed state stays small (< 2KB per thread) — only reference IDs, not full objects.

### Cost and Latency Budget

| Node | Input tokens | Output tokens | Notes |
|------|-------------|---------------|-------|
| classify_intent | ~300 | ~100 | System + query + schema |
| extract_slots | ~350 | ~150 | System + query + schema |
| generate_recommendation | ~3000 | ~400 | Largest: evidence + business context |
| final_response | ~800 | ~300 | Recommendation + formatting |
| **Total per turn** | **~4450** | **~950** | ~5400 tokens/turn |

- No LLM response caching in Phase 3 (unique business context per turn).
- Future: route `classify_intent`/`extract_slots` to cheaper model (GLM-4-Flash). Design nodes to accept LLM client as parameter for easy swap.

### Dimensions

All five dimensions map directly to the domain rubric ingredients in Section 1b. Two additional dimensions (tool use correctness, task completion) are added per the Hybrid system type requirement.

| # | Dimension | PASS | FAIL | Measurement | Priority |
|---|-----------|------|------|-------------|----------|
| 1 | **Policy citation traceability** | `evidence_refs` in the response contains at least one valid `doc_id/chunk_id` pair that exists in the retrieved chunks; the final_response text references the specific rule (e.g., "根据 policy_refund_timeout / chunk_003"). Citation validator confirms all cited IDs are present in retrieval results. | Response gives a refund recommendation with no `evidence_refs`, or cites only "根据平台规则" without a traceable doc_id/chunk_id. Citation validator returns any `invalid_citation` flag. | Code (citation validator + `evidence_refs` field presence check) | Critical |
| 2 | **Evidence-insufficient refusal** | When `retrieval_status == "no_results"` or all chunk scores fall below the confidence threshold, `recommended_action` is `"insufficient_evidence"` and the response explicitly lists what information is missing and suggests next steps. No definitive refund verdict is present. | When evidence is absent or below threshold, the response still contains phrases like "通常可以退款", "应该符合补偿条件", or any definitive action recommendation. `recommended_action` is not `"insufficient_evidence"`. | Code (check `recommended_action == "insufficient_evidence"` when retrieval score < threshold; regex scan for forbidden certainty phrases) | Critical |
| 3 | **Intent routing accuracy** | `current_intent` matches the ground-truth label in the golden set for the given query. The correct downstream tools are called: `refund_troubleshooting` triggers `get_order` + `get_refund_case`; `policy_qa` triggers `search_policy` only; `unknown` returns a structured "cannot handle" response. | `current_intent` does not match ground truth. A `refund_troubleshooting` query is classified as `policy_qa` (order data not loaded). A `compensation_suggestion` query is classified as `policy_qa` (risk label skipped). | Code (exact match against golden set labels; assert tool call list matches expected set per intent) | High |
| 4 | **Execution trace completeness** | `trace_summary` in the API response contains: `run_id` (non-null UUID), `nodes_executed` (list of all 8 node names in order), `tools_called` (list matching actual tool invocations), `evidence_count` (≥ 1 for non-fallback responses), `risk_level` (one of low/medium/high), `final_status` ("completed"). `agent_steps` DB rows exist for every node traversed. | `trace_summary` is absent or missing any required field. `nodes_executed` is incomplete (e.g., `assess_risk_and_approval` missing). `agent_steps` row count is less than the number of nodes executed. `tools_called` is empty when tools were invoked. | Code (assert all required `trace_summary` fields present and non-null; assert `agent_steps` row count == `len(nodes_executed)`; assert `tools_called` matches DB `tool_name` records) | High |
| 5 | **Risk level labeling consistency** | For identical scenario inputs (same refund amount bracket, same merchant tier, same issue_type), `risk_level` is the same across 3 independent runs. The assigned level matches the expected level derived from `risk_rules.yaml` for that scenario. | The same scenario produces different `risk_level` values across runs. A high-amount compensation scenario (e.g., > ¥500) is labeled `low`. The label cannot be traced to a rule in `risk_rules.yaml`. | Code (deterministic: `temperature=0.0` + fake LLM in CI; assert `risk_level` matches expected value from `risk_rules.yaml` lookup for each golden set case) | High |
| 6 | **Tool use correctness** | Each tool is called with valid, schema-conforming inputs (`tenant_id`, `user_id`, `role` all present). Tool response `status == "success"` for valid inputs. `ORDER_NOT_FOUND` and `PERMISSION_DENIED` errors are handled gracefully — the node records the error in `node_errors` and the graph continues to a structured fallback response rather than crashing. | A tool is called without `tenant_id` (PIPL violation). A tool call raises an unhandled exception. An `ORDER_NOT_FOUND` error causes the graph to emit a recommendation based on empty data. | Code (assert tool input schema validity; assert `node_errors` is populated on tool failure; assert no recommendation is generated when `business_context` is empty due to tool error) | High |
| 7 | **Task completion** | For a standard happy-path query (valid order_id, matching policy evidence exists), the graph reaches `final_status == "completed"`, `final_response` is non-empty, `evidence_refs` is non-empty, and `risk_level` is set. The full 8-node path is traversed. | Graph terminates early with `final_status == "error"` on a valid input. `final_response` is null or empty. The graph loops (same node visited > 2 times). | Code (assert `final_status == "completed"` on happy-path cases; assert `final_response` non-empty; assert no node appears more than once in `nodes_executed`) | High |

## 6. Guardrails

### Online (Real-Time)

These run synchronously inside the graph on every request. Phase 3 has two critical failure modes that warrant online guardrails; all others are handled by the graph's deterministic structure.

| Guardrail | Trigger | Intervention | Latency Impact | Failure Mode Defended |
|-----------|---------|--------------|----------------|----------------------|
| **Citation validator** | `generate_recommendation` node produces `evidence_refs` | Re-run `citation_validator.validate(evidence_refs, retrieved_chunks)` before `final_response` node executes. If any cited `doc_id/chunk_id` is not in the retrieved set, strip the invalid refs and set `recommended_action = "citation_invalid"`. Block the fabricated citation from reaching the user. | ~5ms (in-process dict lookup) | Policy fabrication (failure mode 1) |
| **Evidence gate** | `retrieve_policy_evidence` node completes | If `retrieval_status == "no_results"` or `max(chunk_scores) < CONFIDENCE_THRESHOLD`, set `recommended_action = "insufficient_evidence"` and skip `generate_recommendation` LLM call entirely. Proceed directly to `final_response` with the fallback template. | 0ms (short-circuit, saves LLM call) | Evidence-insufficient false confidence (failure mode 2) |

Note: Permission bypass (failure mode 5) is defended at the tool layer (D-08c, SAFE-08) — every tool call validates `tenant_id + user_id + role` before executing. This is not a separate guardrail node; it is enforced in the repository layer.

### Offline (Flywheel)

Sampled batch analysis feeding the improvement loop. Run as a scheduled script or manually after each deployment. Phase 3 volume is low (internal tool), so weekly manual review is sufficient.

| Metric | Sampling Strategy | Threshold | Action on Degradation |
|--------|------------------|-----------|----------------------|
| **Citation validity rate** | 100% of runs (logged in `agent_steps.evidence_refs`) | < 95% valid citations across last 50 runs | Investigate KB coverage gaps; check if new policy documents need ingestion |
| **Evidence fallback rate** | 100% of runs (logged in `agent_runs.final_status`) | > 30% of runs hit `insufficient_evidence` | KB may have coverage gaps for common query types; review query patterns and add documents |
| **Intent classification accuracy** | Weekly sample of 20 runs, reviewed by Product Owner | < 85% match against spot-check labels | Review `classify_intent` prompt; add few-shot examples for misclassified patterns |
| **Risk level consistency** | All runs where `risk_level` is set; compare against `risk_rules.yaml` expected values | Any mismatch on deterministic rule-based cases | Investigate `assess_risk_and_approval` node; check if `risk_rules.yaml` was updated without prompt update |
| **End-to-end latency** | 100% of runs (logged in `agent_runs.total_latency_ms`) | p95 > 8000ms | Profile slow nodes via `agent_steps.latency_ms`; check DashScope API latency |

## 7. Production Monitoring

**Tracing Tool:** LangSmith (self-service SaaS; no self-hosting required for v1 internal tool)

LangSmith auto-instruments LangGraph when `LANGCHAIN_TRACING_V2=true` is set. Every `graph.ainvoke()` call produces a full trace with per-node inputs, outputs, latency, and token counts. Traces are queryable by `run_id`, `thread_id`, and `tenant_id` via the LangSmith UI and API.

For Phase 3, LangSmith is the primary observability surface. OTel + Prometheus + Grafana are deferred to v2 (OBS-01).

**Key Metrics to Track:**

| Metric | Source | Why It Matters |
|--------|--------|----------------|
| `citation_valid_rate` | `agent_steps.evidence_refs` + citation validator result | Primary quality signal; drop indicates policy fabrication risk |
| `evidence_fallback_rate` | `agent_runs` where `final_status == "insufficient_evidence"` | High rate = KB coverage gap or retrieval regression |
| `intent_accuracy` | Spot-check `agent_runs.intent` against query patterns | Misrouting degrades all downstream node quality |
| `p95_total_latency_ms` | `agent_runs.total_latency_ms` | User experience; budget is ~6000ms for 8-node happy path |
| `llm_error_rate` | `agent_steps` where `status == "error"` and `node_name` in LLM nodes | DashScope API reliability; triggers retry budget review |

**Alert Thresholds:**

| Condition | Threshold | Action |
|-----------|-----------|--------|
| `citation_valid_rate` drops | < 90% over any 24h window | Immediate: check citation validator logs; verify KB chunk IDs are stable after any re-ingestion |
| `evidence_fallback_rate` spikes | > 40% over any 24h window | Same-day: review recent queries; check if retrieval confidence threshold needs tuning |
| `p95_total_latency_ms` exceeds budget | > 10000ms | Investigate: check `agent_steps.latency_ms` per node; check DashScope API status |
| `llm_error_rate` elevated | > 5% of LLM node executions in 1h | Check DashScope rate limits and API health; consider temporary fallback to structured error response |
| Any `PERMISSION_DENIED` tool error | Any occurrence | Immediate review: potential PIPL / tenant isolation violation; check `user_id + tenant_id` in the failing request |

**Smart Sampling Strategy:**

Phase 3 is an internal tool with low volume. All runs are logged to `agent_runs` + `agent_steps`. Human review is triggered by signals, not random sampling:

- **Priority 1 — always review:** Any run where `citation_validator` stripped a citation (`citation_invalid` flag in `agent_steps`). These are potential policy fabrication events.
- **Priority 2 — always review:** Any run where `final_status == "error"` on a query that contained a valid `order_id` (should have succeeded).
- **Priority 3 — weekly sample:** 5 randomly selected completed runs per week, reviewed by Support Lead against the golden set rubric. Used to catch quality drift not captured by code metrics.
- **Priority 4 — on demand:** Any run flagged by a user (support agent or merchant operator) as producing a wrong recommendation. Retrieve full trace by `run_id` from LangSmith.

Signal-metric divergence watch: if user-reported errors increase while `citation_valid_rate` stays high, investigate whether the citation validator is passing technically-valid but contextually-wrong citations (a gap in the code-based check that requires LLM judge calibration in Phase 6).
