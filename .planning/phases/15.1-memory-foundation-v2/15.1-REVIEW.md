## Summary

Reviewed the listed Phase 15.1 conversation memory foundation, prompt context assembly, tool result storage, migration/model additions, and tests. The implementation stays mostly inside the intended Phase 15.1 boundary: I did not find new embeddings, tombstone tables, vector search, user-manageable memory, outbox, external execution, reconciliation, or compensation storage in the reviewed changes. `case_id`/`case_current` appear to be forward-compatibility reservations documented in the phase context, not active Phase 16 retrieval.

The main blocker is tenant-local but cross-user conversation leakage: graph checkpoints are user-scoped, while conversation storage and prompt-context reads are only tenant/thread-scoped. There are also correctness and prompt-safety issues around swallowed persistence failures, rolling summary source selection, and concurrent message indexing.

## Critical Issues

### CR-01: Conversation Context Is Not User-Scoped

**File:** `src/conversation/repository.py:25`
**Issue:** `ConversationRepository.get_thread()` and all recent-message/tool-summary/summary reads filter by `tenant_id + thread_id` only. `get_or_create_thread()` receives `user_id`, but returns an existing thread without verifying it belongs to that user. The API graph checkpoint is scoped as `tenant:user:thread` in `src/api/routers/agent.py:60`, but conversation writes use raw `body.thread_id` at `src/api/routers/agent.py:90`, and prompt context reads use only tenant/thread in `src/conversation/service.py:236-249`. If two users in the same tenant submit the same `thread_id`, the second user can inherit the first user's recent messages, tool summaries, and rolling summary in prompt context.

**Fix:**
```python
# Make conversation thread identity match the graph/user boundary.
# Migration/model: replace the active unique index with tenant + user + thread.
Index(
    "uq_conversation_threads_active_tenant_user_thread",
    ConversationThread.tenant_id,
    ConversationThread.user_id,
    ConversationThread.thread_id,
    unique=True,
    postgresql_where=ConversationThread.deleted_at.is_(None),
)

# Repository reads should resolve the scoped thread first, then read by conversation_thread_id.
async def get_thread(self, *, tenant_id: uuid.UUID, user_id: uuid.UUID, thread_id: str) -> ConversationThread | None:
    ...
        ConversationThread.tenant_id == tenant_id,
        ConversationThread.user_id == user_id,
        ConversationThread.thread_id == thread_id,
    ...

# ConversationService.load_prompt_context should accept user_id and pass it through;
# list_recent_messages/list_recent_tool_prompt_summaries/list_thread_summaries should
# filter by the resolved conversation_thread_id, not bare tenant_id + thread_id.
```

## Warnings

### WR-01: Successful Chat Can Silently Lose Final Conversation Memory

**File:** `src/api/routers/agent.py:195`
**Issue:** The success path catches every exception from final persistence, rolls back, and still returns `success=True`. A failure in `write_agent_run`, `write_agent_steps`, assistant message append, thread summary persistence, or `commit()` leaves the initial user message written before graph execution but drops the assistant message and rolling summary. That creates broken conversation history and future prompt context while the client sees a successful response.

**Fix:**
```python
try:
    ...
    await session.commit()
except Exception as exc:
    await session.rollback()
    logger.exception("Failed to persist completed chat turn", exc_info=exc)
    return ApiResponse(
        success=False,
        data=ChatResponse(response=final_response_text, trace_summary=TraceSummary(**trace_summary)).model_dump(),
        error=ErrorDetail(code=INTERNAL_ERROR, message="回复已生成，但会话记录保存失败，请重试。"),
        trace_id=request.state.trace_id,
    )
```

### WR-02: Thread Summary Uses Stored Tool `summary` Before Prompt-Safe `prompt_summary`

**File:** `src/memory/thread_summary.py:151`
**Issue:** `_safe_tool_summary()` prefers `ToolResultRecord.summary` over `prompt_summary`. `prompt_summary` is the field explicitly projected for prompt reuse; `summary` is stored alongside normalized tool result data and is not guarded against PII or arbitrary business payload text unless it happens to contain one of a few forbidden key names. The resulting `summary_text` is later loaded directly as `thread_rolling_summary`, so unsafe tool summary text can become future prompt context.

**Fix:**
```python
def _safe_tool_summary(result: ToolResultRecord) -> str:
    candidates = [result.prompt_summary, result.summary]
    for candidate in candidates:
        sanitized = _sanitize_text(candidate or "")
        if sanitized:
            return sanitized
    return ""
```

Prefer dropping the `summary` fallback entirely unless tool adapters have a documented contract that `summary` is prompt-safe.

### WR-03: Concurrent Appends Can Allocate Duplicate Message Indexes

**File:** `src/conversation/repository.py:64`
**Issue:** `append_message()` computes `message_index` with `max(message_index) + 1` in `_next_message_index()` without locking the conversation thread or retrying on the unique constraint. Two concurrent requests for the same conversation can both choose the same next index, causing one request to fail with an integrity error. This is a correctness bug for multi-tab/client retry scenarios and can also trigger the silent persistence-loss path above.

**Fix:**
```python
# Lock the scoped conversation thread before reading max(message_index),
# and compute by conversation_thread_id inside the same transaction.
thread = await self.get_or_create_thread(...)
await self.session.execute(
    select(ConversationThread.id)
    .where(ConversationThread.id == thread.id)
    .with_for_update()
)
next_index = await self._next_message_index(conversation_thread_id=thread.id)
```

Alternatively, keep the unique constraint and add an explicit retry loop around duplicate-index insert failures.
