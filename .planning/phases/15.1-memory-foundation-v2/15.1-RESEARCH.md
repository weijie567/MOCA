# Phase 15.1: Memory Foundation V2 - Research

**Researched:** 2026-06-17
**Status:** Ready for planning
**Method:** Local repository evidence after `gsd-phase-researcher` spawn stalled and was closed

## Research Objective

Answer: what do we need to know to plan Phase 15.1 well?

Phase 15.1 must establish the pre-Phase 16 memory foundation:

- authoritative conversation log for user/assistant/tool conversation facts
- tool call/result persistence with raw reference, normalized result, summary, and prompt summary separation
- prompt-safe `WorkingStateV1`
- thread rolling summaries with source ranges
- centralized `ContextAssembler` and token budgeting
- trace/audit/conversation ID alignment

It must not implement Phase 16 long-term memory, memory tombstones, user-manageable memory, case vector search, or case precedent retrieval.

## Confirmed Current-Code Findings

### Run and trace persistence

Confirmed in `src/db/models.py`:

- `AgentRun` stores `thread_id`, `tenant_id`, `user_id`, `input_query`, `final_status`, `final_response`, timing, token, cost, and error summary.
- `AgentStep` stores node-level `input_summary`, `output_summary`, optional `tool_name`, `tool_input_summary`, `tool_output_summary`, metrics, evidence refs, and error message.
- `AgentTraceEvent` stores replay event rows with `run_id`, `sequence`, `operation_id`, `parent_operation_id`, `attempt`, `event_type`, actor/resource refs, redaction policy, and `redacted_payload`.
- Existing tables do not provide a complete ordered conversation message log or first-class persisted tool call/result records separate from replay summaries.

Planning implication: Phase 15.1 should add conversation/tool tables beside replay/trace, not overload `agent_trace_events` or `agent_steps` with raw or full conversation payloads.

### Session memory and short-term continuity

Confirmed in `src/db/models.py`, `src/memory/repository.py`, and `src/memory/service.py`:

- `session_memories` is already the PostgreSQL-authoritative same-thread slot continuity table.
- It stores active slots, session summary, unresolved questions, last intent, business context refs, last run, version, expiry, and soft delete fields.
- Existing Phase 12 tests cover schema, service, repository, concurrency, isolation, and evidence boundary behavior.

Planning implication: do not replace `session_memories`; add thread rolling summaries in a separate `summaries` table and keep summary semantics distinct from slot continuity.

### AgentState and current working state

Confirmed in `src/agent/state.py`:

- `AgentState` is a large `TypedDict` mixing durable identity/checkpoint fields, per-turn ephemeral fields, business context, policy evidence, recommendations, approval/action state, tool results, LLM outputs, trace steps, and errors.
- `receive_request` resets per-turn fields and preserves trusted identity state.
- `AgentState` is runtime/checkpoint state, not a prompt-safe projection.

Planning implication: define `WorkingStateV1` as a projection from `AgentState` with allowlisted refs and summaries. It must not include raw `business_context`, raw `tool_results`, `llm_outputs`, approval/action authority bodies, trace/debug blobs, or full policy text.

### Tool contract and tool result risk

Confirmed in `src/tools/contracts.py`, `src/tools/manager.py`, `src/business/adapters.py`, and `src/agent/nodes/investigate.py`:

- `ToolCallContext` already includes tenant/user/thread/run/trace/request/tool call identity.
- `ToolResultV2` has `data`, `summary`, source, freshness, evidence refs, business fact refs, error, retry, latency, and audit ref.
- `investigate` currently appends `{"tool_name": tool_name, **result.model_dump(mode="json")}` into `state["tool_results"]`.
- `ToolResultV2.data` is normalized adapter output, but it can still be large or prompt-unsafe if directly interpolated or persisted without layer separation.

Planning implication: introduce a storage boundary for `tool_calls` and `tool_results`, then project prompt-safe summaries/refs into `AgentState` and `ContextAssembler`.

### Prompt construction and implicit stringification

Confirmed in current prompt code:

- `src/agent/nodes/generate_recommendation.py` uses local helpers such as `_summarize_business_context` and `_summarize_evidence`; `_summarize_business_context` currently `json.dumps` the whole dict, so it can still leak large or prompt-unsafe nested `business_context` values into the prompt.
- `src/agent/nodes/assess_risk_and_approval.py` currently constructs a user message containing `Risk rules: {rules}`, `Recommendation: {draft}`, and `Business context: {context}` where `draft` and `context` are dicts.
- `src/agent/nodes/extract_slots.py` interpolates `candidate_slots` into prompt text.

Planning implication: ContextAssembler and projector helpers must own structured-to-prompt conversion. Tests must prove a large/nested tool result or business context dict is not implicitly stringified or JSON-dumped into assembled prompts.

### Replay, redaction, and audit boundaries

Confirmed in `src/replay/service.py`, `src/replay/validators.py`, `src/replay/schemas.py`, `src/replay/pairing.py`, and replay tests:

- `ReplayService` owns append/projection and shared per-run sequence allocation for `agent_trace_events`.
- `guard_redacted_payload` forbids keys such as `raw`, `raw_prompt`, `raw_args`, `raw_payload`, and `raw_tool_output`.
- Replay is a redacted audit/event timeline, not a raw conversation/tool payload store.
- `src/repositories/audit_repo.py` exists but is lightly integrated.

Planning implication: conversation/tool persistence must reference replay/audit IDs where useful without weakening redaction rules or duplicating replay as raw storage.

### Schema and migration conventions

Confirmed in `src/db/migrations/versions/007_session_memories.py` and `010_replay_event_v3.py`:

- Alembic revision files are used under `src/db/migrations/versions`.
- SQLAlchemy models live in `src/db/models.py`.
- Existing migrations create tables/columns, indexes, check constraints, and PostgreSQL JSONB fields.
- Tests use `pytest`, async SQLAlchemy sessions, and module-specific test directories such as `tests/memory` and `tests/replay`.

Planning implication: Phase 15.1 should add Alembic revision `011_memory_foundation_v2.py` (or current next revision if changed), SQLAlchemy models, repositories/services, and migration contract tests. The plan must include a blocking migration/schema verification task.

### Requirements mapping issue

Confirmed in `.planning/ROADMAP.md`:

- Phase 15.1 maps to `MEMORY-FOUNDATION-01`, `MEMORY-FOUNDATION-02`, and `MEMORY-FOUNDATION-03`.

Confirmed in `.planning/REQUIREMENTS.md`:

## Architecture Boundaries

### Canonical owners

- Conversation log schema/repository/service: `src/conversation/` plus `src/db/models.py` and Alembic.
- Tool result persistence/projection: `src/tools/` contracts/manager integration plus `src/conversation/` storage or `src/tool_results/` if split by local convention.
- WorkingStateV1 projection: `src/agent/working_state.py` or `src/agent/context/working_state.py`.
- ContextAssembler and token budgeting: `src/agent/context/assembler.py`, `src/agent/context/budget.py`, and prompt projector helpers.
- Thread rolling summaries: `src/memory/thread_summary.py` or `src/conversation/summaries.py`, backed by the new `summaries` table.
- Trace/audit/conversation ID alignment: integrations in `src/agent/trace.py`, `src/replay/service.py`, `src/repositories/audit_repo.py`, and graph/API wiring.

### Non-overlap with adjacent phases

- Phase 12 owns PostgreSQL session memory, CAS merge, slot inheritance, fallback behavior, and evidence boundary. Phase 15.1 must not reimplement session memory.
- Phase 15 owns ReplayEventV3, lifecycle finalizer, redaction, retention, and replay read-switch. Phase 15.1 must not weaken replay redaction or store raw replay payloads.
- Phase 16 owns long-term/profile/case memory, memory identity, review workflow, tombstones, and retrieval predicates. Phase 15.1 may reserve nullable `case_id` fields only.
- Phase 17 owns external action execution, outbox, reconciliation, and compensation. Phase 15.1 may reference action draft/approval IDs but must not add external execution storage.

### Package quarantine and forbidden imports

- New prompt code should import context/projector APIs instead of reading raw `AgentState` dicts directly.
- New memory summary code must not import policy KB internals as an authority source.
- New conversation/tool tables must not become source of truth for orders/refunds/tickets, approval state, action state, or policy versions.
- `search_case_memory` remains transitional until Phase 16; Phase 15.1 should not build case retrieval on it.

## Proposed Data Model

### conversation_threads

Minimum fields:

- `id` UUID primary key
- `tenant_id` UUID not null
- `thread_id` string not null
- `user_id` UUID not null
- `case_id` string/UUID nullable reserved for Phase 16
- `status` string default `active`
- `created_at`, `updated_at`, `archived_at`, `retention_until`, `deleted_at`

Indexes/constraints:

- unique active scope on `(tenant_id, thread_id)` where `deleted_at IS NULL`
- lookup index on `(tenant_id, user_id, thread_id)`
- optional `case_id` index if field exists

### conversation_messages

Minimum fields:

- `id` UUID primary key
- `conversation_thread_id` FK
- `tenant_id`, `thread_id`, `run_id`, `trace_id`
- `message_index` integer or monotonic per-thread sequence
- `role` enum/string: `user`, `assistant`, `tool`
- `content` text for user-visible/safe message body or safe tool summary only
- `content_hash` string
- `prompt_template_version`, `prompt_block_hashes_json`, `context_snapshot_ref`, `redacted_prompt_snapshot_ref` nullable
- `metadata_json`
- retention fields

Rules:

- store user-visible assistant final messages, not private reasoning
- do not store full raw prompts by default
- store tool messages only as safe summaries/refs

### tool_calls

Minimum fields:

- `id` UUID primary key or existing tool call ID as unique external ID
- `conversation_thread_id`, `message_id` nullable, `conversation_message_id` nullable, `tenant_id`, `thread_id`, `run_id`, `trace_id`
- `tool_call_id`, `tool_name`, `caller_node`, `operation_id`, `attempt`
- `argument_summary_json`, `argument_hash`, `redaction_policy_version`
- `status`, `started_at`, `completed_at`, `latency_ms`, `error_summary`

Rules:

- argument summary only; no raw args with PII/secrets
- align `operation_id` with replay event pairing where available

### tool_results

Minimum fields:

- `id` UUID primary key
- `tool_call_id` FK
- `tenant_id`, `thread_id`, `run_id`, `trace_id`
- `operation_id`, `conversation_message_id`, `tool_result_id`
- `status`, `source_system`, `data_freshness_at`, `latency_ms`
- `raw_result_ref`, `raw_result_hash` nullable
- `normalized_result_json` bounded JSONB
- `summary` text
- `prompt_summary` text nullable
- `business_fact_refs_json`, `policy_evidence_refs_json`
- `audit_ref`, `replay_event_id` nullable
- retention fields

Rules:

- raw result is reference/hash only, not direct prompt input
- normalized JSON is auditable but still not automatically prompt-safe
- prompt summary is generated by ContextAssembler/projection layer

### summaries

Minimum fields:

- `id` UUID primary key
- `tenant_id`, `thread_id`, `conversation_thread_id`
- `case_id` nullable reserved for Phase 16
- `summary_type`: at minimum `thread_rolling`; optionally reserve `case_current`
- `source_start_message_id`, `source_end_message_id`
- `source_message_ids_json`, `source_tool_result_ids_json`
- `summary_text`, `summary_json` nullable
- `summary_model`, `summary_prompt_version`, `summary_hash`
- retention fields

Rules:

- derived from conversation messages and tool summaries
- source ranges are mandatory for thread rolling summary
- no raw policy text, raw tool payload, or approval/action authority object bodies

## Planning Risks and Countermeasures

| Risk | Impact | Countermeasure |
| --- | --- | --- |
| Conversation log duplicates business source of truth | Refund/order/ticket facts become stale or conflicting | Store conversation facts and refs only; business tables remain authority |
| Raw prompts or private reasoning are persisted | Privacy/compliance leak | Store template version, hashes, context refs, optional redacted snapshot only |
| Tool result `data` leaks into prompt | Raw/large payload exposure and prompt bloat | Store raw ref/hash, normalized JSON, summary, prompt summary separately |
| Dict/list implicit stringification remains in prompt nodes | ContextAssembler can be bypassed | Add projector tests and update prompt nodes to consume assembled/projected blocks |
| Thread summaries become Phase 16 case memory | Scope creep and wrong authority | Keep `summary_type='thread_rolling'`; `case_id` is nullable reserved only |
| Replay redaction is weakened | Phase 15 regression | Conversation/tool tables reference replay IDs without relaxing `guard_redacted_payload` |
| Schema migration is planned but not verified | False-positive execution | Include a blocking Alembic/model/migration test task before downstream service wiring |

## Suggested Plan Split

1. Conversation schema and service foundation.
2. Tool call/result layering and investigate integration.
3. WorkingStateV1 prompt-safe projection.
4. Thread rolling summaries.

This order follows the phase context: conversation log first, then tool result refs/summaries, then prompt-safe working state, summaries, assembler/budget, and final ID alignment.

## Resolved Execution Decisions

### RESOLVED-15.1-R1: Conversation thread identity

Use a UUID primary key on `conversation_threads.id` as the internal canonical row identity. Preserve the existing external `thread_id` and enforce active uniqueness with `(tenant_id, thread_id)` where `deleted_at IS NULL`. This lets current API/checkpoint contracts keep using `thread_id` while new conversation/message/tool rows use stable FK relationships.

### RESOLVED-15.1-R2: Raw tool payload references

Do not introduce blob/object storage in Phase 15.1. Store nullable `raw_result_ref` and `raw_result_hash` only. The ref can point to upstream retention, future object storage, or remain null; prompt and working-state paths must use `summary`, `prompt_summary`, refs, and normalized bounded JSON only.

### RESOLVED-15.1-R3: Prompt snapshots

Do not store raw prompts by default in Phase 15.1. Store `prompt_template_version`, `prompt_block_hashes_json`, `context_snapshot_ref`, and nullable `redacted_prompt_snapshot_ref`. If a redacted prompt snapshot is needed later, it must be explicitly generated through the redaction/projector boundary and must not include private reasoning or raw tool payloads.
