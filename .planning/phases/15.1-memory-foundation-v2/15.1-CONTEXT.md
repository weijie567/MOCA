# Phase 15.1: Memory Foundation V2 - Context

**Gathered:** 2026-06-17
**Status:** Ready for planning
**Source:** User architecture direction after the 2026-06-17 implementation map review

<domain>
## Phase Boundary

Phase 15.1 exists to solve the memory foundation gaps before Phase 16 begins. It should deliver a strong V2 foundation for:

- Conversation log: record what happened.
- Working memory: make the current run's structured work state prompt-safe and explicit.
- Short-term memory: summarize the current thread/case context for prompt continuity.
- ContextAssembler: centralize prompt assembly and token budgeting.
- Tool result storage: split raw result, normalized result, summary, and prompt summary.
- Trace/audit/conversation ID alignment: make run, step, message, tool call, and tool result references traceable.

This phase must not implement Phase 16's long-term memory or case memory retrieval.

</domain>

<decisions>
## Locked Scope Decisions

### D-15.1-01: Conversation log is required and P0

The project currently stores `AgentRun.input_query` and `AgentRun.final_response`, while intermediate steps are mostly redacted summaries in `AgentStep` and `AgentTraceEvent`. Tool call/result records are also summaries rather than complete structured records. Therefore, the project cannot fully reconstruct a run or answer what exact user/assistant/tool events happened.

Phase 15.1 must add a conversation log as the authoritative source for conversation facts.

Conversation log answers:

- What did the user say?
- What did the assistant answer?
- Which run did a turn belong to?
- Which tools were called?
- What argument summary was used?
- What result summary was returned?
- Where does any large raw result live?
- Which messages produced a summary?

Conversation log does not answer:

- The authoritative order/refund/ticket state.
- Whether a refund or action truly completed.
- Which policy version is current.
- Whether approval is complete.

Those remain owned by business tables, policy KB, and approval/action tables.

### D-15.1-02: This phase is V2 Foundation, not V2 Long-term Memory

This phase should implement:

- conversation log v2
- working memory v2
- short-term memory v2
- ContextAssembler v2
- tool result storage v2
- token budget v2
- trace/audit ID alignment v2

This phase must not implement:

- long-term memory write gate
- memory tombstone
- user-manageable memory
- case memory vector search
- case precedent retrieval
- generic semantic / episodic / procedural memory

Reason: the project is a business Agent. Business facts, policy conclusions, approval state, and action state must not be moved into generic memory.

### D-15.1-03: Add conversation storage tables

Planning should consider the following minimum table set:

- `conversation_threads`
- `conversation_messages`
- `tool_calls`
- `tool_results`
- `summaries`

`conversation_threads.case_id` and `summaries.case_id` may be nullable forward-compatibility fields for Phase 16, but they must not imply case memory retrieval in this phase.

### D-15.1-04: Do not store raw prompt by default

Default persistence should not store full raw prompts. It may store:

- prompt template version
- prompt block hashes
- context snapshot reference
- redacted prompt snapshot, if needed

Private reasoning must not be stored. Intermediate assistant reasoning is out of scope; only user-visible assistant messages and safe audit summaries should be persisted.

### D-15.1-05: Tool result storage must use four layers

Tool result handling must distinguish:

- raw result: object/file reference plus hash where needed
- normalized result: auditable structured JSON
- summary: persisted human/model-safe summary for working memory and short-term summary
- prompt summary: ContextAssembler-generated trimmed form

Raw upstream API payloads must not be pushed directly into AgentState or prompt.

### D-15.1-06: Working memory remains AgentState + projection + checkpoint

Do not create a `working_memory` table in this phase.

Working memory should be represented as:

- current `AgentState`
- `WorkingStateV1` prompt-safe projection
- LangGraph/Postgres checkpoint for run recovery

WorkingStateV1 should keep refs and summaries, not raw payloads or authority objects.

### D-15.1-07: Keep existing session memory but add thread rolling summaries

Do not replace `session_memories`.

Use two short-term layers:

- existing `session_memories`: slot continuity, last intent, unresolved questions, light session summary
- new `summaries` rows: thread rolling summary with source message ranges

Case-level summary may be represented as `summary_type='case_current'` later, but formal case memory belongs to Phase 16.

### D-15.1-08: ContextAssembler is mandatory

Adding tables without ContextAssembler is insufficient. Phase 15.1 should add a centralized prompt assembly boundary that can combine:

- system prompt
- business state projection
- WorkingStateV1
- thread rolling summary
- recent conversation messages
- verified policy snippets
- tool result summaries
- current user message

It must enforce token budgeting and must not include raw tool result, raw upstream payload, large policy full text, or approval/action authority object bodies.

### D-15.1-08A: Prompt inputs must not rely on implicit stringification

Current nodes can turn structured values such as `business_context`, `tool_results`, or nested dict/list objects into prompt text by interpolating them directly. Phase 15.1 must treat that as a planning risk.

ContextAssembler and WorkingStateV1 projection must own structured-to-prompt conversion. Prompt assembly must not rely on:

- `str(tool_result)`
- `str(business_context)`
- f-string interpolation of unprojected dict/list objects
- direct inclusion of `ToolResultV2.data`
- direct inclusion of approval/action authority object bodies

Every prompt-facing block must be produced through an explicit projector or summarizer with field allowlists, size limits, and redaction rules. Tests should include at least one large/nested tool result proving that raw or unprojected data does not appear in the assembled prompt.

### D-15.1-09: Development order

Preferred planning order:

1. Conversation log.
2. Tool call / tool result layering.
3. WorkingStateV1 projection.
4. Thread rolling summary.
5. ContextAssembler.
6. Token budget.
7. Trace/audit/conversation ID alignment.

Reason: conversation log is the factual source needed by summary source ranges, tool result refs, ContextAssembler recent messages, tests, replay alignment, and evaluations.

### D-15.1-10: Case memory is only reserved, not implemented

This phase may reserve:

- `conversation_threads.case_id`
- `summaries.case_id`
- indirect thread/run/message/tool references usable by future case memory

It must not add:

- `case_memory` table
- case embeddings
- case precedent retrieval
- case memory write gate
- case similarity search
- reviewed case outcome learning

</decisions>

<specifics>
## Specific Implementation Ideas

### Conversation log tables

Proposed minimum:

- `conversation_threads`
- `conversation_messages`
- `tool_calls`
- `tool_results`
- `summaries`

`conversation_messages` should store user messages, assistant final responses, and safe tool message summaries/refs. System prompt full text should not be stored by default; store version/hash/snapshot refs as needed.

### WorkingStateV1 shape

Planning should define a prompt-safe projection with fields similar to:

```json
{
  "thread_id": "...",
  "run_id": "...",
  "turn_id": "...",
  "current_goal": "resolve_refund_or_policy_question",
  "current_intent": "refund_troubleshooting",
  "active_slots": {
    "order_id": "...",
    "refund_case_id": null,
    "ticket_id": null
  },
  "open_questions": [],
  "constraints": [
    "tool facts override session memory",
    "policy evidence is required before recommendation",
    "high risk action requires approval"
  ],
  "business_context_refs": [],
  "retrieved_evidence_refs": [],
  "recent_tool_results": [
    {
      "tool_call_id": "...",
      "tool_name": "get_order",
      "status": "success",
      "summary": "...",
      "business_fact_refs": [],
      "raw_result_ref": "..."
    }
  ],
  "pending_confirmation": null,
  "draft_artifact": null
}
```

The exact fields should be adjusted to current `AgentState`, `ToolResultV2`, approval/action contracts, and prompt needs.

### Short-term memory structure

Thread rolling summary should be derived from `conversation_messages` and important `tool_results`, with source message range:

```python
old_summary + new_messages + important_tool_results -> new_summary
```

Summary rules:

- Do not invent facts.
- Preserve confirmed business ids.
- Preserve key decisions.
- Preserve open questions.
- Preserve unresolved constraints.
- Do not store raw policy text.
- Do not store raw tool payload.

### Prompt assembly

ContextAssembler should assemble:

```python
system_prompt
+ business_state_projection
+ working_state
+ thread_rolling_summary
+ recent_messages
+ verified_policy_snippets
+ tool_result_summaries
+ current_user_message
```

Protected blocks:

- system prompt
- current user message
- safety constraints
- necessary business ids
- necessary policy refs

Drop/truncate first:

- old recent messages
- verbose tool summaries
- extra policy snippets
- low-value summary details

Prompt assembly tests should also assert that structured tool/business objects are never included through implicit Python stringification. The expected prompt should contain only approved summaries, refs, ids, and bounded snippets.

</specifics>
