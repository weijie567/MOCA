# 08-02 PLAN: PolicyKnowledgeService Facade + LegacyRagKnowledgeAdapter

<objective>
Implement the `PolicyKnowledgeService` facade (`src/knowledge/service.py`) and the `LegacyRagKnowledgeAdapter` (`src/knowledge/adapters.py`) that wraps the existing `Retriever` / `PolicyChunkRepository` / `EmbeddingService` and maps `PolicyChunk` rows into canonical `EvidenceRefV1` (from 08-01).

The facade exposes ONLY the evidence contract: `search(request: KnowledgeSearchRequest, context: KnowledgeContext) -> KnowledgeSearchResult`. It preserves the existing strong/partial/no_evidence outcomes, propagates explicit `effective_at` (no adapter wall-clock), enforces `filters.merchant_id` authorization against `context.merchant_scope` (reject/drop unauthorized — NOT applied as a DB filter, since policy tables have no merchant column; see B4 below), and implements deterministic tenant-scoped retrieval (tenant-over-global is DEFERRED, see traceability).

This plan does NOT switch the node (08-04), does NOT implement the citation membership validator body (08-03 provides `validate_membership`; the facade leaves `citation_validation` at its default until the node populates claims), and does NOT modify `src/rag/*`, `src/agent/*`, `src/db/*`.

Critical adapter rule (RESEARCH GAP-2): `text_hash` MUST be computed over the FULL `chunk.content`, not the retriever's truncated `text[:300]`. The adapter therefore maps from the chunk object / retrieval result that carries full content, not from the truncating `search_policy` tool payload.
</objective>

## Spec consistency findings
- Tenant-over-global "tenant wins over global" rule (§8.3) is NOT a Phase 8 blocking exit. `PolicyDocument.tenant_id` is NOT NULL and there is no global-policy scope in the MVP schema, so Phase 8 implements deterministic tenant-scoped retrieval only; tenant-over-global is DEFERRED_WITH_OWNER (owner: later policy-scope phase; dependency: schema+query migration adding global scope; acceptance gate: schema-and-query tenant-over-global tests). Surfaced in `service.py` docstring; reconciled into docs at 08-05.
- `retrieval_config_version` / `rerank_config_version` literals did not exist in code (RESEARCH GAP-3). This plan introduces `src/knowledge/config.py` with `RETRIEVAL_CONFIG_VERSION = "retrieval.v3"` and `RERANK_CONFIG_VERSION = "rerank.v2"` as the single source, referenced by request defaults and every EvidenceRefV1.
- B4 finding (Codex review): policy tables (`PolicyDocument`, `PolicyChunk`) have NO merchant column and `PolicyChunkRepository.search_similar` accepts no `merchant_id` — so `filters.merchant_id` CANNOT be applied as a retrieval filter without out-of-scope schema/query work. Phase 8 therefore treats `merchant_id` as an AUTHORIZATION check only: validate it against `context.merchant_scope` and reject/drop if unauthorized; it is NOT pushed into the DB query. Policy retrieval stays tenant-scoped. Recorded here and in `08-EVAL-GATE.md` (08-05). Pushing merchant_id into the policy query is DEFERRED to the same later policy-scope phase that owns tenant-over-global.
- Effective-time + LIMIT ordering (Codex review): `search_similar` applies `ORDER BY similarity LIMIT top_k` with no effective-date predicate, so post-LIMIT effective filtering could drop all in-effect chunks and falsely yield `no_evidence`. The adapter must apply the `effective_date <= effective_at` filter BEFORE the `top_k` truncation (filter candidates, then rank/truncate), not after. See task 2.

<threat_model>
ASVS L1; block on high.

| Threat | Impact | Mitigation in this plan | Blocking? |
| --- | --- | --- | --- |
| Untrusted `filters.merchant_id` | Cross-merchant policy leakage / scope bypass | Facade validates `filters.merchant_id ∈ context.merchant_scope`; unauthorized id is rejected/dropped, never trusted. NOT applied as a DB filter (no merchant column) — authorization gate only | high → yes |
| Cross-tenant retrieval | Tenant data leakage | Retrieval keyed strictly on `context.tenant_id`; adapter passes trusted tenant, never request-supplied tenant alone | high → yes |
| `effective_at` taken from adapter wall-clock | Non-deterministic/incorrect time-travel evidence; replay divergence | `effective_at` is required on `KnowledgeContext`; adapter uses it for the cutoff and never calls `datetime.now()` for the effective filter | high → yes |
| Effective filter applied AFTER `top_k` LIMIT | Future-dated chunks crowd out valid ones → false `no_evidence` | Adapter filters `effective_date <= effective_at` on candidates BEFORE ranking/truncation to `top_k` | high → yes |
| `text_hash` over truncated text | Unstable evidence identity (see 08-01) | Adapter hashes full `chunk.content` | high → yes |
| Direct repo path drops the legacy 15s timeout | Hung retrieval blocks the node | Adapter wraps its retrieval in an `asyncio.wait_for(..., timeout=15.0)` equivalent to the legacy `search_policy` guard; on timeout returns an error result | high → yes |
| Facade leaks pgvector/repo internals to caller | Tight coupling, contract bypass | Facade returns only `KnowledgeSearchResult`; no chunk/repo objects exposed | medium |
</threat_model>
