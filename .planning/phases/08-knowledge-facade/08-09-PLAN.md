# 08-09 PLAN: WR-01 red-line fix — fetch policy text in-node, never through AgentState/checkpoint

<objective>
08-08 closed WR-01 by carrying transient policy text through `AgentState.retrieved_evidence_payloads`. Codex phase-acceptance review (three-way confirmed) found a BLOCKER: the graph compiles with `AsyncPostgresSaver` (graph.py:97), so LangGraph serializes the **entire AgentState into the Postgres checkpoint after every super-step**. `retrieve_policy_evidence` and `generate_recommendation` are separate super-steps, so the checkpoint taken between them persists `retrieved_evidence_payloads` — including full policy text. `Field(exclude=True)` only strips `KnowledgeSearchResult.model_dump()`; it cannot stop a state channel from being checkpointed. The next turn's `receive_request` reset to `None` cannot undo already-written historical checkpoints. This violates the hash-only red line (CONTEXT D-B3) — the original 08-08 plan's design blind spot (it audited model_dump/API/trace/canonical, not the checkpoint path).

This plan replaces the transient-state channel with **in-node re-fetch**: `generate_recommendation` re-reads chunk content from the DB at prompt-build time, using the canonical `evidence_refs` (doc_key/chunk_id) already in state. Policy text lives ONLY in node-local variables and the LLM prompt. It never enters AgentState, the checkpoint, trace, audit, or EvidenceRefV1. Correctness does not depend on EphemeralValue, checkpointer internals, or future LangGraph semantics.

WR-02 and IN-01 from 08-08 are verified correct and are NOT re-touched here.
</objective>

<threat_model>
ASVS L1; block on high.

| Threat | Impact | Mitigation | Blocking? |
| --- | --- | --- | --- |
| Policy text persisted via checkpoint (the 08-08 blocker) | Hash-only contract broken; policy content in Postgres checkpoint history | Re-fetch in-node; text never written to any state channel | high → yes |
| Re-fetched content drifted from retrieved version | Prompt shows different policy text than what was cited/hashed | Recompute text_hash on re-fetched content; require it equals the ref's text_hash; fail closed on mismatch | high → yes |
| Cross-tenant / wrong-chunk content fetched | Tenant isolation breach; wrong policy in prompt | Query bound by tenant_id + doc_key + chunk_id; verify returned keys map 1:1 to requested canonical refs | high → yes |
| Missing / duplicate rows on re-fetch | Partial or ambiguous grounding silently used | Fail closed: if any cited ref's content is missing/duplicate, do not present it as grounded | high → yes |
| N+1 query per evidence | Latency blow-up | Single batched query for all keys | medium → no |
</threat_model>

<must_haves>
- Policy text is fetched inside `generate_recommendation` and exists only in node-local scope + the LLM prompt. It is never assigned into any AgentState field.
- All 08-08 transient-channel artifacts (RetrievedEvidencePayload, retrieved_payloads, retrieved_evidence_payloads, its reset, its node write, adapter build) are removed.
- New repository method does a single batched query bound by `tenant_id` + (doc_key, chunk_id) pairs.
- Re-fetched content's `text_hash` (via `evidence_text_hash`) is verified equal to the canonical ref's `text_hash`; on any mismatch / missing / duplicate / tenant-mismatch, that ref is treated as ungrounded — fail closed (do not feed unverified text as grounded policy).
- Prompt text is deterministic prefix-truncated to `MAX_EVIDENCE_TEXT_CHARS`, capped by `MAX_PROMPT_EVIDENCE_ITEMS` and `MAX_PROMPT_EVIDENCE_TOTAL_CHARS`.
- `text_hash` continues to be derived from full `chunk.content` (re-fetch reads full content; truncation only applies to the prompt copy).
- `generate_recommendation` obtains its session via `config["configurable"]["session"]` (same pattern as retrieve node); no implicit/unmanaged session creation.
- WR-02 and IN-01 behavior unchanged. Golden bytes unchanged. No regressions.
</must_haves>
