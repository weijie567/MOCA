# Phase 64.2 Research — Evidence Identity, Immutable Replay, And Memory Provenance

## Research question

What must the planner know to implement Phase 64.2 without confusing the target contract in `docs/contract-spec.md` with the current repository state?

## Executive summary

The roadmap findings are confirmed in live code. The current implementation already has useful building blocks—`EvidenceRefV1`, KnowledgeService validation, `memory_identity.v1`, CWC revisions, replay V3, tombstones, and review metadata—but the trust chain breaks at the joins:

1. CWC terminal projection promotes every non-empty tool summary into `verified_facts` without checking tool status, error, authority class, completeness, freshness, or canonical source identity.
2. Evidence identity is a display alias (`doc_key/chunk_id@vN`) generated by multiple call sites; current repository validation resolves by mutable `(doc_key, chunk_id)` and explicitly requires the latest document version.
3. Re-ingestion increments `PolicyDocument.version` in place, deletes all document blocks/chunks, then inserts replacements. Old evidence content is therefore not resolvable after a new ingestion.
4. Replay events store `evidence_refs_json`, but Replay V3 projection omits it and replay lookup does not resolve immutable evidence versions.
5. Session memory candidate identity is computed twice with different source types, memory types, and content envelopes. The node projection can report a different candidate hash from the durable service event.
6. Case-memory review uses read-then-mutate with no row lock/CAS, pending lists include expired rows, and the case-memory identity index is non-unique. Concurrent duplicates/reviews and stale pending behavior remain service races.

The phase should be seven plans, ordered by dependency and ownership boundary. A single plan would be a planning blocker under `AGENTS.md`.

## Confirmed current-state findings

### 1. CWC fact promotion is status-blind

`src/memory/case_working_context_lifecycle.py::_project_verified_facts` iterates `state["tool_results"]`, selects the first non-empty `summary`/`prompt_summary`/`tool_summary`, and constructs `CaseWorkingContextVerifiedFactV1`. It does not inspect `status`, `errors`, `partial`, authority type, freshness, business-fact refs, or canonical policy refs. A result without a durable tool result id falls back to the run-level source ref.

This directly confirms the roadmap issue that denied/failed/partial summaries can become `verified_facts`. Existing CWC write validation verifies tenant/run/case provenance for the outer candidate but not fact-level authority.

Planning implication: introduce a typed promotion result/reason model and validate source refs before projection. Keep rejected values as observations/errors; do not make the write service infer authority from prose.

### 2. Evidence alias construction is duplicated and mutable

`src/knowledge/schemas.py::EvidenceRefV1.from_parts` creates `evidence_id` as `f"{doc_key}/{chunk_id}@{policy_version}"`. `src/knowledge/retrieval.py` and `src/repositories/policy_chunk_repo.py` construct the same alias independently. There is no single parser/recompute/validation object covering tenant, document row/version, chunk row/version, content hash, and immutable storage identity.

`KnowledgeService.get_verified_evidence_details` verifies `text_hash`, tenant, freshness, scope, and that `current_policy_version == ref.policy_version`, but the repository query is keyed only by current `(doc_key, chunk_id)`. Old refs intentionally fail as `latest_version_invalid`; they cannot support historical replay.

Planning implication: separate canonical immutable evidence identity from current-retrieval eligibility. One owner should mint, parse, canonicalize, and validate; all downstream consumers import it.

### 3. Re-ingestion destroys exact historical resolution

`src/rag/ingestion.py::IngestionService.ingest_document` locks the current `PolicyDocument`, increments its integer `version` in place when the fingerprint changes, overwrites document content/metadata, deletes all `DocumentBlock` and `PolicyChunk` rows for the document, and inserts new rows.

`PolicyDocument` is unique on `(tenant_id, doc_key)`. `PolicyChunk` has neither an immutable version column nor a version table. The physical chunk UUID changes during replacement, but EvidenceRef uses the logical `chunk_id` plus the new mutable document version.

Planning implication: add append-only immutable document/chunk/evidence version storage or equivalent immutable version rows before migrating ingestion. Current document/chunk rows may remain a current head projection, but replay must bind the immutable version row/hash.

### 4. Replay does not project or resolve evidence versions

`AgentTraceEvent` and `ReplayService.append_event` accept `evidence_refs_json`, but `ReplayEventV3` has no typed evidence snapshot field and `ReplayService.project_event` does not project the stored column. `get_replay` rebuilds only timeline and a sanitized RAG claim summary from event payloads; it does not validate or resolve exact document/chunk versions.

Planning implication: introduce a typed immutable evidence snapshot reference in replay events/resource refs, persist it at event creation, backfill only provable legacy refs, and add tenant-scoped exact-version resolution with generic external failures.

### 5. Session candidate hashes have two incompatible envelopes

`src/agent/nodes/memory_write.py::_session_candidate_identity` uses:

- `source_type="agent_run"` with only `agent_run_id`;
- `memory_type="session"`;
- a reduced content envelope containing slot values, intent, summary, and unresolved questions.

`src/memory/service.py::_session_write_identity` uses:

- `source_type="session_memory_write"` with `run_id` and `agent_run_id`;
- `memory_type=SESSION_MEMORY_TYPE`, currently `"session_slot"`;
- the complete versioned write-candidate envelope including tenant/user/thread/run, full slots, refs, expected version, PII classification, decision, and reason.

Both call the shared hashing primitives but cannot produce the same candidate hash. This confirms the roadmap finding.

Planning implication: the service identity builder becomes public/shared; the node must consume the service-produced identity/result rather than precompute a local approximation.

### 6. Memory normalization differs from the accepted target text

`src/memory/identity.py::normalize_memory_content` uses Unicode `NFKC` plus `casefold()` for all content. The accepted target contract describes NFC, whitespace normalization, selective lowercasing only for enum-like fields, and preservation of user/business proper nouns.

This is a verified spec/implementation divergence, not proof that either side is automatically correct. The phase must adjudicate it before changing hashes because existing rows/tombstones depend on the old algorithm.

Planning implication: version the identity algorithm and backfill/compatibility strategy. Do not silently reinterpret old hashes in place.

### 7. Case-memory duplicates and pending review are not transactionally closed

`CaseMemoryRepository` has a non-unique active content index, performs duplicate lookup before insert, and mutates review status after a non-locking read. `approve_case_memory` and `reject_case_memory` both check `needs_review` in Python, so two concurrent reviewers can both pass before flush. `list_pending_review` does not exclude `expires_at <= now`.

The current active duplicate statuses include `needs_review`, which is correct semantically, but no database uniqueness/CAS guarantees the race. Long-term memory has a partial unique current identity index; case memory does not.

Planning implication: define exact duplicate keys, expiry transition semantics, unique constraints or claim/CAS mechanics, and idempotent review behavior before API changes.

### 8. Reviewed case-memory provenance is incomplete at the policy-ref edge

Closed-case precedent generation projects policy refs down to `doc_key`, `chunk_id`, and `policy_version`. It loses tenant, text hash, retrieval config version, rank, immutable version row, and exact source content identity. The case memory row stores source/run/reviewer fields, but these reduced refs cannot reconstruct the actual evidence version.

Planning implication: preserve canonical immutable evidence snapshot refs and source status/authority in the candidate and stored record. Do not make case memory itself an evidence authority.

## Recommended plan decomposition

### 64.2-01 — Canonical immutable evidence contract and persistence

Define the canonical identity/version schemas, immutable document/chunk/evidence tables or rows, constraints, migration, and compatibility resolver. This is the foundation for all other plans.

### 64.2-02 — Ingestion/retrieval identity migration and backfill

Make ingestion append immutable versions, keep an explicit current head, centralize EvidenceRef mint/validate, migrate KnowledgeService/repositories, and add provable backfill plus unresolved legacy status.

### 64.2-03 — Verified-fact promotion boundary

Add typed authoritative promotion rules and reason codes; migrate CWC terminal projection and reviewed precedent generation so invalid/partial/error observations never enter verified facts or reviewed case memory.

### 64.2-04 — Immutable replay binding and resolution

Persist/project typed exact-version evidence snapshot refs, resolve original content after re-ingestion/correction/tombstone, and preserve no-existence-leak semantics.

### 64.2-05 — Shared memory candidate identity and provenance

Adjudicate/version normalization, expose one candidate builder, remove node/service drift, preserve canonical scope/status/source/run/evidence/reviewer/correction lineage through review storage and APIs.

### 64.2-06 — Duplicate, pending-review, correction, and tombstone lifecycle

Add DB constraints/CAS/idempotency, deterministic expiry/rejection/correction/tombstone transitions, concurrency tests, and compatibility migration for legacy hashes/statuses.

### 64.2-07 — Cross-subsystem parity and closeout

Add architecture guards for local hash/alias construction, run migration and end-to-end matrices, update spec MVP/target annotations if needed, and update both validation/debt ledgers.

Dependencies: 01 precedes 02 and 04; 02 precedes 03/04; 05 precedes 06; 03/04/06 precede 07. Plans 03 and 05 may be parallel only if their declared file surfaces do not overlap.

## Migration and backfill design constraints

1. Additive first: create immutable/versioned structures and nullable foreign keys before changing writers.
2. Backfill only when current rows, hashes, tenant, and version aliases prove a unique mapping. Mark ambiguous/missing legacy refs explicitly unresolved.
3. Dual-read must have one canonical resolver and metrics/reason codes; it must not become a permanent second identity algorithm.
4. Cut writers to immutable versions before enforcing non-null exact refs.
5. Add uniqueness/CAS constraints after deduplicating existing provable duplicates with an auditable rule. Never merge distinct tenant/scope/source identities by text similarity.
6. Downgrade must not silently discard historical version data. If a full downgrade is unsafe, document/guard the limitation in the migration test.

## Threat model input

| Threat | Attack/failure | Required mitigation |
|--------|----------------|---------------------|
| T64.2-01 forged evidence alias | Caller supplies another tenant's logical ID or a valid-looking ID with mismatched hash | Recompute at tenant-scoped repository boundary; generic not-found/mismatch externally |
| T64.2-02 mutable replay substitution | Old run resolves current content after re-ingestion | Bind exact immutable version row and integrity hash at event time |
| T64.2-03 unsafe legacy backfill | Ambiguous alias is upgraded to verified evidence | Backfill only unique/provable mappings; unresolved state is non-authoritative |
| T64.2-04 hash algorithm reinterpretation | New normalization makes old candidate/tombstone refer to different content | Version identity algorithms; compatibility reads retain original version |
| T64.2-05 concurrent duplicate/review | Two writers/reviewers create or approve the same identity | Unique constraints, row locks/CAS, idempotent terminal outcomes |
| T64.2-06 tombstone resurrection | Delayed writer recreates deleted/expired content | Tombstone check and candidate claim in same transaction; terminal lifecycle guards |
| T64.2-07 provenance laundering | Failed observation becomes verified fact or reviewed precedent | Typed authority/status promotion gate; reviewed memory cannot upgrade authority |
| T64.2-08 existence leakage | Cross-scope replay/memory/evidence mismatch reveals target existence | Tenant/scope predicates before detailed mismatch; stable generic external errors |

Block execution planning if a plan omits mitigations for T64.2-01, T64.2-02, T64.2-05, or T64.2-07.

## Known uncertainty

- The exact new table names and whether current `PolicyDocument` remains the mutable head are planner discretion; live code confirms the need for immutable version rows, not one mandatory schema shape.
- The accepted normalization rule and existing NFKC/casefold algorithm conflict. The phase must record whether the spec changes or a versioned migration implements the target; this research does not choose silently.
- Production database duplicate cardinality is not available in this local checkout. Migration plans must include a dry-run/audit query before enforcing unique constraints.
