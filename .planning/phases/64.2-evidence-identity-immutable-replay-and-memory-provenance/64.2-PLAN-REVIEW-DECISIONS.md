## Claude Independent Review — Adjudication

All twelve findings were checked against the live repository and the repaired nine-plan graph. Each finding is accepted; the plan changes below remain prospective requirements rather than claims about the current implementation.

### CLAUDE-01 — Scope binding is not part of canonical identity or every trust boundary

- **Outcome:** accepted
- **Live evidence:** `src/db/models.py::PolicyDocument` currently has tenant ownership but no merchant-policy scope column, and `src/repositories/policy_chunk_repo.py` emits an empty `merchant_ids` list. The repository therefore does not support treating a request merchant as an authoritative evidence scope.
- **Repair status:** ✅ planned in Plan 01 Tasks 1–2, Plan 02 Tasks 1–3, Plan 04 Task 1, Plan 05 Tasks 1–2, Plan 06 Tasks 1–2, and Plan 09. The MVP contract fixes exact runtime strings `scope_type="tenant_policy"` and `scope_id=str(tenant_id)`, binds those serialized/stored values into canonical hash identity and every resolver, rejects same-tenant cross-scope and request-derived-scope inputs, and requires any later global/merchant/custom scope to use a versioned identity contract and migration.

### CLAUDE-02 — Production event binding has an unresolved type/granularity mismatch

- **Outcome:** accepted
- **Live evidence:** `src/replay/service.py::ReplayService.append_event` currently accepts raw `evidence_refs_json: list[dict]`, while `ReplayEventV3` has no typed full immutable-snapshot contract. Existing production emitters likewise do not expose a typed canonical-reference input.
- **Repair status:** ✅ planned in Plan 06 Task 1 and Plan 09 Tasks 1–2. Emitters accept only `canonical_evidence_refs: list[EvidenceRefV1]`; `append_event` is the sole owner of `_build_replay_evidence_snapshots` and persists full `ReplayEvidenceSnapshotV1` values. Tests compare the complete stored projection, not merely IDs.

### CLAUDE-03 — Final backfill/cutover is not serialized with concurrent writes

- **Outcome:** accepted
- **Live evidence:** the current repository has neither a database-native evidence write sequence nor a rollout-row lock/CAS protocol capable of serializing the final gap check with read activation. Timestamp-only ordering cannot close that race.
- **Repair status:** ✅ planned in Plan 01 Task 2, Plan 02 Tasks 1–2, and Plan 09 Tasks 1 and 3. The repaired design assigns monotonic write sequences in the ingestion transaction, captures a sequence watermark under rollout locking, reconciles through the current head, and atomically CAS-enables canonical reads only at zero gaps, including a real concurrent-ingestion race.

### CLAUDE-04 — Tombstone replayability and retention are asserted but unspecified

- **Outcome:** accepted
- **Live evidence:** current mutable evidence and replay JSON have no normalized restrictive dependency from replay snapshots to retained immutable evidence, so they do not by themselves prevent destructive purge during the audit-retention window.
- **Repair status:** ✅ planned in Plan 01 Task 2, Plan 06 Tasks 1–2, and Plan 09 Tasks 1 and 3. Immutable content/hash/locator material is retained through the audit period, `EvidenceSnapshotDependency` blocks purge while snapshots depend on it, and expiry/tombstone replay plus destructive purge/downgrade guards are exercised.

### CLAUDE-05 — Rejected observations can enter reviewed case memory

- **Outcome:** accepted
- **Live evidence:** `src/memory/case_precedent.py` currently constructs case-memory summaries/caveats and reduced policy references from CWC-derived material, so the previous plan language allowing rejected observations as bounded caveats would violate D-02.
- **Repair status:** ✅ planned in Plan 07 Task 1 and Plan 09 Tasks 1–2. Rejected/observed material stays exclusively in CWC observation/audit storage and is prohibited from every CaseMemory content, caveat, provenance, authority, and reference field; `test_rejected_cwc_observation_never_enters_case_memory` makes the negative explicit.

### CLAUDE-06 — `contextual_only` and `unknown` are not explicitly non-promotable

- **Outcome:** accepted
- **Live evidence:** the current code has no complete authority-aware promotion contract, and the prior plan did not make both non-authoritative classes unconditional non-promotion outcomes.
- **Repair status:** ✅ planned in Plan 05 Tasks 1–2 and Plan 09. Only `business_fact` and `policy_evidence` may promote; `contextual_only` produces `observe/contextual_only_non_authoritative`, `unknown` produces `reject/unknown_authority`, and both have stable negative tests.

### CLAUDE-07 — Terminal identity resurrection is not durably specified

- **Outcome:** accepted
- **Live evidence:** current `CaseMemory` and `MemoryTombstone` uniqueness/index paths are filtered around active or non-deleted rows and there is no durable full canonical-key claim surviving every terminal state.
- **Repair status:** ✅ planned in Plan 08 Tasks 1–3 and Plan 09. `CaseMemoryIdentityClaim` owns the full seven-field canonical identity independently of row lifecycle, remains after rejection/expiry/supersession/deletion/tombstone, and is acquired or updated in the same transaction as memory, lineage, and event state. Delayed and concurrent resurrection tests cover all terminal states.

### CLAUDE-08 — Legacy-unresolved rows conflict with a strict provenance envelope

- **Outcome:** accepted
- **Live evidence:** current CaseMemory provenance is represented by free-form fields/JSON and has no discriminated legacy-unresolved envelope or central resolution-state validator.
- **Repair status:** ✅ planned in Plan 07 Tasks 1–2, Plan 08 Tasks 1–2, and Plan 09. Resolved rows use `CaseMemoryProvenanceV1`; incomplete legacy rows use the separate `LegacyUnresolvedCaseMemoryProvenanceV1` envelope and are excluded from promotion, authoritative listing/retrieval, review, provenance expansion, and idempotent matching until resolved.

### CLAUDE-09 — Duplicate backfill survivor-to-many lineage cardinality is unclear

- **Outcome:** accepted
- **Live evidence:** current/planned scalar lineage fields cannot faithfully encode one survivor related to every duplicate in groups larger than two, and the repository has no normalized survivor-to-many lineage association.
- **Repair status:** ✅ planned in Plan 07 Task 1, Plan 08 Tasks 1 and 3, and Plan 09. `CaseMemoryLineageLink` stores deterministic ordered survivor-to-related associations; a four-row duplicate fixture must yield one survivor, three lineage links, and one durable identity claim.

### CLAUDE-10 — Migration 026 cannot be exercised by the stated clean-upgrade gate

- **Outcome:** accepted

- **Repair status:** ✅ planned in Plan 09 Task 3. The migration harness now performs 024→025, deploys and health-checks the real dual-write ingestion path, activates it by CAS, then applies 026, reconciles and activates reads, and finally applies 027 and 028. ### CLAUDE-11 — D-18 dependency and overlap validation is asserted but not implemented

### CLAUDE-12 — Operational cutover rollback is missing

- **Outcome:** accepted

## Claude Repair Re-review — Loop 2

All four residual findings were checked against the repaired plans and current repository boundaries. Each is accepted.

### CLAUDE-R2-01 — Cutover lock does not explicitly serialize ingestion writers

- **Outcome:** accepted
- **Evidence:** the first repair locked/CAS-updated the rollout row in cutover, but Plan 02 Task 1 did not require every writer that can publish a visible current head to acquire that same lock/epoch. A pre-activation writer could otherwise cross the final zero-gap boundary.
- **Repair status:** ✅ Plan 02 now requires a single rollout-first lock order for writer, health activation, reconciliation, rollback, and final read activation. Named two-session coverage proves both writer-first and activator-first interleavings under one CAS epoch.

### CLAUDE-R2-02 — Unchanged-ingestion sequence invariant is ambiguous

- **Outcome:** accepted
- **Evidence:** the prior wording allowed unchanged ingestion to advance its sequence only "as defined by the owner," which was insufficient for a sequence-watermarked reconciliation proof.
- **Repair status:** ✅ Every successful ingestion allocates exactly one database sequence. Unchanged ingestion writes that sequence to the current projection while preserving the same immutable FK/identity/hash and row count; tests cover both sides of the watermark.

### CLAUDE-R2-03 — Legacy replay JSON is not clearly read-only

- **Outcome:** accepted
- **Evidence:** current `ReplayService.append_event` accepts `evidence_refs_json`, and the first repair preserved compatibility resolution without explicitly limiting it to already-persisted legacy events.
- **Repair status:** ✅ Plan 06 removes `evidence_refs_json` from every new append signature. Only persisted pre-64.2 rows or an explicit existing-row migration adapter may read it; a raw/reduced append negative must leave event, snapshot, and dependency counts unchanged.

### CLAUDE-R2-04 — Scope ID runtime representation is inconsistent

- **Outcome:** accepted
- **Evidence:** Plan 01 specified `scope_id=str(tenant_id)` while downstream prose sometimes used `scope_id=tenant_id`, risking divergent serialized/hash material.
- **Repair status:** ✅ Plans 01/02/04/05/06/09 and VALIDATION now use exact strings `scope_type="tenant_policy"` and `scope_id=str(tenant_id)` and require serialization/storage/hash equality tests.
