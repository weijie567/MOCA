## GSD Plan Checker — Round 1

### GSD-01 — Production emitters do not bind evidence into replay

- **Outcome:** accepted
- **Evidence:** `src/agent/nodes/investigate.py::_emit_tool_event` receives tool context but the event path through `src/agent/events.py::emit_event` and `src/replay/decision_events.py::emit_decision_event` exposes no canonical evidence binding argument. `ReplayService.append_event` accepts `evidence_refs_json`, but Plan 04 did not include the production emitter files.
- **Required repair:** Plan the complete production path and test the real emitter, not only direct `ReplayService.append_event` calls.

### GSD-02 — D-13 candidate identity migration is incomplete

- **Outcome:** accepted
- **Evidence:** local builders remain in `src/memory/case_memory.py`, `src/memory/long_term.py`, `src/memory/case_working_context_service.py`, `src/memory/service.py`, and `src/agent/nodes/memory_write.py`.
- **Required repair:** enumerate all builders; centralize complete candidate identity construction in `src/memory/identity.py` or typed wrappers owned there; make the static guard executable before closeout.

### GSD-03 — Reviewed provenance is ordered before its CWC source contract

- **Outcome:** accepted
- **Evidence:** current `CaseWorkingContextPolicyRefV1` and `case_precedent._project_policy_refs` preserve only reduced doc/chunk/version triples. Plan 03 owns promotion-bearing canonical refs but Plan 05 tried to persist complete provenance before Plan 03.
- **Required repair:** separate shared identity-owner migration from reviewed provenance; make provenance projection/persistence depend on Plan 03.

### GSD-04 — Source-distinct candidates may be conflated after a unique race

- **Outcome:** accepted
- **Evidence:** the proposed active content uniqueness key is narrower than complete canonical candidate/source identity, while the retry branch returned the winner as idempotent without checking `candidate_hash`/`source_identity_hash` equality.
- **Required repair:** idempotent only for exact canonical candidate identity; different source identity returns explicit conflict/unresolved behavior or bounded additional provenance, with PostgreSQL race coverage.

### GSD-05 — Expansion/backfill and writer cutover leave a write window

- **Outcome:** accepted
- **Evidence:** Plan 01 backfilled mutable current heads; Plan 02 introduced immutable writer behavior later. A write between them would not have an immutable historical version.
- **Required repair:** Plan 01 is additive schema/identity only. Plan 02 installs dual-write before backfill, captures a watermark, backfills, reconciles writes after the watermark, then enables canonical-only reads. Test an intervening write.

### GSD-06 — Spec/debt verification can pass before implementation

- **Outcome:** accepted
- **Evidence:** the Plan 07 `rg` alternation succeeds today because `.planning/ARCHITECTURE-DEBT.md` already mentions Phase 64.2; it does not prove every required marker in the correct spec sections or both RAG/memory ledger entries.
- **Required repair:** use architecture tests or separate ANDed assertions scoped to §8.3/§13/§17 and distinct RAG/memory debt markers including implemented/legacy/target wording.

### GSD-07 — Memory plans exceed safe ownership/file granularity

- **Outcome:** accepted
- **Evidence:** Plan 05 declared 14 files and Plan 06 declared 10 before adding missing D-13 consumers and provenance fixes.
- **Required repair:** split the memory work into shared identity-owner migration, reviewed provenance projection/persistence, and lifecycle/concurrency plans with dependency order and limited file surfaces.

### GSD-08 — Validation strategy is not task-complete

- **Outcome:** accepted
- **Evidence:** `64.2-VALIDATION.md` has seven plan-level rows while the actual graph has multiple tasks per plan and marks not-yet-created test files as existing.
- **Required repair:** one row per actual task, exact task command, and planned/Wave-0 status for new files.

## GSD Plan Checker — Round 2

Round 2 confirmed GSD-01 through GSD-08 closed, then found the following additional issues.

### GSD-09 — Approval snapshot replacement bypasses canonical repository validation

- **Outcome:** accepted
- **Evidence:** `src/approvals/service.py::_replacement_action_and_evidence` parses caller/API evidence with `EvidenceRefV1.model_validate`, canonicalizes the projection, and passes it to `persist_action_safety_snapshot`; it does not recompute tenant/version/hash against the immutable evidence repository.

### GSD-10 — Source authority and memory authority are conflated

- **Evidence:** the repaired promotion plan emits `business_fact|policy_evidence|contextual_only|unknown`, while the reviewed-provenance plan fixed `source_authority_class=contextual_only` and required it to remain so.
- **Required repair:** persist original per-source authority separately from `memory_authority_class=contextual_only`; review changes neither source provenance nor memory authority.

### GSD-11 — D-01 through D-20 lack an explicit coverage map

- **Outcome:** accepted
- **Evidence:** decisions appear across plan frontmatter and prose but there is no complete decision-to-plan/task/rationale map suitable for drift detection.
- **Required repair:** add an explicit D-01..D-20 coverage table to the final closeout plan and make its architecture test validate completeness.

### GSD-12 — Closeout must_haves omit end-to-end key links

- **Outcome:** accepted
- **Evidence:** closeout has truths/artifacts but no `key_links` for the evidence/replay chain or the CWC/memory/lifecycle chain.
- **Required repair:** add both key links with concrete source, destination, mechanism, and test pattern.

## GSD Plan Checker — Round 3

### GSD-13 — `verified_evidence_refs` remains an independent approval bypass

- **Outcome:** accepted
- **Evidence:** approval creation persists `command.verified_evidence_refs or command.evidence_refs`, while Plan 04 Task 1 only required canonical repository validation of `evidence_refs`. The two lists can therefore diverge before request persistence.
- **Required repair:** repository-recomputed canonical refs become the sole persisted verified-evidence source, or an explicitly defined equality/subset contract validates both lists atomically. Add forged, mismatched, and cross-tenant `verified_evidence_refs` negatives and assert no snapshot/request/event rows.

## GSD Plan Checker — Round 4

- **Outcome:** accepted
- **Evidence:** Plan 04 prose required reused snapshot evidence equality, but the test matrix did not explicitly pre-create a valid action/hash-bound snapshot whose stored evidence diverges from repository-canonical evidence. A zero-row assertion is also invalid for a fixture that necessarily starts with a snapshot row.
