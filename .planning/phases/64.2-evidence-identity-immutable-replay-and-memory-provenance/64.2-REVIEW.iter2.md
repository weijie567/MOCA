## Warnings

### WR-01: Unresolved cutover is recorded as an applied migration

**File:** `src/db/migrations/versions/026_phase64_2_evidence_cutover.py:83-92`

**Issue:** When reconciliation finds unresolved current heads, `upgrade()` writes quarantine metadata and then returns normally. Alembic therefore treats revision 026 as successful and stamps it as applied, even though canonical reads remain disabled and the cutover was not achieved. A normal retry cannot re-run 026, and the migration chain can proceed into 027/028 despite the required `025 -> deploy/health/dual-write -> 026 cutover -> 027/028` gate. The tests cover the healthy staged path and statically assert that the migration mentions `legacy_unresolved`, but do not assert the Alembic revision after an unresolved cutover.

**Fix:** Make unresolved reconciliation a failed/retryable gate rather than a successful migration return. Persist quarantine/audit state through a separate operational preflight/reconciliation transaction (so a migration rollback does not erase it), then have revision 026 abort until that preflight proves zero unresolved heads:

```python
if unresolved_count:
    raise RuntimeError(
        "canonical evidence cutover blocked: unresolved legacy heads remain"
    )
```

Add a PostgreSQL migration test proving that an unresolved run leaves the Alembic revision at 025 and that, after reconciliation, 026 can be retried before 027/028.

### WR-02: Verified-context construction bypasses exact immutable identity validation

**File:** `src/knowledge/service.py:613-622`

**Issue:** `build_verified_context()` calls `get_verified_evidence_details()`, which resolves candidates by mutable `(doc_key, chunk_id)` and verifies current content/version/hash, but does not compare `evidence_id`, `document_version_id`, `chunk_version_id`, scope, and version fields to the persisted immutable binding. The exact comparison already exists in `validate_current_evidence()` at lines 446-540, but this production package path does not use it. `ContextBuilder` independently repeats the same legacy call at `src/agent/rag_context/builder.py:210-247`. Consequently, a canonical-shaped ref containing invented immutable UUIDs and a self-consistent recomputed `evidence_id`, while retaining a real current logical key/hash, can enter a `VerifiedEvidencePackageV1` and be presented as verified context. Approval later revalidates exact refs, but non-approval answer generation can still consume unsupported policy authority.

**Fix:** Route both package construction and context content loading through the exact current-evidence validator:

```python
details = await self.validate_current_evidence(
    tenant_id=knowledge_context.tenant_id,
    evidence_refs=candidates,
    effective_at=knowledge_context.effective_at,
    merchant_scope=knowledge_context.merchant_scope,
    doc_type=_optional_str(policy.get("doc_type")),
    risk_level=_optional_str(policy.get("risk_level")),
)
```

Prefer passing the already validated details into `ContextBuilder`; otherwise make the builder call `validate_current_evidence()` before its compatibility methods. Add a negative test using a real current `doc_key/chunk_id/text_hash` with validly hashed but nonexistent/different immutable IDs and assert generic rejection with no verified content.

### WR-03: CWC promotion equates canonical shape with retained policy authority

**File:** `src/memory/case_working_context_lifecycle.py:603-633,679-692,770-811`

**Issue:** The terminal CWC projection parses policy refs with Pydantic, checks tenant/scope strings and `to_canonical_identity()`, and then defaults `reference_validation` to `valid`. It never asks `EvidenceVersionRepository` or `PolicyKnowledgeService` to resolve the exact retained immutable row. `promote_verified_fact()` therefore receives a trusted-looking `reference_validation="valid"` and promotes the observation to `CaseWorkingContextVerifiedFactV1`, from which closed-case projection can create reviewed CaseMemory source authority. The positive fixture at `tests/agent/test_case_working_context_lifecycle.py:319-344` mints random document/chunk version UUIDs without persisting them, and lines 405-434 assert that this fabricated identity is promoted; similar structurally minted fixtures occur in the integration/provenance tests. Those fixtures mask the missing production resolution instead of exercising it.

**Fix:** Move policy promotion behind an async service-owned boundary with an injected exact immutable resolver. Set `reference_validation="valid"` only after every policy ref resolves to the retained row under trusted `tenant_id`, `scope_type="tenant_policy"`, and `scope_id=str(tenant_id)`; malformed, missing, forged, cross-tenant, or cross-scope refs must remain observed/rejected and never enter `verified_facts` or reviewed provenance. Update positive tests to persist `PolicyDocumentVersion`/`PolicyChunkVersion` rows (or stub explicit resolver success), and add a canonical-shaped nonexistent-ID negative test.
