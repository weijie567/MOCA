# Phase 64.2: Evidence Identity Immutable Replay And Memory Provenance - Context

**Gathered:** 2026-08-05
**Status:** Ready for planning
**Mode:** Autonomous discussion; conservative recommended defaults selected

<domain>
## Phase Boundary

Make evidence, replay, Case Working Context, and reviewed memory identity trustworthy across ingestion, retrieval, agent projection, persistence, review, and replay. This phase closes the owned failures named in the roadmap: invalid observations entering `verified_facts`, non-canonical evidence aliases, mutable replay references, competing memory-candidate hashes, provenance loss during review, and unenforced duplicate/pending-review lifecycle behavior.

This phase does not optimize retrieval quality, change PII vocabulary governance (Phase 70), redesign operation dispatch (Phase 66), centralize model/provider policy (Phase 69), decompose broad service boundaries (Phase 71), or add production external effects.

</domain>

<decisions>
## Implementation Decisions

### Verified-fact promotion and authority

- **D-01:** CWC `verified_facts` are produced only by one typed promotion boundary. A successful transport call alone is insufficient: the observation must be authoritative for the fact class, complete, scope-valid, freshness-valid where applicable, and carry validated canonical source references.
- **D-02:** Denied, unavailable, stale, malformed, partial, timeout, error, unresolved, and compatibility-only observations remain typed observations/errors. They must never be silently coerced into verified facts or reviewed case memory.
- **D-03:** Policy evidence, business facts, memory context, and CWC references keep distinct authority classes. Memory and CWC remain contextual-only and cannot mint policy `EvidenceRefV1`, replace fresh business reads, satisfy approval evidence, or become replay authority.
- **D-04:** Promotion failures fail closed with stable reason codes suitable for tests and audit. User-facing paths must avoid existence leakage across tenant or merchant scope.

### Canonical evidence identity and immutable versions

- **D-05:** There is one canonical evidence identity computation and validation owner. Ingestion may mint identity only from persisted canonical document/chunk/version/content material; retrieval, agent state, APIs, memory, approval snapshots, and replay validate or import that identity rather than rebuilding local aliases.
- **D-06:** Identity validation covers canonical document identity, immutable document version, chunk identity/version, evidence content hash, tenant/scope binding, and schema/config version fields required by the accepted contract. Caller-supplied IDs are untrusted until recomputed and matched at a repository/service trust boundary.
- **D-07:** Compatibility reads may accept legacy aliases only through an explicit resolver that returns the canonical immutable identity and records compatibility provenance. New writes, hashes, snapshots, and replay records use only the canonical form.
- **D-08:** Re-ingestion and correction create new immutable versions and supersession links. They do not update content-addressed evidence rows in place or make an old run resolve to the latest material.

### Replay reconstruction and lifecycle

- **D-09:** Replay persists references sufficient to resolve the exact document version, chunk version, evidence content/hash, tenant/scope, and integrity material consumed by the original run. Mutable lookup keys or a list of current evidence IDs alone are insufficient.
- **D-10:** Supersession, correction, archival, expiry, and tombstoning affect current retrieval eligibility but do not destroy historical replayability during the audit retention window. Replay resolves the original immutable version and exposes lifecycle status without treating superseded material as current authority.
- **D-11:** Migration/backfill is fail-closed and observable. Rows that cannot be proven against canonical identity remain explicitly unresolved/legacy and cannot be upgraded to verified evidence by inference.
- **D-12:** Tenant/scope mismatch, forged alias, hash mismatch, missing immutable target, and ambiguous legacy mapping use generic failure semantics externally while preserving auditable internal reason codes.

### Memory candidate identity, provenance, and review lifecycle

- **D-13:** `memory_identity.v1` remains the single owner of content normalization, `content_hash`, source identity normalization, and `candidate_hash`. Nodes, services, events, stores, deduplication, review APIs, migrations, and tests consume the shared implementation.
- **D-14:** Reviewed case-memory records preserve the real tenant and stable case/merchant scope, source status/authority class, review decision and reviewer provenance, source run/event/evidence references, candidate identity, and correction/supersession lineage. Review must not replace these fields with placeholders or defaults.
- **D-15:** Duplicate identity is exact canonical identity, not semantic similarity. Concurrent candidate submission/review is enforced by database uniqueness or transactional compare-and-set semantics plus idempotent service behavior.
- **D-16:** Pending-review expiry, rejection, correction, supersession, deletion, and tombstoning are deterministic lifecycle transitions. Expired or terminal candidates cannot be revived by a delayed writer, and distinct scope/source identities must not be silently merged.
- **D-17:** Backfill preserves uncertainty: unverifiable legacy hashes or provenance are marked legacy/unresolved and excluded from authoritative promotion until explicitly reviewed or corrected.

### Verification and rollout

- **D-18:** Planning must split the phase by ownership boundary and dependency order; a single oversized plan spanning promotion, evidence storage, replay, memory, migration, and closeout is a blocker.
- **D-19:** Verification must include unit/contract tests, PostgreSQL migration and concurrency tests, compatibility reads, forged/cross-scope negatives, re-ingestion/correction/tombstone replay, and end-to-end agent-to-memory promotion behavior.
- **D-20:** Any target-contract text in `docs/contract-spec.md` that is not fully implemented must be identified as target state. If implementation intentionally narrows it, add an explicit MVP annotation and named deferral instead of silently diverging.

### the agent's Discretion

- Exact module and class names, provided ownership remains singular and imports do not create circular service dependencies.
- Whether immutable evidence is represented by dedicated version tables or normalized immutable rows plus explicit version references, subject to migration safety and replay acceptance criteria.
- Exact stable reason-code names and index names.
- Wave composition, provided contract/schema foundations precede caller migration and final integration gates.

</decisions>

<code_context>
## Existing Code Insights

### Reusable Assets

- `src/knowledge/schemas.py`, `src/knowledge/service.py`, `src/knowledge/provenance.py`, and `src/knowledge/text_hash.py` already own much of the evidence contract, verified lookup, provenance, and content hashing surface.
- `src/common/canonical_hash.py` and `src/approvals/snapshots.py` provide the accepted canonical JSON/hash profile and an existing immutable evidence projection consumer.
- `src/replay/schemas.py`, `src/replay/service.py`, and replay validators provide the event/replay boundary to extend rather than bypass.
- `src/memory/identity.py`, `src/memory/case_memory.py`, `src/memory/case_working_context_service.py`, `src/memory/write_service.py`, `src/memory/repository.py`, and `src/memory/tombstones.py` contain current identity, promotion, review, deduplication, and lifecycle behavior.
- `src/db/models.py` plus migrations `013_long_term_case_memory.py`, `015_rag_production_ingestion_ocr.py`, and `022_case_working_context.py` expose the current schema and migration lineage.

### Established Patterns

- Canonical typed contracts live at service boundaries; caller-local dict variants and hash serializers are drift risks.
- Tenant/scope authorization fails closed and external lookup failures avoid existence leakage.
- Durable safety/replay identity uses immutable redundant identity/hash fields plus service-level transaction validation when a full composite FK cannot express the invariant.
- Memory is contextual-only. Policy evidence and current business facts retain separate authoritative services.

### Integration Points

- RAG ingestion and repositories mint document/chunk versions; KnowledgeService retrieval and provenance lookup validate them.
- Agent evidence projection and `CaseWorkingContextService` decide which observations may become verified facts.
- Replay event persistence and API reconstruction consume immutable evidence refs from the original run.
- Memory write nodes/services and review API/storage share candidate identity, provenance, lifecycle transitions, and concurrent idempotency.

</code_context>

<specifics>
## Specific Ideas

- Prefer append-only immutable versions with explicit supersession/correction lineage over in-place mutation.
- Treat legacy compatibility as a read adapter with visible provenance, not a second accepted identity algorithm.
- Preserve historical replayability while separately expressing whether evidence remains eligible for current retrieval.

</specifics>
