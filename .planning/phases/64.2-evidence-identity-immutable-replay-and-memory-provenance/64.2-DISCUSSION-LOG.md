## Verified-fact promotion

| Option | Description | Selected |
|--------|-------------|----------|
| Typed authoritative promotion | Promote only complete, scope-valid, authoritative successful observations with validated source references; retain all other outcomes as typed observations/errors | ✓ |
| Success-status promotion | Treat any tool/retrieval success status as a verified fact | |
| Reviewer-only cleanup | Allow broad promotion and rely on later memory review to remove invalid facts | |

**Choice:** Typed authoritative promotion.
**Notes:** This is the only option consistent with the roadmap requirement that failed/denied/partial observations never enter CWC `verified_facts` or reviewed case memory.

## Canonical evidence identity and versioning

| Option | Description | Selected |
|--------|-------------|----------|
| Single recomputable canonical identity | Mint identity at persisted ingestion boundary, recompute/validate at trust boundaries, and create immutable versions on change | ✓ |
| Preserve existing aliases | Keep multiple evidence ID algorithms and map them opportunistically | |
| Mutable logical key | Resolve `doc_key/chunk_id` to the latest row during all reads | |

**Choice:** Single recomputable canonical identity with immutable versioning.
**Notes:** Legacy aliases may be compatibility inputs only; they must resolve to a canonical immutable identity and cannot be written into new snapshots or replay events.

## Immutable replay

| Option | Description | Selected |
|--------|-------------|----------|
| Exact immutable source reconstruction | Store enough canonical version/hash/scope identity to resolve the exact evidence consumed by the original run after later corrections or tombstones | ✓ |
| Current-row replay | Store a logical reference and resolve the newest current document/chunk at replay time | |
| Snapshot text only | Copy snippets into events without retaining authoritative source/version identity | |

**Choice:** Exact immutable source reconstruction.
**Notes:** Lifecycle state and current retrieval eligibility are separate from historical replay retention.

## Memory identity and review lifecycle

| Option | Description | Selected |
|--------|-------------|----------|
| Shared exact identity plus transactional lifecycle | Reuse `memory_identity.v1`, preserve full provenance/scope, and enforce duplicate/review/expiry/correction invariants transactionally and in the database | ✓ |
| Service-local hashes | Let each node/store choose its own candidate hash and reconcile during review | |
| Similarity deduplication | Merge semantically similar candidates regardless of exact scope/source identity | |

**Choice:** Shared exact identity plus transactional lifecycle.
**Notes:** Exact canonical duplicates are idempotent; distinct scope/source identities remain distinct even when text is similar.
