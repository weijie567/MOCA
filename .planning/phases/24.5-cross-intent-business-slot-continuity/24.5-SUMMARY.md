# Phase 24.5 Summary: Cross-Intent Business Slot Continuity

## 目标

收口 Phase 24 之后发现的 follow-up 记忆问题：业务 ID 类 slot 在同一线程内可以跨相关 intent 延续，避免“这个订单下一步怎么处理？”这类追问因为 intent 从 `order_status_inquiry` 转为 `refund_troubleshooting` 而丢失上一轮可信 `order_id`。

## 交付

- `src/agent/nodes/memory_write.py`
  - 对 `order_id`、`refund_case_id`、`ticket_id` 这类业务 ID slot 写入跨 intent compatible intents。
  - compatible intents 来自 `REQUIRED_SLOT_POLICY`，避免手写分散列表。

- `src/memory/service.py`
  - 读取 session memory 时允许业务 ID slot 在明确相关的 intent group 内复用。
  - 非业务 ID slot 仍维持原有 intent 兼容过滤，避免 stale slot 泛化泄漏。

- `src/agent/intent_policy.py`
  - 将“下一步/怎么处理”类 advice 追问从 `action_request`/`advise` 归一到 `refund_troubleshooting`/`read_status`。
  - 避免系统误要求用户补充 action type。

## 设计边界

- 不扩大所有 slot 的跨 intent 复用，只处理业务 ID continuity。
- 不把 session memory 升级为 evidence、policy authority、action authority 或 replay truth。
- 不改变 TTL、scope 校验、tombstone 或 memory write isolation 规则。
