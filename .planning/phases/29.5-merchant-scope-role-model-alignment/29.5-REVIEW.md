Reviewed the Phase 29.5 merchant-scope / role-model alignment across the normative spec, trusted-context derivation, API resource routers, agent run/trace/replay visibility, approval resume, knowledge projection, business tool authz, and the changed regression tests.

## Warnings

### WR-01: Admin branch trusts caller-supplied role without validating the user

**File:** `src/integrations/demo_business/authz.py:25`
**Issue:** `merchant_can_access()` returns `True` for `role == "admin"` before parsing `user_id` or checking that the user exists, is active, belongs to the tenant, and actually has the admin role in the database. The public API currently gets `role` from `get_current_user()`, and the agent tool path gets it from `TrustedContextFactory`, so I did not confirm a direct external bypass. Still, this is the low-level ownership helper used by raw business tools; any future/internal caller with a forged or stale `ToolCallContext(role="admin")` would bypass all merchant checks.
**Fix:**
```python
async def merchant_can_access(
    session: AsyncSession,
    *,
    tenant_id: UUID,
    user_id: str,
    role: str,
    merchant_id: UUID,
) -> bool:
    try:
        user_uuid = UUID(user_id)
    except ValueError:
        return False

    user = (
        await session.execute(
            select(User).where(
                User.id == user_uuid,
                User.tenant_id == tenant_id,
                User.is_active.is_(True),
            )
        )
    ).scalar_one_or_none()
    if user is None or user.role != role:
        return False
    if user.role in PLATFORM_ADMIN_ROLES:
        return True
    if user.role not in MERCHANT_BOUND_ROLES:
        return False
    return user.merchant_id is not None and user.merchant_id == merchant_id
```

### WR-02: Refund and ticket merchant ownership lookup can crash instead of failing closed

**File:** `src/api/routers/refund_cases.py:46-50`, `src/api/routers/tickets.py:46-48`
**Issue:** Both routers fetch the parent order merchant with `scalar_one()` after adding `Order.tenant_id == user.tenant_id`. If a same-tenant refund case or ticket references a missing or cross-tenant order row, the lookup raises `NoResultFound` and returns a 500 instead of a controlled 404/403. This is an edge-case data-integrity path, but it sits on an authorization boundary and should fail closed.
**Fix:**
```python
merchant_id = (
    await session.execute(
        select(Order.merchant_id).where(
            Order.id == refund_case.order_id,
            Order.tenant_id == user.tenant_id,
        )
    )
).scalar_one_or_none()
if merchant_id is None:
    raise HTTPException(
        status_code=404,
        detail={"code": REFUND_CASE_NOT_FOUND, "message": "Refund case not found"},
    )
require_merchant_access(user, merchant_id, resource_name="refund cases")
```

Apply the same `scalar_one_or_none()` fail-closed pattern in `tickets.py` before `require_merchant_access()`, using the existing ticket error code/message.
