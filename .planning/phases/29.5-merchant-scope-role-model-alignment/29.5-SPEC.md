# Phase 29.5: Merchant Scope / Role Model Alignment — Specification

**Created:** 2026-06-27
**Ambiguity score:** 0.07 (gate: <= 0.20)
**Requirements:** 19 locked

## Goal

MOCA 将身份和权限模型收敛为单 tenant MVP 下的多 merchant 业务隔离模型：`support` / `manager` / legacy `merchant` 默认只能访问自己 merchant 的业务数据，`admin` 是唯一跨 merchant 业务数据角色，tenant 级平台公共政策仍可被普通业务用户读取。

## Background

当前代码已经具备单 tenant / 多 merchant 的数据基础：`Tenant`、`Merchant`、`User.merchant_id`、`Order.tenant_id + Order.merchant_id`、`RefundCase.tenant_id`、`Ticket.tenant_id`、`PolicyDocument.tenant_id` 都已存在。JWT 登录会携带 `tenant_id`，API 和 repository 路径大量使用 `user.tenant_id` 做 tenant 隔离。

当前缺口是 merchant scope 语义仍保留平台客服模型：`TrustedContextFactory` 对非 `merchant` role 默认生成 `merchant_scope=["*"]`；订单、退款、工单 API 的 merchant 隔离主要只约束 `role == "merchant"`；`support` / `manager` / `admin` 的产品语义与目标 MVP 不一致；approval、agent run、memory、replay 等对象尚未可靠绑定 target merchant。

重要前提：`docs/contract-spec.md` 是 MOCA 的 normative contract 文件，但它也是历史累计文件，不等于当前代码事实，也不保证每一段旧内容都符合新的 MVP 产品模型。Phase 29.5 的工作不是“相信旧 contract 并按字面执行”，而是把新产品决策、旧 contract、当前代码、测试和 roadmap 对齐。若旧 contract 与 Phase 29.5 目标冲突，必须先修 contract delta 并留痕；若代码与新 contract 冲突，必须通过 plan/task/test 明确改动。

Phase 30 将引入 `BusinessFactService` 作为当前业务事实权威入口。如果 Phase 29.5 不先锁定 role / merchant scope / public policy scope 语义，Phase 30-35 会继续继承旧的 tenant-wide support / manager 模型。

## Requirements

1. **Product identity model**: Phase 29.5 必须锁定目标身份模型：`tenant` 是平台/组织，`merchant` 是 tenant 下的店铺/商家，`user` 是商家内部账号。
   - Current: 文档和代码同时表达平台内部客服跨 merchant 与商家用户单 merchant 两种叙事。
   - Target: SPEC 明确单 tenant MVP 下多 merchant 的目标语义，普通业务用户默认绑定一个 merchant。
   - Acceptance: SPEC 中存在明确的 `tenant` / `merchant` / `user` 定义，并声明单 tenant MVP 的核心隔离对象是 merchant。

2. **Merchant-bound roles**: Phase 29.5 必须定义 `merchant_bound_roles = {"support", "manager", "merchant"}`。
   - Current: `support` / `manager` 被多处当作 tenant-wide 业务角色，legacy `merchant` 才被当作商家侧账号。
   - Target: `support` 是商家客服，`manager` 是商家客服主管，legacy `merchant` 兼容期按 `support` 处理；三者都必须绑定 merchant 才能访问业务数据。
   - Acceptance: SPEC、ROADMAP 或后续 tests 明确三类 role 都是 merchant-bound business user。

3. **Platform-wide role**: Phase 29.5 必须定义 `platform_admin_roles = {"admin"}`。
   - Current: `admin` 可跨 merchant，但语义未被明确为唯一跨 merchant 业务数据角色。
   - Target: `admin` 在本 phase 中等同 platform admin，是唯一允许 `merchant_scope=["*"]` 的 human role。
   - Acceptance: SPEC 明确 `admin` 是唯一 platform-wide business data role，未来新增 role 未显式归类前不得默认获得 wildcard。

4. **Unknown role default**: 任何新增或未知 role 在未显式归类前必须按 merchant-bound deny-all 处理。
   - Current: `SUPERVISOR_ROLES` 等集合中存在 `supervisor`、`approval_manager`、`manager` 等名称，未来新增 role 可能被误认为 tenant-wide。
   - Target: 未分类 role 不得默认跨 merchant；必须显式加入 `platform_admin_roles` 才能获得 wildcard。
   - Acceptance: SPEC 写明 unknown role 默认 merchant-bound deny-all，Phase 29.5 tests 或 follow-up plan 不允许新增 wildcard role 漏洞。

5. **TrustedContextFactory merchant scope**: `TrustedContextFactory` 必须按 role 和用户绑定生成 merchant scope。
   - Current: `role == "merchant"` 得到自己的 merchant scope，其他 role 默认 `["*"]`。
   - Target: `support` / `manager` / legacy `merchant` 有 `merchant_id` 时得到 `[merchant_id]`，缺失时得到 `[]`；`admin` 得到 `["*"]`。
   - Acceptance: `tests/platform/test_trusted_context_factory.py` 和 agent-run trusted config tests 覆盖 support、manager、legacy merchant、admin 的新 scope 矩阵。

6. **Server scope override cannot widen**: `server_merchant_scope` 只能缩小 scope，不能扩大 human actor 的 merchant scope。
   - Current: `TrustedContextFactory` 收到 `server_merchant_scope` 时直接采用；approval resume 路径存在 `server_merchant_scope={"merchant_ids": ["*"]}`。
   - Target: `server_merchant_scope=["*"]` 仅允许 `admin` human actor；普通 human actor 包括 `manager` 不得通过 server override 获得 wildcard。System-owned internal job wildcard scope defer 到独立 `TrustedSystemContext` 契约，不由 `create_from_request(user=...)` 隐式授权。
   - Acceptance: Tests 覆盖 non-admin human actor 传入 wildcard server scope 被拒绝；不得静默收窄后继续执行。`server_tool_permissions` 只能增加工具权限，不能扩大 merchant scope。

7. **Contract-to-code reconciliation**: Phase 29.5 必须同步更新 `docs/contract-spec.md`，但不得把旧 contract 内容当成不可质疑的事实。
   - Current: `PROJECT.md` / `ROADMAP.md` / `29.5-SPEC.md` 已记录 MER-01；`contract-spec.md` 是 normative contract 文件，但历史段落可能仍表达旧平台客服模型或未实现目标态。
   - Target: `contract-spec.md` §8.0 或相邻小节定义本 phase 新的 role-to-merchant-scope policy，并把任何与 MER-01 冲突的旧 contract 语义修正、覆盖或标注为历史/目标态。Plan 必须用仓库代码和测试核对 contract，而不是只引用 contract 证明 contract 正确。
   - Acceptance: Phase 29.5 plan 同时列出 contract delta、代码改动点和测试改动点；后续 Phase 30-35 以修订后的 contract delta 为准。若执行中发现旧 contract 与新产品模型冲突，必须修 contract 或记录 MVP scope，不得静默偏离。

8. **Required interim approval guard**: Phase 29.5 不完成最终 Approval merchant binding，但必须阻断 manager tenant-wide approval visibility / wildcard resume。
   - Current: `APPROVAL_ROLES={"admin","manager"}`，pending approval 列表按 tenant 查询；approval resume 当前可传入 wildcard server scope。
   - Target: Phase 29.5 采用 admin-only / fail-closed interim guard：`manager` 暂时不能 list/get/decide approvals，也不能通过 approval resume 获得 wildcard merchant scope。`admin` 仍可跨 merchant。Phase 29.5 不采用 `requested_by -> user.merchant_id` temporary approximation，因为 ApprovalRequest 当前缺可靠 target merchant / `BusinessFactRefV1` binding。
   - Acceptance: Tests 覆盖 manager 不能 list/get/decide approvals；manager approval resume 不生成 wildcard merchant scope；admin 仍可处理 approvals。Phase 34 再用 target merchant / `BusinessFactRefV1` binding 恢复 manager same-merchant approval queue。

9. **Required interim AgentRun / trace guard**: Phase 29.5 不完成最终 AgentRun target merchant binding，但不能继续让 `manager` 作为 tenant-wide supervisor 访问业务 run/evidence/trace。
   - Current: `SUPERVISOR_ROLES` 包含 `manager`，非 owner manager 可查看 run status/evidence/trace。
   - Target: 在 target merchant binding 落地前，business-data AgentRun status/evidence/trace 访问限制为 run owner 或 `admin`；`manager` 的 same-merchant run visibility 必须等 Phase 32/35 具备 target merchant 或 scoped business refs 后恢复。Phase 29.5 同时必须从 `SUPERVISOR_ROLES`（`src/api/routers/traces.py`、`src/api/routers/agent_runs.py`）移除无真实 role 定义的 `supervisor`、`approval_manager`，business-data run/trace 可见集合收敛为 owner 或 `admin`，符合 §8.0.1 unknown-role deny-all。
   - Acceptance: Tests 覆盖 manager 不能查看非本人 business run/evidence/trace，admin 可以；ROADMAP/deferred 明确 Phase 32/35 恢复 same-merchant manager visibility 的条件。

10. **Business data scope**: 业务数据访问必须按 `tenant_id + merchant_id` 进行普通用户隔离。
   - Current: API 路由已按 tenant 过滤，merchant 判断散落且主要只约束 legacy `merchant` role；agent/tool 路径会经由 `BusinessToolService` 调用 demo business raw reads，不能只靠 HTTP router 修复达成目标。
   - Target: `support` / `manager` / legacy `merchant` 只能访问自己 merchant 的 order、refund case、ticket；`merchant_id is None` 时 fail closed。Phase 29.5 必须提供 raw tool/business-read interim guard：当前 `get_order` / `get_refund_case` / `get_ticket` 工具路径不得允许 merchant-bound 用户读取 same-tenant 但不同 merchant 的资源。
   - Acceptance: Order / RefundCase / Ticket API tests 覆盖 same-merchant allow、same-tenant cross-merchant deny、missing merchant deny、admin cross-merchant allow；tool/business-path tests 覆盖 support/manager same-merchant allow、cross-merchant deny、admin allow、missing merchant deny、unknown role deny，且 denied tool read 不产生 `BusinessFactRefV1` 或 prompt-visible business facts。

11. **Unified API helper**: Order / RefundCase / Ticket API 必须使用统一 merchant access helper，而不是各自手写 role 条件。
   - Current: `orders.py`、`refund_cases.py`、`tickets.py` 各自实现 merchant 判断，语义已出现漂移。
   - Target: Phase 29.5 引入或指定统一 helper，例如 `require_merchant_access(user, merchant_id, resource_name)`。
   - Acceptance: 三个 API 路径均通过统一 helper 处理 merchant access，tests 证明 helper 语义覆盖 admin、merchant-bound、missing merchant、mismatch。

12. **API 403/404 semantics**: API 层必须区分 cross-tenant 与 same-tenant out-of-merchant-scope。
   - Current: tenant isolation tests 已要求跨 tenant order 返回 404；merchant mismatch 多数返回 403。
   - Target: cross-tenant resource 返回 404 以避免泄露存在性；same-tenant but out-of-merchant-scope 返回 403；non-admin `merchant_id is None` 返回 403；tenant 内不存在返回 404。
   - Acceptance: Tests 同时覆盖 cross-tenant 404 和 same-tenant cross-merchant 403，二者不能互相替代。

13. **Public policy scope remains tenant-level**: 平台公共政策读取不得被 business merchant scope 错误过滤。
    - Current: policy documents 按 tenant 存储，未建 merchant-specific policy 维度；KnowledgeContext 携带 merchant scope。`src/knowledge/service.py` 目前对空 `merchant_scope` 直接返回 no evidence，这会在 Phase 29.5 把缺 `merchant_id` 的普通业务用户改成 deny-all business scope 后误拒 tenant public policy。
    - Target: tenant public policy retrieval 是 policy-only path，要求 trusted tenant identity 和 `knowledge:read` / `tool:search_policy`，不要求 wildcard merchant scope；`merchant_scope=[merchant_id]` 或 deny-all business scope `[]` 不得自动阻断 authenticated tenant public policy retrieval。Future merchant-specific policy 必须单独引入 policy scope。
    - Acceptance: Knowledge/search tests 覆盖 support / manager 可读 tenant public policy；missing merchant 但有 `knowledge:read` 的 policy-only read 仍可用；同一用户对 business-scoped policy filter 或 business data 请求仍被拒；request body / LLM payload 不能扩大 policy 或 merchant scope。

14. **BusinessFact no-leak handoff**: Phase 29.5 必须区分 API HTTP 语义与 Phase 30 service/tool no-leak 语义。
    - Current: API 可以对 same-tenant out-of-merchant-scope 返回 403；BusinessFactService 尚未实现。
    - Target: Phase 29.5 的 interim tool guard 必须阻止显然越权的 raw business read 并避免发出 `BusinessFactRefV1`；Phase 30 的 `BusinessFactResultV1.permission_denied` 不得泄露资源是否存在；API helper 的 403/404 语义不得直接传播为 agent graph/tool/final response 的存在性信号。
    - Acceptance: Phase 29.5 tests 覆盖 denied raw tool read 不产生 business refs；SPEC/ROADMAP 要求 Phase 30 plan 验证 permission_denied no-leak、scope pass 前不发 `BusinessFactRefV1`、final response 不推断越权资源存在。

15. **ToolPlatform domain scope handoff**: Phase 30 必须把 ToolPlatform 的 domain scope marker 转成强制业务归属证明。
    - Current: ToolPolicyEngine 对 `order_no` / `refund_case_no` / `ticket_id` 只能标记 `requires_domain_scope_check`，不能证明 merchant ownership。
    - Target: 任何产生 `BusinessFactRefV1` 的 order/refund/ticket read，在 domain ownership proof 通过前不得返回 ok/success，不得写 business refs，不得写 prompt summary。
    - Acceptance: ROADMAP Phase 30 success criteria 和 deferred todo 要求 `requires_domain_scope_check` 由 BusinessFactService 消化，不停留在 marker。

16. **Seed/demo alignment**: Demo 数据必须体现一个 tenant 下多个 merchant，每个至少有可测试的 support + manager 账号。
    - Current: demo 里 support / manager 多数未绑定 merchant，legacy merchant users 承担商家侧测试。
    - Target: 至少两个 merchant 各有一组 `support` + `manager`，`admin_user` 不绑定 merchant 并作为 platform admin，legacy `merchant` 只保留兼容样例。
    - Acceptance: `scripts/seed_demo.py` 和 `tests/conftest.py` 中的测试数据可覆盖 merchant A allow、merchant B deny、admin cross-merchant allow。

17. **Approval / AgentRun deferred risk is explicit**: Phase 29.5 不完整改造 AgentRun / Approval / ActionDraft 的最终 target merchant binding，但必须提供 interim guards 并记录目标 phase。
    - Current: `APPROVAL_ROLES={"admin","manager"}`，pending approval 列表按 tenant 查询；agent run trace supervisors 包含 `manager`；approval resume 可注入 wildcard server scope；`src/agent/nodes/investigate.py` 还存在不经过 `TrustedContextFactory` 的 `merchant_scope={"merchant_ids":["*"]}` fallback。
    - Target: Phase 29.5 明确最终 binding deferred，但现有 manager tenant-wide visibility、wildcard resume、以及 factory 外部硬编码 wildcard 不能保持静默 active；不满足 interim guard 的路径必须 fail closed 或限制为 admin-only。
    - Acceptance: SPEC 和 deferred todo 文件列出 interim guard、目标 phase 和 required outcome；tests 或 static guard 覆盖 `create_from_request` 之外不得继续构造业务数据 wildcard merchant scope。

18. **BusinessFactService handoff**: Phase 30 必须消费本 phase 的 merchant scope 语义。
    - Current: Phase 30 尚未规划，BusinessFactService 目标仅概括当前业务事实权威入口。
    - Target: Phase 30 plan 必须让 BusinessFactService 用 trusted `tenant_id + merchant_scope + permissions + role` 做 order / refund / ticket scope check 和 domain ownership proof。
    - Acceptance: ROADMAP Phase 30 success criteria 引用 Phase 29.5 merchant scope semantics，并要求 `permission_denied` 不泄露资源存在性。

19. **No schema hardening in this phase**: Phase 29.5 不做数据库大迁移，但必须路由硬化工作。
    - Current: 表结构足以表达目标模型，但没有 DB-level role constraints、RLS、merchant_id denormalization。
    - Target: `users.merchant_id` 约束、`username` 唯一约束调整、RLS、role cleanup、merchant-specific policy 等进入 Phase 36+ deferred work。
    - Acceptance: SPEC 和 deferred todo 明确这些不阻塞 v1.9 主链路，但不得被遗忘。

## Boundaries

**In scope:**
- 写清并锁定 `tenant` / `merchant` / `user` 的目标产品身份模型。
- 定义 `merchant_bound_roles = {"support", "manager", "merchant"}` 与 `platform_admin_roles = {"admin"}`。
- 明确 legacy `merchant` role 兼容期按 `support` 处理，不作为推荐主路径。
- 收敛 `TrustedContextFactory` 的 merchant scope 生成规则。
- 收紧 `server_merchant_scope`，禁止 non-admin human actor 通过 server override 获得 wildcard。
- 同步 `docs/contract-spec.md`，把 role-to-merchant-scope policy 作为 normative contract delta，并修正/覆盖与 MER-01 冲突的旧 contract 语义。
- 清理或封堵 `TrustedContextFactory` 外部硬编码 `merchant_scope={"merchant_ids":["*"]}` 的业务数据 fallback。
- 引入或指定 Order / RefundCase / Ticket API 的统一 merchant access helper。
- 为 manager approval queue / resume 与 AgentRun status/evidence/trace visibility 增加 Phase 29.5 interim guard。
- 调整 seed/demo 与测试 fixture，使至少两个 merchant 具备 `support` + `manager`。
- 补齐 Order / RefundCase / Ticket 的 merchant isolation tests 与 tenant isolation regression。
- 明确 tenant public policy scope 与 business merchant scope 不同。
- 修正 tenant public policy 检索路径，避免 `merchant_scope=[]` 的 authenticated `knowledge:read` 用户被误判为 no evidence，同时保持 business-scoped filter / business data deny。
- 将 AgentRun / Approval / ActionDraft / Memory / Replay / DB hardening 的 deferred routing 写入 SPEC、ROADMAP 和 `.planning/todos/deferred/`。

**Out of scope:**
- PostgreSQL RLS — 属于 Phase 36+ 数据库强隔离硬化，不阻塞当前 MVP。
- 删除 `Tenant` 表或 `Merchant` 表 — 当前双层模型正是目标模型。
- 大规模数据库 schema 重构 — 当前字段足以支持 Phase 29.5 语义收敛。
- 删除 legacy `merchant` role — 兼容期保留，后续 Role Naming Migration 再处理。
- 引入 `agent` / `supervisor` / `merchant_admin` 新 role 名称 — 当前保留 `support` / `manager` / `admin`，降低改动面。
- 完整改造 AgentRun / Approval / ActionDraft / Memory / Replay target merchant binding — 必须记录 deferred risk，由 Phase 30-35 接住；但 Phase 29.5 必须先加 interim guard，不能继续保留 manager tenant-wide visibility 或 non-admin wildcard resume。
- 重写所有 repository — Phase 30 先在 BusinessFactService 主路径下沉 business fact scope。
- 商家级 policy document 完整模型 — 当前只保证 tenant public policy 不被误过滤。
- 用户管理后台、商家配置后台、真实 SaaS SSO — 不属于 v1.9 平台边界主线。

## Constraints

- Phase 29.5 必须保持 Phase 29 Tool Platform Boundary 的机制成果，不返工 `ToolDescriptor` / `ToolView` / `ToolPolicyDecision` / projection 框架。
- Phase 29.5 不得新增新的 wildcard merchant scope 扩权路径，也不得保留 `TrustedContextFactory` 外部的业务数据 wildcard fallback。
- Phase 29.5 不得让 public policy retrieval 因普通业务用户的 non-wildcard merchant scope 被错误拒绝。
- `create_from_request(user=...)` 不授权 system-owned internal job wildcard scope；任何 system wildcard 必须等单独 `TrustedSystemContext` / actor type / reason code / decision event contract。
- `manager` 在 Phase 29.5 后不再是 tenant-wide supervisor；没有 target merchant binding 的 business run/evidence/trace 只能 owner 或 `admin` 访问。
- `manager` approval list/get/decide 在 Phase 29.5 必须 fail closed 或限制为 admin-only，不能继续 tenant-wide；本 phase 不采用 `requested_by -> user.merchant_id` approximation。
- 后续 plan-phase 必须保留 tenant isolation 与 merchant isolation 两套测试；merchant isolation 不替代 tenant isolation。
- Repository 不应理解完整 agent context；service 层解析 `MerchantScopeV1`，repository 接收已解析的数据库过滤条件。
