## User Constraints (from CONTEXT.md)

### Locked Decisions

Phase 29.5 aligns MOCA's single-tenant MVP identity and business-data authorization model before Phase 30 BusinessFactService planning.

The phase makes `support`, `manager`, and legacy `merchant` merchant-bound business users; keeps `admin` as the only platform-wide human business-data role; preserves tenant public policy retrieval for authenticated business users; and adds interim guards for approval, run, trace, graph, memory, and wildcard-scope risks without completing the later target merchant binding work.

**Implementation Decisions**

- **D-01:** Put the unified merchant access helper in `src/auth/permissions.py`.
  - Rationale: this keeps the helper next to `get_current_user` and `require_roles`, lets `orders.py`, `refund_cases.py`, and `tickets.py` reuse it directly, and avoids creating a heavier domain authorization module in a scope-alignment phase.
- **D-02:** The helper should express the locked API semantics:
  - `admin` allows cross-merchant business-data access.
  - `support`, `manager`, and legacy `merchant` require `user.merchant_id`.
  - Missing `merchant_id` for merchant-bound users returns/raises 403.
  - Same-tenant but out-of-merchant-scope returns/raises 403.
  - Cross-tenant remains a repository/API not-found 404 path and must not be converted into a merchant-scope 403.
- **D-03:** Planner should keep route handlers thin: fetch by `tenant_id`, derive the target `merchant_id`, then call the helper before returning business data.
- **D-04:** `TrustedContextFactory.create_from_request(...)` should raise `ValueError` when a non-admin human actor receives wildcard `server_merchant_scope`.
  - Rationale: `src/platform` should not depend on FastAPI `HTTPException`; API or graph callers can translate `ValueError` into a safe 403/fail-closed path where needed.
- **D-05:** The role matrix is locked:
  - `support` / `manager` / legacy `merchant` with `merchant_id` -> `merchant_scope=[merchant_id]`.
  - `support` / `manager` / legacy `merchant` without `merchant_id` -> `merchant_scope=[]`.
  - `admin` -> `merchant_scope=["*"]`.
  - Unknown roles -> deny-all business scope unless explicitly classified later.
- **D-06:** `server_tool_permissions` may add trusted tool permission such as approval resume action-draft permission, but it must not affect `merchant_scope`.
- **D-07:** Tests should assert reject-not-narrow for non-admin wildcard override. Silent narrowing is explicitly rejected.
- **D-08:** Fix `KnowledgeService` by moving the empty-scope early return so policy-only tenant public policy search can proceed for authenticated users with `knowledge:read`.
  - Rationale: current `src/knowledge/service.py` treats empty merchant scope as no evidence, which would incorrectly block tenant public policy after Phase 29.5 changes unbound merchant-bound users to `merchant_scope=[]`.
- **D-09:** Empty business merchant scope remains deny-all for business data and business-scoped / merchant-specific policy filters.
- **D-10:** Do not fully ignore merchant scope in knowledge search. The plan should preserve a clear hook for future merchant-specific policy filtering.
- **D-11:** Implement manager approval interim as admin-only / fail-closed.
  - `manager` cannot list/get/decide approvals in Phase 29.5.
  - `admin` remains allowed.
  - Phase 29.5 must not implement `requested_by -> user.merchant_id` as a temporary authorization approximation.
  - Phase 34 restores manager same-merchant approval once ApprovalRequest / ActionDraft has target merchant or scoped `BusinessFactRefV1` binding.
- **D-12:** Implement this by removing `manager` from `APPROVAL_ROLES`, not by keeping the role and hand-writing per-endpoint denials.
  - Rationale: one role set change is clearer and less leak-prone.
- **D-13:** Approval resume cannot create wildcard merchant scope for non-admin human actors. `ACTION_DRAFT_PERMISSION` may still be injected through `server_tool_permissions`, but merchant scope must come from the authenticated actor and role rules.
- **D-14:** AgentRun / trace business-data visibility should be owner/admin-only until Phase 32/35 can prove target merchant or scoped business refs.
- **D-15:** `SUPERVISOR_ROLES` in `src/api/routers/traces.py` and `src/api/routers/agent_runs.py` must no longer grant business-data visibility to `manager`, `supervisor`, or `approval_manager`. Ghost roles should be removed or rendered ineffective for this path.
- **D-16:** `src/agent/nodes/investigate.py` missing trusted config must fail closed instead of fabricating `merchant_scope={"merchant_ids":["*"]}`.
  - Preferred behavior: no visible tools / no business tool execution when trusted tool context cannot be built.
  - Do not use a special graph fallback that couples graph fail-closed behavior to KnowledgeService policy-only behavior.
- **D-17:** Migration order should be fixtures/seed first, then production code, then old test expectation updates.
  - Rationale: support/manager users are currently often unbound; binding test users first makes subsequent failures represent real permission behavior rather than fixture noise.
- **D-18:** Seed/demo and test fixtures should include at least two merchants, each with `support` and `manager`, plus an unbound `admin` and a small number of legacy `merchant` compatibility users.
- **D-19:** Existing tests that assert support/manager wildcard behavior must be rewritten. Examples include `tests/platform/test_trusted_context_factory.py` assertions for non-merchant `["*"]`.
- **D-20:** Old happy-path tests should be sorted into three buckets:
  - Keep as same-merchant allow.
  - Change actor to `admin` when cross-merchant visibility is intended.
  - Change expected result to 403 when same-tenant cross-merchant access is now forbidden.
- **D-21:** Add a static or grep-backed regression that business-data code paths outside `TrustedContextFactory` do not fabricate `merchant_ids=["*"]`.

## Architecture Patterns

### System Architecture Diagram

```text
Authenticated API request
  -> FastAPI Security(get_current_user, scopes=[...])
  -> User + verified_token_scopes from JWT/database
  -> TrustedContextFactory
       -> role matrix:
          admin -> merchant_scope ["*"]
          support/manager/merchant + merchant_id -> [merchant_id]
          support/manager/merchant missing merchant_id -> []
          unknown role -> []
       -> optional server_tool_permissions only adds tool permissions
       -> optional server_merchant_scope may only narrow; non-admin wildcard raises ValueError
  -> Projection / route decision
       -> Order/Refund/Ticket API:
          fetch by tenant_id -> if missing 404 -> require_merchant_access -> same-tenant mismatch 403
       -> Knowledge policy-only:
          require tenant + knowledge permission -> allow tenant public policy even with [] -> deny explicit merchant/business filters
       -> Approval:
          APPROVAL_ROLES={"admin"} -> manager denied -> resume uses actor scope, not wildcard
       -> AgentRun/Trace:
          fetch by tenant_id -> owner or admin -> otherwise 403
       -> Investigate:
          missing/invalid trusted_context -> no visible business tools / no execution
  -> Response / graph config / audit data with no new wildcard business scope
```

### Pattern 1: Deny-First API Merchant Helper

**What:** Add a single helper in `src/auth/permissions.py` that allows `admin`, requires `merchant_id` for `support` / `manager` / legacy `merchant`, rejects missing merchant binding, and rejects same-tenant mismatch with 403. [VERIFIED: 29.5-CONTEXT.md]

**When to use:** Use after the route has already fetched the resource by `tenant_id`, and before returning order/refund/ticket business data. [VERIFIED: 29.5-CONTEXT.md; src/api/routers/orders.py]

**Example:**

```python
# Source: 29.5-CONTEXT.md D-01..D-03; existing FastAPI HTTPException pattern in src/auth/permissions.py
MERCHANT_BOUND_ROLES = {"support", "manager", "merchant"}
PLATFORM_ADMIN_ROLES = {"admin"}


def require_merchant_access(user: User, merchant_id: object, resource_name: str) -> None:
    if user.role in PLATFORM_ADMIN_ROLES:
        return
    if user.role not in MERCHANT_BOUND_ROLES or user.merchant_id is None:
        raise HTTPException(status_code=403, detail={"code": FORBIDDEN, "message": "Insufficient permissions"})
    if str(user.merchant_id) != str(merchant_id):
        raise HTTPException(status_code=403, detail={"code": FORBIDDEN, "message": f"Cannot access this {resource_name}"})
```

### Pattern 2: Fetch By Tenant Before Merchant Check

**What:** Preserve tenant-not-found semantics by fetching through existing tenant predicates first, then apply merchant helper only when a same-tenant resource exists. [VERIFIED: 29.5-CONTEXT.md; src/api/routers/orders.py]

**When to use:** Use for order, refund case, and ticket endpoints. [VERIFIED: 29.5-SPEC.md]

**Example:**

```python
# Source: existing route shape in src/api/routers/orders.py plus 29.5-CONTEXT.md D-02
result = await repository.get_with_hints(order_no, user.tenant_id)
if result is None:
    raise HTTPException(status_code=404, detail={"code": ORDER_NOT_FOUND, "message": "Order not found"})
order = result["order"]
require_merchant_access(user, order.merchant_id, "order")
```

### Pattern 3: Trusted Context Role Matrix Is Central

**What:** `TrustedContextFactory` must derive business merchant scope from trusted `user.role` and `user.merchant_id`; no graph/request fallback should fabricate wildcard. [VERIFIED: docs/contract-spec.md; 29.5-CONTEXT.md]

**When to use:** Use in API run creation/streaming, approval resume, tools, and projection tests. [VERIFIED: src/api/routers/agent_runs.py; src/api/routers/approvals.py]

**Example:**

```python
# Source: docs/contract-spec.md §8.0.1 and src/platform/trusted_context.py
if role == "admin":
    base_scope = MerchantScopeV1(merchant_ids=["*"])
elif role in {"support", "manager", "merchant"}:
    merchant_id = getattr(user, "merchant_id", None)
    base_scope = MerchantScopeV1(merchant_ids=[str(merchant_id)] if merchant_id is not None else [])
else:
    base_scope = MerchantScopeV1(merchant_ids=[])
```

### Anti-Patterns to Avoid

- **Checking merchant before tenant fetch:** This can convert cross-tenant no-leak 404 into 403 and leak existence. [VERIFIED: 29.5-CONTEXT.md]
- **Leaving `manager` in `APPROVAL_ROLES`:** The locked interim is admin-only by removing `manager`, not per-endpoint special cases. [VERIFIED: 29.5-CONTEXT.md; src/api/routers/approvals.py]
- **Keeping `SUPERVISOR_ROLES` as a business-data visibility set:** `manager`, `supervisor`, and `approval_manager` must not provide tenant-wide business run/trace visibility. [VERIFIED: 29.5-CONTEXT.md; src/api/routers/agent_runs.py; src/api/routers/traces.py]
- **Using `merchant_scope=[]` as no policy evidence:** Empty business scope remains valid for policy-only tenant public policy retrieval when authenticated and authorized. [VERIFIED: docs/contract-spec.md; 29.5-CONTEXT.md]
- **Fabricating `{"merchant_ids":["*"]}` outside factory:** Current sites exist in `investigate.py`, approval resume tests, and eval scripts; production business-data fallback must fail closed. [VERIFIED: codebase grep]

## Common Pitfalls

### Pitfall 1: Fixture Noise Masks Authorization Behavior

**What goes wrong:** After changing `support`/`manager` to merchant-bound, old tests may fail because users are unbound rather than because authorization logic is wrong. [VERIFIED: 29.5-CONTEXT.md; tests/conftest.py]

**Why it happens:** Current seed and fixtures create support/manager users with `merchant_id=None`. [VERIFIED: scripts/seed_demo.py; tests/conftest.py]

**How to avoid:** Plan fixture/seed updates first, then production logic, then expectation rewrites. [VERIFIED: 29.5-CONTEXT.md]

**Warning signs:** Many support/manager happy paths return 403 immediately after `TrustedContextFactory` changes. [VERIFIED: inference from current fixtures and locked matrix]

### Pitfall 2: Cross-Tenant 404 Becomes Same-Tenant 403

**What goes wrong:** A helper applied before tenant-scoped fetch can leak that a cross-tenant resource exists. [VERIFIED: 29.5-SPEC.md; 29.5-CONTEXT.md]

**Why it happens:** Merchant mismatch and missing tenant resource are both authorization-like failures unless the route preserves fetch order. [VERIFIED: src/api/routers/orders.py]

**How to avoid:** Always fetch by `tenant_id` first; only call helper after resource exists in same tenant. [VERIFIED: 29.5-CONTEXT.md]

**Warning signs:** Cross-tenant tests expecting 404 start returning 403. [VERIFIED: tests/test_trace_api.py; 29.5-SPEC.md]

### Pitfall 3: Approval Tightened But Trace/Run Backdoor Remains

**What goes wrong:** `manager` loses approval access but can still inspect another user's business run, evidence, trace, or replay through supervisor role sets. [VERIFIED: 29.5-DISCUSSION-LOG.md; src/api/routers/agent_runs.py; src/api/routers/traces.py]

**Why it happens:** `APPROVAL_ROLES` and `SUPERVISOR_ROLES` are separate constants in different routers. [VERIFIED: src/api/routers/approvals.py; src/api/routers/agent_runs.py; src/api/routers/traces.py]

**How to avoid:** Plan approval and run/trace interim guards together. [VERIFIED: 29.5-CONTEXT.md]

**Warning signs:** Tests for manager approval denial pass, but manager can still call `/agent-runs/{run_id}`, `/evidence`, `/trace`, or `/replay` for another user's run. [VERIFIED: current route code]

### Pitfall 4: Policy-Only Knowledge Gets Blocked By Business Scope

**What goes wrong:** Unbound merchant-bound users get `merchant_scope=[]`, and current `PolicyKnowledgeService.search` returns no evidence before checking whether the request is policy-only. [VERIFIED: src/knowledge/service.py]

**Why it happens:** The current service treats empty merchant scope as a universal no-evidence condition. [VERIFIED: src/knowledge/service.py; tests/knowledge/test_service.py]

**How to avoid:** Move the empty-scope early return so tenant public policy retrieval can proceed when authenticated and authorized, while explicit merchant/business filters still deny. [VERIFIED: 29.5-CONTEXT.md; docs/contract-spec.md]

**Warning signs:** Existing `test_missing_or_empty_merchant_scope_returns_no_evidence_without_adapter_call` must be split/replaced by policy-only allow and business-scoped deny tests. [VERIFIED: tests/knowledge/test_service.py]

### Pitfall 5: Static Wildcard Regression Over-Matches Legitimate Tests

**What goes wrong:** A grep-backed wildcard check may fail on admin tests, projection tests, eval scripts, or explicit negative cases. [VERIFIED: codebase grep]

**Why it happens:** Wildcard is still valid for admin and for some low-level contract tests; the phase only forbids business-data wildcard construction outside `TrustedContextFactory` / future trusted system context. [VERIFIED: docs/contract-spec.md; 29.5-CONTEXT.md]

**How to avoid:** Make the static regression precise: production business-data fallback paths must not fabricate wildcard; tests may use wildcard when naming admin/contract/negative cases. [VERIFIED: codebase grep]

**Warning signs:** The static test blocks `tests/platform/test_context_projections.py` or admin-only fixtures instead of production fallback sites such as `investigate.py` and approval resume. [VERIFIED: codebase grep]
