# Phase 64.4: Token-Aware Policy Chunking And Reindex Validation - Context

**Gathered:** 2026-08-11
**Status:** Ready for planning

<domain>
## Phase Boundary

Replace character-count policy chunk sizing with one versioned, tokenizer-aware assembly contract that measures the exact final `text-embedding-v4` input. The contract must preserve parser structure and provenance, remain deterministic, coexist safely with Phase 64.2 immutable evidence/replay semantics, and support an isolated, resumable, rollback-safe reindex. Prove the candidate against the sealed Phase 64.3 format-parity baseline before cutover.

This phase owns the embedding-model tokenizer/counting contract, final-input-aware block/table/oversized/overlap assembly, production/dry-run/golden path convergence, configuration and token-count provenance, identity compatibility, reindex lifecycle, and character-versus-token A/B selection. It does not redesign parsers, hybrid retrieval, RRF, query rewrite, reranking, `ContextBuilder`, claim verification, the embedding model, or Phase 69 generation-model prompt budgets; it also does not add an LLM clause classifier or parent-child chunking.

</domain>

<decisions>
## Implementation Decisions

### Tokenizer ownership, parity, and failure semantics
- **D-01:** Define one versioned model-to-tokenizer/counting contract. The configured embedding model, tokenizer implementation and version, normalization/special-token settings, and count-contract version form an explicit immutable configuration rather than ambient library behavior.
- **D-02:** The offline deterministic counter is the authoritative preflight and assembly counter. Research must establish the provider-supported tokenizer/counting method for `text-embedding-v4`; the implementation must not guess an undocumented model mapping.
- **D-03:** Add a provider-backed parity check over safe synthetic probes and the exact submitted input boundary. Compare offline counts with provider-reported usage using a documented, versioned comparison rule. If the provider does not expose usable per-input accounting, record parity as `unavailable` with evidence rather than fabricating success.
- **D-04:** Unknown model/tokenizer/configuration, tokenizer load/count failure, non-deterministic results, and inputs that cannot be assembled within the hard bound fail closed before embedding or persistence. Production must not silently fall back to character sizing. The old character path may exist only as an explicit compatibility/A-B candidate, never as an automatic fallback.
- **D-05:** Research/planning fixes the actual max/target/overlap token values from provider limits and measured envelope behavior before implementation. Values, rationale, and safety margin are versioned; they are not tuned after seeing the final A/B result merely to turn a gate green.

### Exact final-input assembly and structural preservation
- **D-06:** The token budget applies to the exact string sent to the embedding provider, including title, section path, repeated table headers, overlap, and allowed source-block context. Nothing may be appended after the authoritative token count.
- **D-07:** One authoritative assembler returns the canonical citation content and provenance together with the exact embedding input, token count, and configuration identity. The embedder consumes that exact returned input; it must not reconstruct or decorate it independently.
- **D-08:** The hard maximum is inviolable. Split in deterministic structural order: parsed block boundaries, table rows, sentence/clause boundaries, then a tokenizer-window split for a single unpunctuated oversized unit. Never silently truncate user-visible evidence, table headers, protected values, or source references.
- **D-09:** Preserve table header repetition and row integrity whenever a row fits. An oversized single row/cell is split deterministically while retaining row/header provenance so reconstruction and citation remain explainable.
- **D-10:** Overlap is measured in tokenizer tokens and is charged inside the same final-input budget. The algorithm must prove forward progress and stable ordering, including zero-content, envelope-dominant, and unpunctuated inputs; identical source plus identical configuration produces byte-identical chunks and embedding inputs.

### Authoritative path convergence and compatibility
- **D-11:** Production ingestion, CLI dry-run, golden/fixture validation, tokenizer parity probes, and Phase 64.3 A/B evaluation call the same authoritative parsed-block assembly boundary. Tests may inject deterministic tokenizer/embedder fakes but may not implement a second chunking algorithm.
- **D-12:** Legacy `chunk_markdown` becomes either a thin adapter into parser-compatible blocks and the shared assembler or an explicitly named read-only character-baseline adapter. It cannot remain an independent production-capable algorithm.
- **D-13:** Preserve the separation between canonical citation content, search text, and embedding input documented by the RAG architecture. Token-aware envelope changes must not silently change the displayed evidence text or parser provenance.
- **D-14:** Existing Phase 64.2 evidence and replay records remain readable exactly as written. Compatibility reads may resolve historical character-chunked material, but no new write may mint legacy or ambiguous identity.

### Configuration identity, reindex, cutover, and rollback
- **D-15:** Persist the chunker contract version, tokenizer identity/version/settings, embedding model/dimensions, max/target/overlap values, envelope/assembly version, configuration fingerprint, and actual final-input token count on the auditable current and immutable version surfaces used by ingestion, replay, and evaluation.
- **D-16:** Rechunking under an incompatible configuration must not silently reuse current document/chunk/evidence bindings. Reuse is allowed only when a versioned compatibility predicate proves canonical content, source, provenance, and configuration equivalence; otherwise create a new immutable version while retaining historical resolution.
- **D-17:** A reindex run is bound to a fixed tenant, source set, run ID, and configuration fingerprint. It stages a complete candidate corpus outside the active view, is resumable/idempotent at a documented checkpoint boundary, and refuses resume under drifted source or configuration.
- **D-18:** Failures leave the prior active corpus usable and the candidate visibly incomplete; no query may observe a partially mixed old/new corpus. Candidate cleanup is allowlisted and tenant/run scoped, preserving immutable evidence needed by historical replay.
- **D-19:** Cutover happens only after completeness, deterministic rebuild, identity/replay, token-bound, and evaluation gates pass. Reuse the Phase 64.2 rollout lock and compare-and-swap epoch pattern for one atomic active-version flip. Rollback flips to the prior complete version without deleting the failed/new immutable history.

### A/B selection and phase-completion gates
- **D-20:** Run the character incumbent and token-aware candidate over the same Phase 64.3 corpus, questions, provider/runtime configuration, and immutable manifest/Gold hashes in isolated namespaces. The report records candidate configuration fingerprints and makes runs reproducible.
- **D-21:** Hard safety gates for the token-aware candidate are: no final-input overflow, deterministic rebuild, complete source coverage, no identity/replay regression, safe interrupted-resume behavior, atomic cutover/rollback, and evaluation cleanup isolation. Any hard-gate failure forbids selection.
- **D-22:** Before execution, planning versions explicit non-regression tolerances against the same-run character incumbent. Report Hit@1/3/5, MRR, anchor/fallback/locator coverage, format spread, duplicate rate, chunk count, latency, embedding tokens, and estimated/observed cost. Existing Phase 64.3 target gates remain visible but are not silently redefined to compensate for parser/retrieval failures outside this phase.
- **D-23:** Select and cut over only a token-aware configuration that passes all hard safety gates and the fixed non-regression profile. If the candidate fails, keep the character corpus active, emit a truthful failed-candidate report, and iterate only token-aware sizing/assembly parameters inside this phase. Unlike Phase 64.3's measurement baseline, Phase 64.4 is not complete until a token-aware configuration passes its selection contract.
- **D-24:** Missing provider credentials/service or missing usage accounting is `unavailable`, not pass or quality failure. CI-safe deterministic contract tests remain mandatory; the provider-backed final A/B artifact must state prerequisites and execution evidence explicitly.

### the agent's Discretion
- Exact module/class/schema/table/index names, tokenizer adapter interface, safe synthetic parity corpus, reason-code spelling, and report layout, within the locked contracts above.
- Exact token limits, target size, overlap, safety margin, and non-regression tolerances after official provider research and pre-execution baseline analysis.
- Migration and candidate-version representation, provided immutable replay, atomic active selection, resumability, and tenant/run isolation are demonstrably preserved.
- Dependency-ordered wave composition, subject to the hard granularity rule: tokenizer contract/parity, final-input assembly/path convergence, persistence/reindex compatibility, and A/B/cutover/closeout must be separate numbered plans. A single catch-all plan is a planning blocker.

</decisions>

<code_context>
## Existing Code Insights

### Current gaps
- `src/rag/chunker.py` currently enforces `max_chars`, `target_chars`, and character overlap in both `chunk_blocks` and `chunk_markdown`; table-header repetition and oversized splitting are also character-based.
- `src/rag/ingestion.py` calls `chunk_blocks` and then appends title, section, and `source_block_id` context in `_embedding_text`, so current budgets do not measure the final provider input.
- `src/rag/embedder.py` submits `text-embedding-v4` batches through the DashScope OpenAI-compatible API but discards response usage accounting.
- `scripts/ingest_policies.py` dry-run calls legacy `chunk_markdown`, while production parses blocks and calls `chunk_blocks`; these paths are not authoritative equivalents.
- Current persistence/evaluation surfaces do not record the full chunker/tokenizer configuration or per-final-input token counts.

### Reusable assets and established patterns
- Parser `ParsedBlock` structure and provenance, existing table header repetition, source-block IDs, and stable ordering are reusable inputs; the new assembler should replace sizing without redesigning parsers.
- Phase 64.2 provides immutable document/chunk versions, exact evidence identity/replay, current-head selection, rollout locking, and compare-and-swap epoch patterns that reindex must extend rather than bypass.
- Phase 64.3 provides the fixed manifest/Gold, isolated evaluation tenant/round cleanup, provider-backed retrieval evaluator, canonical JSON/Markdown reporting, and metric calculations for same-run A/B comparison.
- Repository validation uses `UV_CACHE_DIR=/tmp/uv-cache uv run ...`; bare `pytest` or bare `python -m pytest` is invalid in this project.

### Planning hotspots
- Research must trace every current `chunk_blocks`, `chunk_markdown`, `_embedding_text`, evidence-version write/read, and active-head/cutover caller before choosing compatibility seams.
- Persistence changes likely span ORM/models, repositories, migrations, service orchestration, replay resolution, evaluator reports, and CLI tooling; migration order and rollback behavior need explicit plan-level verification.
- Provider usage may be batch-aggregate rather than per-input. The parity design must prove what the API actually reports and avoid inferring unsupported per-chunk counts.

</code_context>

<specifics>
## Specific Ideas

- Treat the final embedding string as a first-class immutable assembly result so no caller can add uncounted context.
- Preserve Phase 64.3 semantic Gold precisely because chunk IDs and boundaries are expected to change.
- Keep safety gates binary and selection tolerances versioned before the final provider run; a report can truthfully show remaining parser/retrieval target misses without redefining them as chunking failures.

</specifics>
