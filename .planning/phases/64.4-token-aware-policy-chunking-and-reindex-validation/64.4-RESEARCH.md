# Phase 64.4: Token-Aware Policy Chunking And Reindex Validation - Research

**Researched:** 2026-08-11
**Status:** Complete
**Question:** What do we need to know to plan Phase 64.4 well?

## Executive Summary

Phase 64.4 is feasible without changing the embedding model or Phase 64.2 evidence schema, but it is not a local `len(text) -> token_count(text)` replacement. The implementation has four coupled boundaries:

1. a pinned offline tokenizer contract whose exact service compatibility is empirically approved and continuously drift-gated;
2. one assembler that owns the final string submitted to `text-embedding-v4` and enforces its budget before any provider call;
3. an index-generation boundary that permits inactive candidate chunks to coexist with the active corpus and makes the active generation a tenant-scoped CAS pointer;
4. a same-run character/token A/B evaluator that reuses Phase 64.3 semantic Gold and selects only a safety-clean, non-regressing token configuration.

The most important provider finding is nuanced. Alibaba Cloud documents the `text-embedding-v4` limits and usage fields, but does not publish the service's exact offline tokenizer mapping. A safe synthetic provider experiment in this worktree established an exact 10/10 match between the pinned official `Qwen/Qwen3-Embedding-0.6B` tokenizer, including its EOS post-processor, and single-input DashScope `prompt_tokens`. That is sufficient for a versioned **empirically provider-parity-approved** mapping, not permission to claim an Alibaba-guaranteed mapping. Any asset or provider drift must quarantine new token-aware writes and cutover.

The first-pass research grouped the work into six boundaries, but plan checking showed that schema/bootstrap, active-path migration, reindex lifecycle, activation, and provider selection each need their own execution unit. Planning must therefore split those boundaries further rather than use six catch-all plans.

## Official Provider Facts And Tokenizer Evidence

### Documented facts

- Alibaba Cloud lists `text-embedding-v4` as part of the Qwen3-Embedding family, with 64-2048 output dimensions (1024 default/current MOCA value).
- One input is limited to **8,192 provider tokens**; one synchronous request accepts at most **10 inputs**.
- The OpenAI-compatible response exposes request-level `usage.prompt_tokens` and `usage.total_tokens`. The native response exposes request-level `usage.total_tokens`. Neither is documented as a per-input array.
- The documented usage value is the count calculated by the model tokenizer. There is no documented token-count-only endpoint.
- Current Alibaba Cloud API/SDK documentation does not publish an offline tokenizer asset, immutable model-to-tokenizer revision, or compatibility guarantee for `text-embedding-v4`.

## Current Repository Truth

### Chunking and final-input divergence

- `src/rag/chunker.py` owns two character-based algorithms. `chunk_blocks` preserves parser blocks/provenance and table headers; `chunk_markdown` is the legacy Markdown path. Both use `max_chars=1200`, `target_chars=800`, `overlap_chars=100` and character/punctuation splitting.
- `src/rag/ingestion.py` calls `chunk_blocks`, then `_embedding_text` appends title, section, and `source_block_id=...` lines. The string actually submitted to the provider is therefore larger than the string bounded by the chunker.
- `scripts/ingest_policies.py` dry-run calls `chunk_markdown`, not the parsed-block production path.
- `src/rag/embedder.py` batches up to 10 inputs and returns vectors only. It currently discards provider usage, so Phase 64.3 correctly recorded `embedding_tokens_status: unavailable`.

### Persistence, identity, and replay

- `src/db/models.py` stores the mutable retrieval projection in `policy_documents`, `document_blocks`, and `policy_chunks`. `PolicyChunk` stores citation content, `search_text`, provenance refs, and the 1024-dimensional embedding, but no chunker/tokenizer/config identity or token count.
- Phase 64.2 migrations `025_phase64_2_immutable_evidence.py` and `026_phase64_2_evidence_cutover.py` added append-only `policy_document_versions`, `policy_chunk_versions`, snapshot dependencies, a rollout lock, write-sequence reconciliation, and canonical-read CAS activation.
- `src/repositories/evidence_version_repo.py` is the authority for exact immutable binding, writer rollout locking, backfill, reconciliation, and current identity lookup. Compatibility reuse currently proves content/provenance identity but does not know a chunking configuration fingerprint.
- `src/knowledge/evidence_identity.py` mints `evidence_identity.v1` from persisted immutable material. Phase 64.4 should not create a new evidence schema merely because chunk boundaries change. It should increment/create immutable chunk versions and include the chunk-config compatibility predicate before binding reuse.
- Historical replay reads retained `policy_chunk_versions`; current retrieval reads `policy_chunks`. New fields and joins must not make legacy immutable rows unreadable.

### Retrieval and evaluation

- `src/repositories/policy_chunk_repo.py` and the hybrid retrieval path query all `policy_chunks` for a tenant. Candidate generations cannot be placed there safely until every current-read query filters through one active corpus pointer.
- Phase 64.3 provides a fixed three-policy/nine-fixture manifest, chunk-ID-independent semantic Gold, isolated format rounds, provider-backed retrieval, strict cleanup ownership, and canonical JSON/Markdown reporting.
- The sealed baseline is `completed_quality_fail`, but retrieval Hit@5 (`0.977778`) and cross-format Hit@5 spread (`0.066667`) already pass their targets (`>=0.90`, `<=0.10`). Parser/locator failures are outside Phase 64.4.
- The baseline's overall retrieval values are Hit@1 `0.844444`, Hit@3 `0.933333`, Hit@5 `0.977778`, MRR `0.900000`, semantic anchor coverage `0.211111`, locator coverage `0.333333`, fallback correctness `0.851852`; there are 45 answerable and 54 total retrieval cases.

## Recommended Tokenizer Contract

Add an exact runtime dependency on `tokenizers==0.23.1` and vendor the approved `tokenizer.json` plus a small `SOURCE.json`/license notice. Runtime must never download tokenizer material. Load and hash the asset at startup; mismatch is a typed configuration error.

Recommended immutable contract `embedding_tokenizer.v1`:

```json
{
  "schema_version": "embedding_tokenizer.v1",
  "provider": "dashscope",
  "model": "text-embedding-v4",
  "dimensions": 1024,
  "tokenizer_source": "Qwen/Qwen3-Embedding-0.6B",
  "tokenizer_revision": "97b0c614be4d77ee51c0cef4e5f07c00f9eb65b3",
  "tokenizer_asset_sha256": "def76fb086971c7867b829c23a26261e38d9d74e02139253b38aeb9df8b4b50a",
  "tokenizer_runtime": "tokenizers==0.23.1",
  "add_special_tokens": true,
  "provider_max_input_tokens": 8192,
  "max_embedding_tokens": 512,
  "target_embedding_tokens": 384,
  "overlap_tokens": 48,
  "assembly_schema_version": "policy_embedding_input.v1"
}
```

Sizing recommendation: **512 hard / 384 target / 48 overlap tokens**. This is a planning recommendation, not a provider requirement. It gives 16x distance from the provider's 8,192-token rejection boundary, keeps a 12.5% overlap ratio, and normalizes the current language-dependent character budgets. The approved final A/B configuration must use these values; any later tuning is a new fingerprint/report, not an unrecorded constant edit.

The configuration fingerprint is SHA-256 over canonical JSON with sorted keys and no ambient fields. The loader returns a frozen typed object plus fingerprint. Unknown model, asset mismatch, missing asset, runtime-version mismatch, non-integer/negative count, or parity quarantine raises an allowlisted typed error before provider or persistence work.

Provider parity contract:

- CI runs offline golden counts for the 10 locked probes and property/adversarial corpus.
- The provider command sends one probe per request, compares exact `prompt_tokens`, and records safe labels/counts, provider request IDs/hashes as allowed, model, asset/config fingerprints, timestamp, region/base URL classification, and result; it never records probe text, keys, or raw payloads.
- Activation requires all probes exact. Batch aggregation is separately checked by comparing one ten-input request's usage with the sum of offline counts, but single-input calls remain the per-probe authority.
- Any mismatch sets `provider_parity_status=quarantined`; token-aware ingestion/reindex/cutover fail closed. Current already-active reads remain available.

## Authoritative Final-Input Assembly

Create a typed assembly result rather than returning only `Chunk`:

```text
AssembledPolicyChunk
  chunk_id, section, citation_content, source_block_refs, ocr_metadata
  search_text
  embedding_input                 # exact provider string
  embedding_input_hash            # sha256 of exact string
  embedding_token_count
  chunking_config_fingerprint
```

One pure `PolicyEmbeddingInputAssembler` owns both chunk grouping and envelope rendering. `EmbeddingService.embed_texts` receives `embedding_input` values directly and must not add title/section/source context.

Deterministic assembly order:

1. Render the immutable envelope for a candidate body: first section is `"{title}: {content}"`; later sections are `"{title} / {section}: {content}"`; append sorted/deduplicated `source_block_id=...` lines exactly as production does today.
2. Count that exact string, including EOS. An empty/envelope-only unit is rejected with a typed reason rather than looping.
3. Accumulate whole parser blocks until adding the next block would exceed target 384. Emit the preceding non-empty candidate.
4. For tables, repeat the normalized header in every piece and accumulate whole rows. If one row is oversized, keep header/provenance and split the row deterministically.
5. Split an oversized non-table unit at paragraph/newline, then sentence/clause punctuation, then whitespace. If none yields a fitting unit, split by tokenizer token windows and decode only boundaries that round-trip to the exact original substring; a byte-offset map is required for Unicode correctness.
6. Apply at most 48 tokens of overlap from the prior **citation body**, re-render the full next envelope, and shrink overlap until the final count fits. Envelope/header/source context always wins over overlap.
7. Every loop must either consume source bytes/tokens or emit a chunk. Add explicit no-progress assertions and stable ordering.
8. Verify `count(embedding_input) == embedding_token_count <= 512` immediately before the provider call and again before persistence.

`chunk_markdown` becomes an explicit `character_baseline` adapter used only by A/B compatibility, or parses Markdown to production-compatible blocks then calls the assembler. It must not be a second token-aware implementation. Production, CLI dry-run, golden fixture checks, and A/B must call the same assembler.

## Configuration Provenance And Immutable Compatibility

Recommended auditable fields:

- On each mutable `policy_chunks` row: `corpus_version_id`, `chunking_config_fingerprint`, `embedding_input_hash`, `embedding_token_count`.
- On each `policy_chunk_versions` row: chunking configuration, exact-input hash/count, retained `search_text`, and retained embedding vector, but **not** rollout/corpus identity.
- On the mutable corpus projection: an explicit binding from `(tenant, corpus, current chunk)` to the reusable immutable chunk-version ID. Corpus identity controls visibility and activation provenance only; it is not part of `evidence_identity.v1` or immutable compatibility.
- On `rag_ingestion_jobs`: config fingerprint and count summary (`chunk_count`, min/max/total tokens) in typed columns or the existing safe `counts_json` only if schema validation locks the keys.
- In Phase 64.3/64.4 reports: full allowlisted config JSON, fingerprint, per-candidate aggregate tokens, and per-chunk safe counts/IDs without raw provider payloads.

Do not change `evidence_identity.v1`. Instead:

- exact compatibility reuse requires canonical source/document material, citation content/hash, ordered provenance refs, logical chunk identity, **and chunking config fingerprint** to match; a different corpus ID does not defeat reuse;
- a changed incompatible config creates a new immutable chunk version/binding even if a coincidental body string matches; an equivalent rebuild in another corpus reuses the same immutable row through the explicit projection binding;
- legacy immutable rows have `chunking_config_fingerprint=NULL` and remain compatibility-read-only;
- current identity lookup filters the active corpus generation first, then resolves its exact immutable binding;
- historical snapshots continue to resolve their stored immutable version IDs without active-generation filtering.

## Isolated Reindex And Corpus Activation

Use generation visibility rather than an in-place delete/reinsert. Add:

- `policy_corpus_versions`: tenant, run token, owner marker, config JSON/fingerprint, source-manifest hash, state, state version, lease, next document index, counts/proofs, validation report hash, terminal timestamps.
- `policy_corpus_rollouts`: one row per tenant, active corpus version, previous corpus version, rollout epoch, quarantine/drift fields, updated timestamp.
- `policy_chunks.corpus_version_id`: candidate and active chunks may coexist; unique `(tenant_id, doc_id, corpus_version_id, chunk_id)`.

Migration 030 must create one bootstrap `character.v1` corpus version and rollout row for every tenant with current RAG material, backfill all current chunks, add constraints/indexes, then make the FK non-null. A migration test must prove all legacy tenants get exactly one active bootstrap generation and no row becomes invisible.

All current retrieval/evidence/provenance/delete queries must join the tenant rollout and filter `active_corpus_version_id`. This includes dense, sparse/fuzzy, canonical evidence lookup, provenance lookup, ingestion replacement, evaluation cleanup, and repository test fakes. A static architecture test should reject a direct production `select(PolicyChunk)` that lacks the active-generation helper, with allowlists only for migration/reindex/history code.

Recommended build-state machine:

```text
claimed -> building -> built -> validating -> ready
                   \-> failed         \-> failed
```

`active` is derived exclusively from the tenant rollout pointer, not from a terminal corpus-state transition. Every pointer flip appends an immutable activation-history row/receipt. This lets the same complete corpus be selected, rolled back from, and restored without an impossible `superseded -> active` mutation while the CAS pointer still guarantees exactly one active corpus.

- Claim fixes tenant, allowlisted doc keys/source checksums, source-manifest hash, config fingerprint, expected evidence rollout epoch, run token, and lease.
- Resume locks the owner row, validates state/lease/CAS, and refuses changed source manifest, config, tenant, owner, or rollout epoch.
- Each document build is idempotent under `(corpus_version_id, doc_key)` and advances progress only after all chunks, embeddings, immutable bindings, and counts commit.
- Candidate chunks are never visible because the rollout pointer still names the old corpus.
- Pre-selection validation proves complete doc coverage, zero overflow, deterministic rebuild hash, immutable replay, and cleanup isolation, but may remain pending final A/B evidence.
- Cutover locks `policy_corpus_rollouts` and the Phase 64.2 evidence rollout in a fixed order, checks both epochs and zero drift, then changes exactly one active pointer and increments epoch in one transaction.
- Rollback and restoration perform the same CAS pointer flip between complete `ready` corpora. They never delete the new immutable history and each append an activation-history receipt.
- If source content changed after cutover, the prior corpus is marked source-stale and a direct flip is refused; rebuild current sources under the prior config as a new complete candidate before rollback. This avoids silently restoring obsolete policy content.
- Candidate cleanup is tenant/run/owner allowlisted and may remove only unselected mutable candidate rows after retention; immutable rows referenced by snapshots are never deleted.

## A/B Selection Contract

The A/B command must run the character incumbent and token candidate over identical Phase 64.3 manifest/Gold hashes, provider/runtime config, questions, and isolated evaluation ownership. The same new tokenizer measures both candidates, so character-baseline embedding tokens are no longer `unavailable`.

Hard token-candidate gates:

- overflow count `== 0`; all persisted counts recompute exactly;
- deterministic rebuild hash identical across two builds;
- source/document coverage exact; no mixed active generation;
- immutable evidence/replay and rollback tests green;
- interrupted resume and stale-CAS probes green;
- evaluation cleanup isolation green;
- provider parity status `passed` for the pinned contract at final run time.

Predeclared quality/operational profile `rag_token_chunk_ab.v1`:

| Metric | Selection gate |
|--------|----------------|
| Hit@5 | candidate `>= max(0.90, incumbent)` |
| Cross-format Hit@5 spread | candidate `<= min(0.10, incumbent + 0.00)` |
| Hit@1, Hit@3, MRR | candidate no more than exact rational `1/45` absolute below incumbent |
| Per-format Hit@5 | candidate no more than exact rational `1/15` below incumbent in any format |
| Anchor, locator, fallback coverage | candidate no more than exact rational `1/54` absolute below incumbent |
| Duplicate rate | candidate `<= incumbent + 0.02` absolute |
| Chunk count | candidate `<= 1.50 * incumbent` |
| Total embedding tokens | candidate `<= 1.25 * incumbent` |
| Provider retrieval duration | report paired values and percent delta; no hard gate because live-provider latency is externally noisy |

These are Phase 64.4 selection gates, not replacements for Phase 64.3 parser/retrieval target profiles. Implementations compare raw counts or `Fraction`/`Decimal` values and round only presentation fields. Every terminal run writes a create-only canonical `runs/{run_id}.json/.md`, including quality/safety failure, unavailable, and execution failure; only `selected_pass` additionally writes an immutable `selections/{selection_id}` decision. Missing provider credentials/service produces `unavailable` and cannot select/cut over. A failing candidate report is retained, but the phase remains incomplete until a token candidate passes.

Selection and activation use separate immutable evidence. Fresh provider parity feeds an immutable selection-decision artifact; readiness and cutover bind its hash. Cutover, rollback, and restoration append a separate hash-chained activation receipt and never rewrite the artifact that authorized activation.

## Threat Model And Safety Constraints

| Threat | Severity | Required mitigation/proof |
|--------|----------|---------------------------|
| Candidate chunks leak into active retrieval | Critical | active pointer join in every current query; static drift test; pre-cutover retrieval integration |
| Cross-tenant reindex/cleanup | Critical | tenant/run/owner constraints, row locks, allowlisted doc set, no broad prefix/global delete |
| Incompatible config silently reuses evidence | High | canonical config fingerprint in compatibility predicate; immutable chunk version increment; replay regression |
| Provider/tokenizer drift causes overflow | High | asset SHA, exact provider parity gate, quarantine new writes/cutover, final pre-submit recomputation |
| Source changes during/resumed reindex | High | fixed source-manifest hash at each resume and cutover; stale run fails closed |
| Concurrent ingestion races cutover | High | fixed lock order, Phase 64.2 rollout epoch plus corpus rollout CAS, transactional pointer flip |
| Rollback restores obsolete policy content | High | source-drift marker; direct flip refused; rebuild prior config over current sources |
| Raw policy/provider payload leaks through reports | High | safe synthetic probes, allowlisted reason codes/counts/hashes only; no raw key/text/payload/stack trace |
| Unicode/token-window corruption | Medium | byte-offset round trip, property tests, exact source reconstruction/provenance |
| No-progress splitter denial of service | Medium | monotonic consumption assertion, max-piece bound, typed terminal error |

Each PLAN.md must include an explicit `<threat_model>` block and test the relevant rows above. Security enforcement defaults to ASVS L1 and blocks high-severity unresolved threats.

## Migration And Deployment Order

1. Land tokenizer asset/runtime/config and offline tests; no production behavior switch.
2. Run provider parity and store the approved report for the exact config fingerprint.
3. Land assembler behind explicit token-aware config; keep active character corpus readable.
4. Apply corpus/provenance migration and bootstrap every legacy tenant; prove row counts and active visibility before enforcing non-null/FK constraints.
5. Deploy active-generation filtering and token-aware dual-write/candidate builder; verify current retrieval is unchanged.
6. Build candidate, resume-test, deterministic-rebuild-test, replay-test, and run Phase 64.3 A/B.
7. Cut over only a passing candidate under both rollout locks/CAS epochs.
8. Exercise rollback in the isolated evaluation tenant, then restore selected token generation and seal evidence.

Downgrade must refuse once token-aware corpus versions, immutable bindings, snapshots, or active pointers depend on new fields. Operational rollback is an active pointer operation, not a destructive Alembic downgrade.

## Pitfalls To Make Explicit In Plans

- Do not use `tiktoken` merely because it is present transitively in `uv.lock`; no official/empirical evidence ties a tiktoken encoding to this provider model.
- Do not count without special tokens; the experiment proved an exact one-token EOS difference.
- Do not treat aggregate batch usage as per-chunk usage. Persist offline per-chunk counts and provider batch totals separately.
- Do not append title/source metadata after the count or reconstruct provider strings in the embedder.
- Do not call `decode(token_ids)` without proving byte-for-byte substring round trip for Unicode.
- Do not reuse `chunk_id={doc_key}_{index}` alone as a compatibility proof across config generations.
- Do not let evaluation cleanup delete inactive production generations or immutable replay history.
- Do not accept a red token candidate as Phase completion; that policy belonged to Phase 64.3's measurement goal.
- Do not run bare `pytest`, bare `python -m pytest`, or scoped Ruff as the final lint gate.
