## Summary

The implemented Phase 64.4 production scope was reviewed against `origin/main...HEAD`, including migration/ORM consistency, active and exact corpus joins, ordinary-ingestion copy-on-write publication, immutable evidence replay, candidate reservation/provider gates, authority timestamps, rollback isolation, artifact durability, and safe failure surfaces. The principal issue is an enforceable-budget bypass: the reviewed candidate CLI treats any caller-supplied artifact root as its authority root, so a copied self-consistent artifact tree resets the per-document reservation namespace and permits additional provider executions. Four additional correctness and crash-consistency defects are documented below.

## Critical Issues

### CR-01: Copying the reviewed candidate artifact tree resets the provider-execution budget

**Files:** `scripts/reindex_policies.py:139-142`, `scripts/reindex_policies.py:242-248`, `scripts/reindex_policies.py:492-529`, `src/rag/policy_reindex_artifacts.py:367-389`, `src/rag/policy_reindex_artifacts.py:1179-1181`

**Issue:** Every reviewed command accepts an arbitrary `--artifact-root`; `_reviewed_descriptor`, the state/budget loaders, reservation scan, and provider construction all use that same caller-selected root. The artifact guard only proves that the state path is below the root supplied in the same invocation, while the attempt cap counts only JSON files below that root. An operator can therefore copy the complete descriptor/state/budget tree to another directory after an allowlisted transient/unavailable attempt, invoke `build-next-reviewed` against the copied root, receive a new ordinal 1/2 reservation, and construct `EmbeddingService` again against the unchanged DB candidate. Repeating the copy bypasses `max_build_executions_per_document=2`, including the required crash-consumption/provider-cost security boundary.

**Fix:** Define the reviewed-candidate root once from the resolved repository root (for example, `REPOSITORY_ROOT / "evaluation/reports/rag_token_chunk_ab/v1/candidates"`) and reject alternate, copied, outside, and symlinked roots before descriptor/state/budget loading, reservation, or provider construction. Production reviewed commands should pass that canonical root internally rather than trusting a caller-owned namespace. Add adversarial copied-tree and symlink-root tests that assert zero reservation and zero provider-factory calls.

## Warnings

### WR-01: A clean install or newly created tenant cannot ingest its first policy document

**Files:** `src/db/migrations/versions/030_phase64_4_token_corpora.py:491-496`, `src/rag/ingestion.py:302-315`, `src/rag/ingestion.py:420-431`, `src/repositories/policy_corpus_repo.py:105-137`, `scripts/seed_demo.py:465-490`

**Issue:** Migration 030 creates bootstrap corpora only for tenant IDs already present in `policy_documents`. On a clean database the migration normally runs before demo tenants/documents exist, and any tenant created after the migration likewise has no rollout or manifest. Ordinary ingestion resolves an active corpus before parsing and then requires locked rollout/manifest rows during publication; the repository only raises when either is absent. `seed_demo.py` now also requires an already-active policy corpus instead of creating the first one. The supported seed and ingest paths therefore form a bootstrap deadlock for clean installs, empty tenants, and future tenants.

**Fix:** Bootstrap all existing policy-capable tenants in the migration, including empty tenants, and add an idempotent runtime first-corpus initializer under the tenant advisory lock for tenants created later. It should create an empty manifest, complete character-compatible corpus, rollout pointer, and bootstrap history before the first ingestion transaction. Cover clean install + `seed_demo`, empty-tenant first ingest, and concurrent first-ingest cases.

### WR-02: `claim-reviewed` backdates its second authorization transaction to descriptor creation time

**Files:** `scripts/reindex_policies.py:279-302`, `src/rag/policy_reindex.py:449-482`

**Issue:** Transaction A claims and commits the DB row using current time, but transaction B calls both `recover_identity` and `resume` with `descriptor.sealed_at`. `recover_identity` normalizes the supplied timestamp and then discards it without checking lease or parity expiry. If either authority expires after transaction A (or before transaction B starts), the backdated time still permits the `claimed/v1` row to advance to `building/v2` and publish state/budget artifacts. This violates the rule that every authorization boundary must use a current non-operator-supplied timestamp and lets an expired descriptor finish the claim composition.

**Fix:** Capture a fresh `checked_at = datetime.now(UTC)` before transaction B/artifact publication, require it to be strictly earlier than both descriptor expiries, and pass it through recovery/resume. Make `PolicyReindexService.recover_identity` enforce lease and parity expiry itself instead of discarding `now`. Add a fault test that expires authority between transactions A and B and proves no resume, v2 state, or budget publication occurs.

### WR-03: Equality at parity expiry is treated as fresh

**File:** `src/rag/policy_reindex.py:1004-1007`

**Issue:** Lease authority correctly rejects `lease_expires_at <= now`, but parity authority rejects only when `now > parity_expires_at`. At the exact expiry instant, `_lock_validated` therefore authorizes resume/build/validate work even though the contract requires `checked_at` to be strictly earlier than both expiries.

**Fix:** Change the parity check to `now >= owner.parity_expires_at` and add equality-at-expiry coverage for resume, candidate preparation/build, and validation.

### WR-04: Create-only authority files return before the directory entry is durable

**Files:** `src/rag/tokenizer_parity.py:188-210`, `src/rag/activation_receipt.py:485-504`

**Issue:** Both writers fsync the temporary file and publish it with `os.link`, but neither fsyncs the destination directory after the hard-link commit point. A process can report a successful immutable parity report or activation receipt while the filesystem has not durably persisted the directory entry; a crash can then lose the authority/evidence file even though the caller observed success. The parity file is later used as build/selection authority, and receipts are expected to be create-only committed-history evidence.

**Fix:** After a successful link (and after byte-identical reconciliation where applicable), fsync `destination.parent`/`path.parent` before returning; if directories may be newly created, durably fsync the created directory chain as well. Add fault-injection tests at link-before-directory-fsync and directory-fsync boundaries.
