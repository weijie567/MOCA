## Critical Issues

### CR-01: A symlink below the canonical root can still reset the provider-execution budget

**Files:** `scripts/reindex_policies.py:147-174`, `scripts/reindex_policies.py:279-286`, `scripts/reindex_policies.py:533-570`, `src/rag/policy_reindex_artifacts.py:295-324`, `src/rag/policy_reindex_artifacts.py:367-388`, `src/rag/policy_reindex_artifacts.py:740-773`, `src/rag/policy_reindex_artifacts.py:826-875`, `src/rag/policy_reindex_artifacts.py:1170-1193`

**Issue:** `_require_canonical_reviewed_root` checks only the canonical root itself and its ancestors up to the repository boundary. It never checks the descendant path used for `tenants/<tenant>/runs/<run>`. The descriptor, state, and budget loaders then compare lexical `Path.absolute()` values, while `read_bytes()`, `glob()`, and create-only publication follow filesystem symlinks. `_validate_build_artifact_authority` likewise uses a lexical `is_relative_to` check. Consequently, replacing the canonical run directory (or an ancestor such as `tenants`) with a symlink to a copied, self-consistent tree that omits consumed attempts passes the root and artifact checks. `reserve_candidate_build_attempt` sees a fresh attempt list and `_build_next_reviewed` constructs `EmbeddingService` again against the unchanged DB candidate, bypassing `max_build_executions_per_document=2`.

**Fix:** Before the first reviewed read, validate every existing component from the repository root through the exact tenant/run directory with `lstat()` and reject any symlink or resolved path outside the canonical root. Keep subsequent reads, scans, and create-only publications race-resistant by opening the canonical directory chain with directory file descriptors and no-follow semantics (or an equivalent mechanism), rather than re-following pathnames after a one-time check. Add adversarial tests for symlinked `tenants`, tenant, `runs`, and exact run directories; each must prove zero reservation and zero provider-factory calls, including after a copied pre-attempt tree is substituted.

## Warnings

### WR-01: Initial claim still accepts the exact parity-expiry instant

**Files:** `src/rag/tokenizer_parity.py:293-300`, `src/rag/policy_reindex.py:330-342`, `src/rag/policy_reindex.py:1219-1263`, `scripts/reindex_policies.py:181-226`, `scripts/reindex_policies.py:317-343`

**Issue:** The parity loader rejects only `age > maximum_age`, and `_validate_claim` rejects only `now - captured_at > parity_maximum_age`. At `now == captured_at + maximum_age`, both gates accept the report and `claim()` can create and return a candidate whose stored `parity_expires_at` already equals the authorization time. This conflicts with the fixed recovery/resume/build gates, which correctly require current time to be strictly earlier than expiry. In the reviewed path, transaction A can therefore commit the `claimed/v1` row and v1 artifact before transaction B rejects the same equality; in the ordinary `_claim` path, the already-expired identity can be returned directly.

**Fix:** Change both initial freshness comparisons to reject equality (`age >= maximum_age`, or equivalently `now >= captured_at + maximum_age`) and compute/reuse that exact expiry consistently through claim. Add equality tests for `require_fresh_provider_parity`, direct `PolicyReindexService.claim`, ordinary `_claim`, and reviewed claim, with the reviewed case proving that no candidate row or v1 artifact is created at expiry.
