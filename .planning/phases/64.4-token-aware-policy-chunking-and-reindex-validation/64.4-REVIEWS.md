# Cross-AI Plan Review — Phase 64.4

## Claude Review

### Summary

Phase 64.4 is a genuinely hard, contract-heavy phase: replace character-count policy chunking with a tokenizer-aware assembler that counts the exact `text-embedding-v4` input, while preserving Phase 64.2 immutable evidence/replay identity, isolated reindex, atomic cutover/rollback, and an A/B selection gate against the sealed Phase 64.3 baseline. The 11-plan / 22-task decomposition is real, single-purpose, and strictly dependency-ordered (`01→11`), which honors the `AGENTS.md` granularity hard rule and the CONTEXT split mandate.

The core factual claims hold against live code: `src/rag/chunker.py` enforces character budgets `1200/800/100` in both `chunk_blocks` and `chunk_markdown`; `src/rag/ingestion.py` appends title/section/`source_block_id` in `_embedding_text` after `chunk_blocks`, confirming the count-then-decorate gap; `src/rag/embedder.py` caps batches at 10 and discards usage; migrations end at `029`; Phase 64.2 CAS/rollout machinery exists in `evidence_version_repo.py`; and replay reads immutable `PolicyChunkVersion`. The three Phase 64.3 hashes in Plan 09 match `baseline.json` exactly.

The clean three-iteration GSD plan-checker convergence is largely justified. The external review found one ordering issue it rated blocking, several traceability/ownership gaps, and an open-ended completion-feasibility risk. It considered all fixable at plan level.

### Strengths

- Granularity and ordering are correct: each plan has a single owned surface, dependencies form a clean chain, and shared files are only touched sequentially.
- The sealed Phase 64.3 hashes are byte-exact and use the existing `FormatParityDataset` loader rather than a reinvented hash.
- The tokenizer contract is fail-closed: pinned asset/runtime/EOS behavior, no character fallback, and explicit parity quarantine.
- The assembler directly targets the verified `_embedding_text`-after-chunk divergence and pairs it with static ownership guards.
- Parity, selection, and activation are separated without a hidden cycle: Plan 08 builds a fixture-tested cutover API, Plan 09 mints real immutable selection, and Plan 10 performs the real drill/receipts.
- Immutable replay remains exact because replay resolves retained immutable IDs rather than active current heads.
- Real-provider and PostgreSQL completion is mandatory; unavailable/red evidence cannot substitute for passing selection.

### Concerns

#### HIGH — Plan 04 production default may flip before corpus isolation exists

Plan 04 says production ingestion uses `PolicyEmbeddingInputAssembler` while character behavior is only an explicit compatibility/A-B mode. Corpus generation, active pointer, and immutable compatibility do not exist until Plans 05–06. If ingestion runs between those waves, one document could be replaced with token-boundary chunks in the shared tenant table while the remainder stays character based.

Evidence: current `src/rag/ingestion.py` writes shared `policy_chunks`; current repository queries are tenant-scoped without corpus generation; the research deployment order says to land the assembler behind explicit token-aware configuration while keeping the character corpus active.

Suggested fix: make Plan 04's token mode explicit and default-off, keeping production character-compatible until Plan 06 resolves the active pointer/config. Avoid relying on a deployment freeze between waves.

#### MEDIUM — Threat IDs lack a canonical registry

Plans/VALIDATION reference `T64.4-*` IDs with gaps, but RESEARCH lists descriptive threats without the IDs. Inline plan definitions do not provide a 1:1 phase registry for the security auditor.

Suggested fix: add a numbered threat registry in RESEARCH or a phase threat artifact that maps all research threats to the IDs used by plans and VALIDATION.

#### MEDIUM — Plan 06 scope resolution is ambiguous for `src/knowledge/retrieval.py`

The production hybrid retrieval caller is not listed in Plan 06. This is safe only if active-current scope is resolved internally by repository methods without changing production caller signatures; the plan does not say that explicitly, while evaluation paths do require explicit corpus ownership.

Suggested fix: state that production repository methods resolve active scope internally, explicit corpus ownership is limited to evaluation/reindex/history methods, and add a retrieval cutover behavior test or list `src/knowledge/retrieval.py` if it must change.

#### MEDIUM — Passing-candidate completion can be unbounded

D-23 requires Phase completion only when a token config passes the fixed non-regression profile, but the plan does not define an iteration budget or escalation if no candidate passes.

Suggested fix: define a bounded number of sizing/assembly iterations, then surface a truthful red report and explicit user decision rather than looping indefinitely.

#### LOW — REQUIREMENTS.md traceability is stale

`REQUIREMENTS.md` ends at Phase 64.2 and does not register Phase 64.3/64.4 ROADMAP success criteria.

Suggested fix: add Phase 64.4 `ROADMAP-SC-1..6` traceability, preferably before execution rather than leaving the plan IDs orphaned.

#### LOW — New native tokenizer dependency adds platform/license risk

`tokenizers==0.23.1` is not yet in `uv.lock`; it is a compiled wheel dependency and the vendored asset is about 11.4 MB.

Suggested fix: make Plan 01 resolve/lock the exact dependency before vendoring and retain source/license plus resolved package hashes.

#### LOW — Plan 09 sealed hash field names drift from the live contract

Plan 09 says `manifest_sha256` / `gold_sha256`, while the existing contract and baseline use `manifest_hash` / `gold_hash`. Values match.

Suggested fix: use the existing field names in plan wording.

### Suggestions

- State in Plan 11 that the rollout/receipt machinery is driven by the inherited Phase 64.2 replay contract rather than by the small evaluation corpus size.
- Add a first-class integration test proving ordinary ingestion after cutover lands in the active token generation.
- Ensure the checked-in empirical parity fixture captures the 10/10 result provenance, not only probe labels.

### Risk Assessment

- Correctness/ordering: one material Plan 04 default-flip risk, fixable by a default-off gate.
- Migration/rollback: well covered; residual risk is operational around migration 030 backfill/non-null enforcement.
- Security/disclosure: mitigations are concrete; the gap is threat traceability, not absent controls.
- Completion feasibility: a token candidate may remain red and the plan currently lacks bounded escalation.
- Verification integrity: strong; hashes match, live provider/PostgreSQL gates are mandatory, and deterministic fakes cannot substitute for completion.

Confirmed repository facts are the chunker budgets, post-chunk embedding decoration, usage discard, migration numbering, Phase 64.2 CAS, immutable replay path, and hash equality. The Plan 04 continuity risk, unbounded iteration risk, and production-vs-explicit scope ambiguity are inferences from plan text with no repository evidence contradicting them.
