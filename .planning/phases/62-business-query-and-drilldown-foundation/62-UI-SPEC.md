# Phase 62 — UI Design Contract

> Visual and interaction contract for typed business-query results in the existing Agent Console. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

---

## Design System

| Property | Value |
|----------|-------|
| Tool | shadcn, existing initialization under `frontend/components.json`; do not reinitialize |
| Preset | `style=default`, `base=radix`, `baseColor=slate`, `cssVariables=true`, `tsx=true`, `rsc=false` |
| Component library | Existing local shadcn-style components: `badge`, `button`, `card`, `dialog`, `scroll-area`, `tabs`, `textarea` |
| Icon library | `lucide-react` |
| Font | `Inter, system-ui, sans-serif` |

Phase 62 must reuse the current Agent Console shell: Chat, Agent Timeline, and Details. This phase is not a new landing page, analytics dashboard, hero, chart builder, or report/export surface. The UI must remain quiet, operational, dense, and compatible with the existing dark console patterns from Phase 61.

Do not introduce a new page shell, new design system, decorative gradients, oversized cards, marketing copy, arbitrary charting, or nested cards. Use the existing 8px-or-less radius system and existing semantic color tokens.

---

## Spacing Scale

Declared values (must be multiples of 4):

| Token | Value | Usage |
|-------|-------|-------|
| xs | 4px | Icon gaps, dense metadata separators, status-dot offsets |
| sm | 8px | Badge gaps, row inner gaps, compact detail-list spacing |
| md | 16px | Panel padding, timeline item padding, details tab padding |
| lg | 24px | Section grouping inside Details only when separating result summary from rows |
| xl | 32px | Reserved for major console layout gaps; avoid inside dense business result rows |
| 2xl | 48px | Reserved; do not add new 48px vertical gaps in Phase 62 |
| 3xl | 64px | Reserved; not used in Phase 62 console work |

Exceptions: existing compact controls may keep established heights: 32px for topbar/select/new-conversation controls and 40px for primary buttons. Timeline rows must keep stable grid columns equivalent to `20px 1fr auto`; new labels, badges, and timestamps must not move the dot rail or resize neighboring rows.

## Typography

| Role | Size | Weight | Line Height |
|------|------|--------|-------------|
| Label | 12px | 400 | 1.33 |
| Body | 14px | 400 | 1.5 |
| Heading | 16px | 600 | 1.25 |
| Display | 20px | 600 | 1.2 |

Use only weights 400 and 600. Timeline primary labels use `text-body font-semibold`. Timeline subtitles, metadata labels, table headers, timestamps, field labels, and cursor labels use `text-label text-muted-foreground`. Query result values may use `text-heading font-semibold`; do not introduce larger analytics/dashboard display type.

Do not use viewport-scaled font sizes, negative letter spacing, or text that depends on hover to be understandable.

## Color

| Role | Value | Usage |
|------|-------|-------|
| Dominant (60%) | `hsl(var(--background))` = `220 24% 8%` | Page background and Details panel background |
| Secondary (30%) | `hsl(var(--card))` = `220 20% 11%`; `hsl(var(--muted))` = `218 16% 17%` | Timeline panel, chat/result cards, empty states, table headers |
| Accent (10%) | `hsl(var(--accent))` / `hsl(var(--primary))` = `187 68% 44%` | Active tab underline, focus ring, primary CTA, topbar shield mark, cursor/drilldown affordance when enabled |
| Success | `hsl(148 66% 48%)` | Completed query status dot/icon and success badges |
| Waiting | `hsl(42 93% 56%)` | Clarification/waiting states |
| Warning | `hsl(26 91% 56%)` | Unsupported-but-handled, degraded, or partial result states |
| Destructive | `hsl(0 72% 56%)` | Error, failed, rejected, and destructive approval states only |

Accent reserved for: active tab state, keyboard focus ring, primary `发送问题` button, topbar shield icon, and enabled cursor/drilldown controls. Do not use accent for every row, every value, or arbitrary business-query category coloring.

Business-query operations do not get new color families. Distinguish `aggregate`, `list`, `detail`, `breakdown`, and `compare` by labels, icons, row structure, and operation metadata, not by adding a multi-color analytics palette.

## Phase 62 Console Scope

The frontend must support typed business-query result payloads for these result kinds:

| Result Kind | Required Console Recognition |
|-------------|------------------------------|
| `aggregate` | Single value/rate with scope, time, filters, freshness |
| `list` | Bounded row list with safe display fields, row count, limit, optional cursor |
| `detail` | One safe projected resource detail view with allowlisted fields |
| `breakdown` | Dense group table with group label, value/rate, scope/time metadata |
| `compare` | Dense comparison table with compared periods/scopes and delta label when backend supplies one |
| `rag_answer` | Existing policy/evidence answer behavior; do not mix with business-fact authority |
| `clarification` | Existing clarification result, extended with business-query missing-slot/field reasons |
| `unsupported` | Existing unsupported result, extended with business-query operation/resource boundary reasons |

Phase 62 may keep `metric_answer` as a compatibility display path, but new long-term query answers must render from typed `business_query` payload data rather than by parsing localized final-response text.

## Safe Payload Contract

Frontend rendering must consume only backend-projected, UI-safe fields. The frontend must never render raw rows, raw SQL, arbitrary filters, hidden scope internals, prompt payloads, tool arguments, model routing hints, stack traces, or unallowlisted JSON.

Typed business-query payloads should follow this UI shape:

| Field | UI Contract |
|-------|-------------|
| `response_kind` | Use `business_query_answer` for new Phase 62 query results; existing `metric_answer`, `rag_answer`, `clarification`, and `unsupported` remain supported |
| `business_query.operation` | One of `aggregate`, `list`, `detail`, `breakdown`, `compare`; required for business-query display |
| `business_query.resource_label` | Safe localized resource label such as `订单`, `退款单`, `工单`, `补偿券记录`, `商家指标` |
| `business_query.result_label` | Short safe result label for timeline/details summary |
| `business_query.scope_label` | Safe display scope such as `当前权限范围`; no unauthorized merchant existence disclosure |
| `business_query.time_label` | Safe time range/preset label |
| `business_query.filters_label` | Safe summarized filters; omit rather than render raw filter objects |
| `business_query.freshness_label` | Safe freshness label when available |
| `business_query.fields_label` | Safe display-field summary for list/detail |
| `business_query.safe_reason` | Allowlisted reason code for clarification, unsupported, partial, empty, or denied states |
| `business_query.rows` | Optional UI-safe projected rows only; each row must contain display fields already redacted/allowlisted by backend |
| `business_query.cursor_label` | Safe pagination/cursor label; no raw cursor token text |

If a field is absent, render a conservative placeholder such as `-` or omit the metadata row. Do not synthesize scope, freshness, field, or evidence claims on the frontend.

## Timeline Result Labels

Timeline rows remain compact. They identify the result kind and why the run stopped or completed; details stay in chat final answer and Details.

| Result Type | Running Label | Completed Label | Subtitle Pattern |
|-------------|---------------|-----------------|------------------|
| aggregate | `正在查询业务汇总` | `业务汇总查询完成` | `aggregate: {result_label} · scope: {scope_label}` |
| list | `正在查询业务列表` | `业务列表查询完成` | `list: {resource_label} · rows: {row_count}/{limit}` |
| detail | `正在查询业务详情` | `业务详情查询完成` | `detail: {resource_label} · fields: {fields_label}` |
| breakdown | `正在查询业务分组` | `业务分组查询完成` | `breakdown: {resource_label} · by: {group_by_label}` |
| compare | `正在查询业务对比` | `业务对比查询完成` | `compare: {result_label} · {compare_label}` |
| metric compatibility | `正在查询业务指标` | `业务指标查询完成` | `metric: {metric_label} · scope: {scope_label}` |
| RAG answer | Existing RAG node label | Existing RAG final label | `evidence: {count}` only when backend supplies verified count |
| clarification | `需要补充信息` | `需要补充信息` | `原因: {safe_reason_label}` |
| unsupported | `当前能力不支持` | `当前能力不支持` | `原因: {safe_reason_label}` |
| error | `执行遇到问题` | `执行遇到问题` | `{safe_error_label}` |

Timeline subtitles may truncate. Full result metadata belongs in Details and the final answer. Timeline must not display raw row values except a safe `result_label`, safe count, and safe scope/time metadata.

## Details Panel Contract

Add or enable a Details tab named `Result` for typed business-query payloads. Tab order: `Result`, `Evidence`, `Approval`, `Trace`, `Run Info`. If no business-query result exists, the tab may show its empty state and must not replace existing Evidence behavior.

| Operation | Details Layout |
|-----------|----------------|
| aggregate | One compact summary card with value/rate first, then a 2-column metadata list for scope, time, filters, freshness, formula/caveat when safe |
| list | Dense table or list with at most 5 visible fields per row, 20 rows per page by default, sticky-free plain header, row-level drilldown affordance only when backend says it is allowed |
| detail | 2-column definition list grouped by safe field category; no raw JSON viewer |
| breakdown | Dense table with group label, value/rate, numerator/denominator when supplied, and caveat row when supplied |
| compare | Dense table with compared periods/scopes, value/rate, delta label when backend supplies it; no chart in Phase 62 |
| empty/denied | Dashed-border empty state or warning state using safe no-existence-leak copy |

Row-level drilldown controls use a lucide chevron or external-link style icon button with an accessible label such as `查看详情`. The control is disabled or omitted when `allowed_drilldowns` is empty. Do not expose raw cursor tokens; cursor controls show `上一页`, `下一页`, or `查看更多` only when backend provides a safe cursor capability.

Do not put a card inside another card. A repeated list/detail result may use individual cards or a table-like list, but the Details tab itself is not a floating card.

## Final Answer Placement

The final chat answer remains the primary user-facing explanation. Typed Details provides inspection, not a replacement for the answer.

| Operation | Final Answer Contract |
|-----------|-----------------------|
| aggregate | First sentence starts with the number/rate. Second sentence states scope, time range, filters, and freshness. |
| list | First sentence states the list result count and bounded scope. Follow with up to 5 safe identifiers or names when useful, then mention whether more results are available. |
| detail | First sentence names the safe resource type and whether the detail is available in the current permission scope. Follow with the most relevant safe fields. |
| breakdown | First sentence states the grouping basis and total/summary. Follow with the top groups as safe projected values. |
| compare | First sentence states the compared periods/scopes and main difference. Follow with the exact values and freshness. |
| RAG | Preserve existing evidence-backed wording only when RAG/claim gates actually supplied verified evidence. |
| clarification | Ask for the missing input and list accepted options. |
| unsupported | Explain the capability boundary and list supported alternatives. |

No response may claim policy/RAG evidence for business-fact-only answers. No response may reveal whether an out-of-scope merchant/resource/id exists.

## Copywriting Contract

| Element | Copy |
|---------|------|
| Primary CTA | `发送问题` |
| Result tab empty heading | `暂无业务查询结果` |
| Result tab empty body | `业务查询完成后，将在这里显示安全投影后的汇总、列表、详情、分组或对比结果。` |
| Timeline empty state | `等待提交问题后开始执行` |
| Business query loading | `正在查询业务数据` |
| Missing time clarification | `要查询该业务数据，请选择时间范围：今天、本周、本月、本季度、今年，或指定起止时间。` |
| Missing drilldown field clarification | `请说明要查看的字段或明细类型，例如订单号、退款单状态或工单状态。` |
| Unsupported operation/resource | `当前不支持该业务查询。你可以查询订单、退款单、工单、补偿券记录和商家指标的汇总、列表、详情、分组或对比结果。` |
| Scope denial | `当前权限范围内无法提供该业务数据。` |
| Empty safe result | `当前权限范围和筛选条件下没有可显示的结果。` |
| Error state | `业务查询遇到问题，请重试。若问题持续，请联系管理员。` |
| Destructive confirmation | none; Phase 62 business queries are read-only and must not introduce destructive UI actions |

Copy must explain the missing input or safe capability boundary. It must not mention raw SQL, internal registry names, hidden policy gates, prompt parsing, or whether denied resources exist.

## Interaction And State Requirements

- Starting a new query clears active timeline/details state for the current run while preserving prior chat messages in the conversation.
- Same-thread follow-up drilldown may rely on backend `last_query_spec`, `last_answer_context`, and `result_cursor`, but the frontend displays only the safe projected current result.
- The representative drilldown flow `本周多少订单？` then `订单号是多少？` must render as aggregate followed by list, with fresh scope/field/cursor validation reflected in the second run.
- Clarification, unsupported, denied, empty, and error outcomes must leave the input usable for retry or follow-up.
- Business-query Details must update from the latest active run only; late SSE callbacks from old runs must not repopulate the active Result tab.
- Mobile and desktop widths must keep timeline labels, timestamps, tabs, table/list fields, and cursor controls non-overlapping.
- Long values must truncate or wrap within their own cell; they must not resize the timeline rail, topbar, tabs, or adjacent panels.
- Sorting, export, dashboard charts, arbitrary field pickers, and free-form database exploration are out of scope for Phase 62.
