## Phase 9 BusinessToolService loop-facing contract requirements (anti-rework payload)

This section is a design INPUT for Phase 9 so its `BusinessToolService` is built loop-ready in one pass. Phase 10's `investigate` loop is the bounded caller (P10-DEV-02 reverses Phase 9 CONTEXT's "no bounded caller" lock — service-layer reuse is unaffected; only that stance is overridden).

What the loop needs BusinessToolService to PROVIDE (Phase 9 builds these):
- Read tools the loop may select (per-call, one at a time): `get_order`, `get_refund_case`, `get_ticket`, `get_logistics`, `get_merchant_risk`. (logistics/merchant_risk have no repo backing yet — register-but-unavailable.)
- A per-call typed result contract = `ToolResult` (`tool_result.v2`, §12.5) with the 9+ status states: `success | partial_success | not_found | permission_denied | timeout | unavailable | conflict | invalid_request | invalid_response | error`. The loop branches on `status`; today's interim raw tools only return success/error, so the interim seam MUST normalize the raw `{status, data, error}` shape into at least {success, permission_denied (from error_code FORBIDDEN), not_found (ORDER_NOT_FOUND), timeout (DB_TIMEOUT), error} so Phase 9's richer ToolResult is a drop-in superset.
- Input = `ToolCallContext` (`tool_context.v2`, §12.5): tenant_id/user_id/role/permissions/merchant_scope/session_id/thread_id/run_id/trace_id/request_id/tool_call_id/caller_node/deadline_at/attempt/idempotency_key/policy_snapshot_ref. All system-injected; never LLM/user-generated. The loop assembles this from trusted state + config and passes it down.
- Business-fact provenance via `business_fact_refs: list[BusinessFactRefV1]` — NOT policy `EvidenceRefV1`. The loop must not coerce business facts into evidence_refs.
- Aggregated output = `BusinessContextV1` (§8.4): status + facts + missing_required_facts + errors + tool_results carried SIMULTANEOUSLY (the substrate that makes D-08 fine-grained possible).

What stays in Phase 10's loop/router, NOT in the Phase 9 facade (so Phase 9 does not over-build):
- Result CONSUMPTION and routing decisions: fine-grained permission-denied handling (D-08), `termination_reason`, sufficiency judgement. These belong to investigate + route_after_investigate, not the facade.
- The bounded loop control (max_iterations, tool selection, iteration counting, event emission). The facade executes one read; the loop decides whether/what to read next.
- Phase 9's facade owns permission/scope/not_found/timeout/partial/invalid-response at the per-call boundary; Phase 10 owns how those per-call results compose into a route.

Integration swap point: when Phase 9 lands, replace the interim raw-tool calls in `investigate.py` (`get_order(...)` etc.) with `BusinessToolService.fetch_context(slots, intent, ToolCallContext) -> BusinessContextV1` (§8.4 signature). Do NOT `import from src.business_tools...` in this plan (it does not exist).
</phase_9_loop_facing_contract>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| LLM tool selection -> tool execution | LLM may only pick from the read-only allowlist; a write/unknown tool must be rejected before execution (D-04/D-06). |
| Tool result (denied) -> business_context.facts/reply | Denied-resource data must not enter facts or leak via inference (D-08). |
| Loop iteration -> resource consumption | Hard max_iterations cap bounds the loop (D-03). |
| Tool output -> trace event | Per-call events carry only safe summaries, no raw payload (§17.2). |
