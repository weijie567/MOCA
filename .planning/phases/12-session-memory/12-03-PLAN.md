<interfaces>
Normal response path target:
```text
graph final_response -> API persists/emits final response -> post-response memory_write finalizer
```

`memory_write` input state:
- `tenant_id`, `user_id`, `thread_id`, `current_run_id`
- `extracted_slots` and resolved `active_slots`
- `primary_intent` or `current_intent`
- `clarification_request`
- `final_response`
- `last_business_context_refs`

`memory_write` output state:
- `memory_write_result`
- appended `trace_steps` item with node `memory_write`
- optional node error on failed write
- optional memory write events

  Non-blocking requirement:
  - Non-SSE `/chat`: persist final response, construct the `ChatResponse`, return it to the caller, then run memory write in background using a fresh DB session/transaction or a safe app-owned session factory. The endpoint must not wait for a slow memory write merely because the response payload was already fixed.
  - SSE `/agent-runs/{run_id}/events`: yield the `final_response` SSE event before awaiting/scheduling memory write. Any later memory-write telemetry is optional and must not be required for the client to receive the final answer.
  - Slow MemoryService, lock waits, CAS retry, or DB unavailability must not delay final response delivery. The timeout bounds only the background/finalizer work, not the user-visible response path.
  - If the current runtime cannot safely schedule background work with an independent DB session, the implementation must record a blocking deviation instead of satisfying this plan with a synchronous pre-return await.

Forbidden write candidates:
- policy conclusions
- risk decisions
- approval decisions
- action authorization
- durable preferences
- case precedent
- raw tool output
- raw prompt/LLM chain content
</interfaces>
