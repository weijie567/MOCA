## User Constraints (from CONTEXT.md)

### Locked Decisions

#### Shared manifest and semantic Gold
- **D-01:** The checked-in `format_parity_manifest.jsonl` remains the physical-fixture authority. A versioned validation layer must verify the exact three parity groups, nine variants, file existence, source-of-truth linkage, allowed formats/source types, checksums, and format metadata before evaluation starts.
- **D-02:** Each canonical policy owns one format-independent fact/anchor definition shared by all three variants. Gold binds canonical policy ID, expected section, evidence anchors, table/header/row anchors, optional locator constraints, question category, and no-answer behavior; it must not bind generated chunk IDs or duplicate full answers per format.
- **D-03:** Gold must cover the roadmap cases (facts, exceptions, amounts/time limits, tables, cross-section questions, and no-answer) with stable IDs and schema tests. Format-specific expectations are additive locator/OCR constraints, not alternate policy truth.
- **D-04:** Fixture, manifest, and Gold hashes are first-class run inputs. Any content change must be visible in the report and cannot silently reuse the prior baseline identity.

#### Parser-parity scoring and diagnostics
- **D-05:** Parser parity invokes the existing `ParserRegistry`/production parser DTO path directly and stays independent of tenant, database, embeddings, and retrieval.
- **D-06:** Score distinct dimensions rather than one aggregate: parse status, semantic anchor recall, heading/structure preservation, table/header/row preservation, provenance/location coverage, page coverage for PDFs, OCR diagnostics for scanned PDFs, and warning/failure codes.
- **D-07:** Normalization is evaluation-only and comparison-only. It may normalize whitespace/OCR layout artifacts for anchor matching, but must not mutate source fixtures, parser output, canonical evidence text, or production behavior. Exact numeric, date, percentage, negation, and policy identifiers remain protected anchors.
- **D-08:** Every miss must retain enough safe evidence to attribute it to parser/OCR/structure/provenance without emitting raw unsafe parser payloads. Results must be deterministic and stably ordered.

#### Retrieval rounds and reset safety
- **D-09:** Retrieval parity is provider-backed and exercises the real `IngestionService` plus existing `KnowledgeService`/retrieval path. Unit/contract tests may use deterministic fakes, but they cannot be presented as the provider-backed baseline.
- **D-10:** Use one fixed, explicitly evaluation-owned tenant and stable logical `doc_key` values. Run Markdown, digital PDF, and scanned PDF in separate rounds; each round ingests exactly one equivalent variant per canonical policy and asks the identical Gold questions.
- **D-11:** Cleanup is a dedicated evaluation boundary that fails closed unless tenant identity, evaluation ownership marker, allowed `eval_` doc-key set, and expected round/run token all match. Every delete is tenant-scoped and allowlisted; no global table reset, broad prefix delete, production tenant selection, or unqualified repository cleanup is permitted.
- **D-12:** A round must prove both pre-clean and post-clean state. Residual evaluation-owned current rows, blocks, chunks, jobs, or incompatible immutable evidence heads fail the run instead of contaminating the next format. Historical immutable evidence/replay semantics from Phase 64.2 must not be weakened or deleted to make the evaluator convenient.
- **D-13:** Report Hit@1/3/5, MRR, semantic anchor coverage, no-answer/fallback correctness, and locator coverage by case, policy, and format. Capture safe ingestion/retrieval diagnostics and stage attribution without leaking credentials, raw provider payloads, or cross-tenant existence.

#### Baseline, thresholds, and reproducibility
- **D-14:** JSON is the canonical machine-readable report; Markdown is a deterministic human-readable projection of the same result. Both record schema version, command/mode, timestamps, manifest/Gold hashes, parser/OCR versions, embedding model/config, retrieval/RRF/rewrite/reranker config, environment prerequisites, per-stage metrics, and failure tables.
- **D-15:** The first baseline may be red. Evaluator correctness, complete attribution, reproducibility, and honest gate status are phase completion criteria; metric misses must remain visible and receive a named target phase (Phase 64.4 only for chunking/token-aware gaps, otherwise a specifically named RAG quality follow-up/backlog item).
- **D-16:** Preserve the initial target thresholds from `docs/quality/rag-quality-plan.md` as explicit evaluated gates, while also reporting the observed baseline. Threshold changes require versioned rationale and old/new values; they cannot be silently edited to make a run pass.
- **D-17:** Deterministic schema/scoring/reset/report tests are CI-safe. Provider/OCR-backed baseline execution has an explicit command and prerequisites, produces checked-in versioned artifacts when run, and must distinguish unavailable prerequisites from quality failure.

## Summary

Phase 64.3 should build an evaluator around the production system, not a second RAG implementation. Parser parity must call the production `ParserRegistry` DTO path without database/provider dependencies; retrieval parity must call the real `IngestionService` and production knowledge/retrieval facade with provider-backed embeddings and OCR where required. Deterministic fakes are valid only for schema, scoring, isolation, and report contract tests, never as the checked-in provider baseline. [VERIFIED: `64.3-CONTEXT.md` D-05, D-09, D-17; `src/rag/ingestion.py`]

The immediate contract gate is red: the three Markdown SHA-256 values recorded in `format_parity_manifest.jsonl` do not match the current Markdown fixtures, while all six PDF hashes do match their current files. This is more than a metadata typo: because Markdown is declared the source of truth, blindly refreshing only the Markdown hashes could bless stale PDFs as equivalent. Plan 64.3-01 must reconcile fixture lineage, regenerate/review variants if the Markdown changes are intentional, and add a checksum regression test before Gold authoring or any baseline run can be trusted. [VERIFIED: prior Phase 64.3 checksum audit; `evaluation/rag_sources/README.md`; `evaluation/rag_sources/format_parity_manifest.jsonl`]

Reset design is the other hard constraint. `PolicyDocumentVersion` and `PolicyChunkVersion` are append-only, the current `PolicyDocument` head is referenced through restrictive foreign keys, and `PolicyDocumentRepository` has no deletion seam. Therefore “full reset” cannot mean truncate/delete every RAG row. The evaluator needs a fail-closed, evaluation-owned round-isolation boundary that preserves immutable history while proving that only the exact three allowlisted current projections can participate in a round. [VERIFIED: prior Phase 64.3 schema audit; `src/repositories/policy_document_repo.py`; `src/repositories/policy_chunk_repo.py`; `src/repositories/document_block_repo.py`; `src/repositories/rag_ingestion_job_repo.py`]

**Primary recommendation:** create exactly five dependency-ordered plans: contract/Gold; parser evaluator; retrieval isolation/runtime; reporting/baseline; final regression/docs/ledgers. Do not combine them into one implementation plan. [VERIFIED: `AGENTS.md`; `64.3-CONTEXT.md`; confirmed prior Phase 64.3 research]

## Repository Facts

### Fixture contract

- The checked-in manifest contains exactly three top-level policy groups, each with Markdown, digital-PDF, and scanned-PDF variants, for nine variants total. Each PDF variant records five pages; scanned variants record zero extractable text characters. [VERIFIED: `evaluation/rag_sources/format_parity_manifest.jsonl`]
- The README declares each Markdown file to be its policy family's source of truth and says the six PDFs are generated from those sources. It also requires format rounds to avoid loading equivalent variants together. [VERIFIED: `evaluation/rag_sources/README.md`]
- Current checksum state is inconsistent: all three Markdown entries are stale, whereas all six PDF entries match. This must be treated as a contract-plan red light and covered by a regression test. [VERIFIED: prior Phase 64.3 checksum audit]
- The target quality plan defines the initial gates: all nine parse successfully; Markdown and digital-PDF semantic anchor recall is 100%; scanned-PDF anchor recall is at least 95% after comparison-only whitespace normalization; critical table headers/rows are preserved; PDF evidence has page provenance; retrieval Hit@5 is at least 90%; and cross-format Hit@5 spread is at most 10 percentage points. These are target gates, not proof of current performance. [CITED: `docs/quality/rag-quality-plan.md` §5]

### Production ingestion and persistence

- `IngestionService.ingest_document(file_path, doc_meta, *, expected_rollout_version=None)` performs production parsing, block chunking, and embedding before taking the locked document-replacement path. It then updates or creates the current `PolicyDocument`, replaces current blocks/chunks, appends immutable evidence when needed, and commits. [VERIFIED: `src/rag/ingestion.py`]
- Production parsing is reached through `self.parser_registry.parse(file_path, doc_key=..., source_type=..., metadata=...)`, which is the signature parser parity should mirror directly. [VERIFIED: `src/rag/ingestion.py`]
- Re-ingestion already deletes current `DocumentBlock` and `PolicyChunk` rows by both `document_id` and `tenant_id`, then writes replacements; this is current-projection replacement, not immutable-history deletion. [VERIFIED: `src/rag/ingestion.py`; `src/repositories/document_block_repo.py`; `src/repositories/policy_chunk_repo.py`]
- `PolicyDocumentRepository` exposes tenant-scoped reads, a locking read, and `upsert`; it exposes no delete method. `RagIngestionJobRepository` exposes a tenant-scoped `delete_by_document_id`, but that alone cannot reset the document/evidence graph. [VERIFIED: `src/repositories/policy_document_repo.py`; `src/repositories/rag_ingestion_job_repo.py`]
- The immutable document/chunk version rows must remain append-only, and the restrictive relationship to the current document head makes broad document deletion unsafe. [VERIFIED: prior Phase 64.3 schema audit]

### Existing evaluator assets

- `scripts/eval_rag.py` is DB-backed but defaults to the first active tenant when `--tenant-id` is absent. That behavior is forbidden for the new parity runner; the fixed evaluation tenant must be mandatory and ownership-validated. [VERIFIED: `scripts/eval_rag.py`; D-10–D-11]
- The legacy evaluator scores expected document/chunk IDs and Hit@5/fallback behavior. Its CLI/report organization may be reused, but its chunk-bound Gold and tenant fallback must not define parity semantics. [VERIFIED: `scripts/eval_rag.py`; D-02, D-13]
- `scripts/eval_rag_ablation.py` deliberately synthesizes deterministic fake evidence in dry-run mode and raises for real local retrieval. It is useful as a deterministic scoring/report pattern only; its output cannot be labeled a provider-backed baseline. [VERIFIED: `scripts/eval_rag_ablation.py`; D-09, D-17]
- `build_safe_ingestion_report` already projects an allowlisted ingestion trace and removes unsafe nested fields. New reports should consume this safe boundary or an equally strict existing projection rather than serialize exception objects, raw parser DTOs, or provider payloads. [VERIFIED: `src/rag/ingestion.py`; D-08, D-13]

## Implementation Guidance

### System architecture and data flow

```text
Checked-in manifest + fixtures + semantic Gold
                    |
                    v
       strict contract/hash preflight
          | invalid             | valid
          v                     v
  contract_error          +-----+-------------------+
  (no evaluation)         |                         |
                          v                         v
                ParserRegistry.parse       evaluation-owned round guard
                          |                 (tenant + marker + allowlist
                          v                  + run/round token)
                ParseResult/blocks                    |
                          |                            v
                          |                  IngestionService + providers
                          |                            |
                          |                            v
                          |                  production KnowledgeService
                          |                            |
                          +-------------+--------------+
                                        v
                         stage-attributed case results
                                        |
                      +-----------------+------------------+
                      | prerequisite unavailable           | completed
                      v                                    v
             unavailable report                    pass/red-quality report
                                                           |
                                                           v
                                      canonical JSON -> deterministic Markdown
```

The two evaluator paths share only validated inputs, scoring primitives, failure taxonomy, and report schemas. Parser evaluation must not import tenant/database/embedder concerns, while retrieval evaluation must not bypass production ingestion or retrieval. [VERIFIED: D-05, D-09, D-14]

### Contract and Gold

1. Implement one versioned manifest loader that rejects anything other than the exact three unique `parity_group`/`doc_key` values and their exact nine allowed variant tuples. Validate relative paths, file existence, source-of-truth linkage, format/source-type pairs, PDF page/text-layer metadata, and SHA-256 before constructing evaluator inputs. [VERIFIED: D-01]
2. Make checksum reconciliation a prerequisite task. Because the canonical Markdown hashes are stale while generated PDF hashes are stable, require human-reviewed lineage reconciliation: either restore the intended canonical Markdown, or regenerate/review both PDF variants and the manifest from the intended Markdown. Never “fix” only the three manifest hash strings. [VERIFIED: prior checksum audit; `evaluation/rag_sources/README.md`]
3. Use one versioned semantic Gold envelope per canonical policy. Each stable case ID should carry policy ID, category, expected section, protected evidence anchors, optional table/header/row anchors, optional PDF/OCR locator constraints, and no-answer behavior. Parser and retrieval expectations may be separate fields, but they must reference the same fact IDs rather than duplicate truth. [VERIFIED: D-02–D-03]
4. Hash fixture bytes, manifest bytes, and Gold bytes independently. Construct baseline identity from the schema version plus those hashes and relevant runtime configuration; do not derive identity from timestamps or output filenames. [VERIFIED: D-04, D-14]

### Parser evaluator

1. Call the production parser exactly as ingestion does: `ParserRegistry.parse(path, doc_key=..., source_type=..., metadata=...)`. Do not instantiate repositories, tenant state, embeddings, or retrieval. [VERIFIED: `src/rag/ingestion.py`; D-05]
2. Preserve separate scores for parse status, semantic anchors, headings/structure, tables, provenance/location, PDF page coverage, and scanned-PDF OCR diagnostics. Emit per-anchor/per-structure misses before aggregates so every aggregate is auditable. [VERIFIED: D-06]
3. Keep normalization as a pure evaluator function that returns comparison text without changing the DTO or fixture. Normalize only enumerated whitespace/layout artifacts; compare numbers, dates, percentages, negations, policy IDs, table headers, and critical rows with protected exact anchors. [VERIFIED: D-07]
4. Emit stable reason codes and bounded safe snippets/locator summaries. Sort output by policy ID, variant order, case ID, anchor ID, and reason code; inject clocks in tests so generated artifacts are deterministic aside from explicitly modeled timestamps. [VERIFIED: D-08, D-14]

### Retrieval isolation and runtime

1. Require an explicit fixed evaluation tenant; remove the legacy “first active tenant” fallback from the new runner. Require exact tenant UUID, evaluation ownership marker, exact three `eval_` document keys, run token, and round token before any mutation. [VERIFIED: `scripts/eval_rag.py`; D-10–D-11]
2. Build a dedicated evaluation-only round-isolation service instead of scattering deletes through CLI code. The service must first lock/inspect the three allowlisted heads, verify ownership and expected lineage, and refuse unknown keys, extra current retrieval-visible rows, mismatched tokens, or cross-tenant state without revealing another tenant's existence. [VERIFIED: D-11–D-12]
3. Define “clean” in terms of retrieval-visible current projection plus exact immutable-head compatibility, not “all historical rows absent.” Preserve `PolicyDocumentVersion`/`PolicyChunkVersion`; never truncate, delete the `PolicyDocument` head, or weaken restrictive foreign keys. Use the existing tenant-and-document-scoped child deletion seams only after ownership proof, and add whatever evaluation ownership/run-token persistence is necessary to make that proof durable. [VERIFIED: prior schema/repository audit; D-11–D-12]
4. For each format round, prove pre-state, ingest exactly one variant for each of the three stable logical doc keys through `IngestionService`, verify exactly those three current projections, run the identical Gold questions through the production knowledge/retrieval facade, then prove post-state. Any residual or incompatible state is an isolation failure, not a quality score. [VERIFIED: D-09–D-12; `src/rag/ingestion.py`]
5. A provider-backed baseline must use the configured production embedding/rewrite/reranker behavior, with OCR on the scanned-PDF route. Deterministic fake providers belong only in unit/contract tests. [VERIFIED: D-09, D-17]

### Failure taxonomy and stage attribution

Use mutually exclusive top-level execution outcomes:

| Outcome | Meaning | Gate treatment |
|---|---|---|
| `completed_pass` | Prerequisites available and every configured gate passed. [VERIFIED: D-15–D-17] | Pass |
| `completed_quality_fail` | Execution completed truthfully but one or more parser/retrieval/provenance thresholds missed. [VERIFIED: D-15–D-17] | Red baseline; phase may still complete if attribution and follow-up are complete |
| `unavailable_prerequisite` | OCR/provider/config/runtime prerequisite was unavailable before a trustworthy metric could be produced. [VERIFIED: D-17] | Neither pass nor quality failure; explicit unavailable gate |
| `execution_error` | Contract, isolation, malformed result, unsafe diagnostic, or evaluator invariant failed. [VERIFIED: D-01, D-08, D-11–D-12] | Evaluator failure; no quality conclusion |

Attribute completed misses by evidence transition: parser misses an anchor → `parser`/`ocr`; parser has it but no produced chunk contains it → `chunking`; an eligible chunk has it but Top-K does not → `retrieval`; the retrieved evidence contains it but canonical locator/page binding is absent or invalid → `provenance`. A case may retain secondary reason codes, but exactly one primary stage must drive the failure table. [VERIFIED: `64.3-CONTEXT.md` phase boundary and D-06, D-13]

### Reporting and baseline

1. Make JSON the only result owner. Generate Markdown by a pure, stable projection from the JSON object; never calculate metrics independently in the Markdown renderer. [VERIFIED: D-14]
2. Record schema version, execution outcome, command/mode, timestamp, manifest/Gold/fixture hashes, parser/OCR versions, embedding and retrieval configurations, environment prerequisites, round tokens, stage metrics, gates, and case-level failure attribution. [VERIFIED: D-14]
3. Report the quality-plan targets unchanged alongside observed values. A target miss stays red; threshold revisions require a new version and explicit old/new rationale. [VERIFIED: `docs/quality/rag-quality-plan.md` §5; D-15–D-16]
4. Check in provider-backed baseline artifacts only when prerequisites were available and the real production paths ran. An unavailable report may be checked in for diagnosis but must not replace or masquerade as the baseline. [VERIFIED: D-09, D-17]
5. Route observed gaps by stage: token/chunk-boundary findings may target Phase 64.4; parser/table remediation, retrieval tuning, and mixed-corpus findings must receive their separately named deferred phases/backlog entries. [VERIFIED: D-15; CONTEXT Deferred Ideas]

## Pitfalls

### Pitfall 1: Blessing stale fixture lineage

**What goes wrong:** Updating three stale Markdown hash strings makes validation green while the six PDFs may still represent earlier Markdown content. [VERIFIED: prior checksum audit; `evaluation/rag_sources/README.md`]

**Avoidance:** Stop Plan 01 at the red checksum test, determine which Markdown revision is canonical, regenerate/review both PDF variants if needed, then update the manifest as one reviewed fixture change. [VERIFIED: D-01, D-04]

### Pitfall 2: Treating reset as deletion of immutable history

**What goes wrong:** A truncate/delete-all strategy violates append-only replay semantics, cannot safely remove restrictive document heads, and risks non-evaluation data. [VERIFIED: prior schema audit; D-11–D-12]

**Avoidance:** Prove exact evaluation ownership and current retrieval-visible isolation while preserving immutable version rows and allowed document identities. Fail closed on any unexpected head, key, token, tenant, block, chunk, or job. [VERIFIED: D-11–D-12]

### Pitfall 3: Selecting the first active tenant

**What goes wrong:** Reusing the legacy evaluator's default tenant resolution could mutate or evaluate a non-evaluation tenant. [VERIFIED: `scripts/eval_rag.py`]

**Avoidance:** Make the evaluation tenant explicit and validate a durable ownership marker before reads or writes. Return one non-enumerating denial for all ownership/scope mismatches. [VERIFIED: D-10–D-11]

### Pitfall 4: Calling a fake baseline “provider-backed”

**What goes wrong:** Deterministic fake evidence can make metrics green without executing OCR, embeddings, ingestion, retrieval, rewrite, or reranking. [VERIFIED: `scripts/eval_rag_ablation.py`; D-09]

**Avoidance:** Separate CI contract mode from provider-baseline mode in both CLI and report schema. Record `unavailable_prerequisite` when OCR/provider requirements are missing. [VERIFIED: D-17]

### Pitfall 5: Conflating unavailable with bad quality

**What goes wrong:** Provider/OCR absence reported as zero recall suggests a product-quality regression that was never measured; treating absence as pass hides an unexecuted baseline. [VERIFIED: D-17]

**Avoidance:** Use distinct execution outcomes and calculate quality gates only after required stages complete. [VERIFIED: D-15–D-17]

### Pitfall 6: One aggregate hides the broken stage

**What goes wrong:** A single parity score cannot distinguish parser/OCR loss, chunk containment loss, retrieval ranking loss, or locator/provenance loss. [VERIFIED: D-06, D-13]

**Avoidance:** Persist per-case stage transitions and independent dimension metrics before summary gates. [VERIFIED: D-06, D-13]

### Pitfall 7: Normalization changes policy meaning

**What goes wrong:** Broad OCR cleanup can erase negation or alter amounts, dates, percentages, and identifiers, creating false anchor hits. [VERIFIED: D-07]

**Avoidance:** Keep normalization comparison-only, enumerate allowed layout changes, and protect semantic tokens with exact anchors and focused tests. [VERIFIED: D-07]

### Pitfall 8: Oversized phase plan

**What goes wrong:** Combining contracts, parser evaluation, persistence isolation, provider runtime, reporting, and regression closeout into one plan produces broad file surfaces and non-executable acceptance criteria. [VERIFIED: `AGENTS.md` plan granularity rule]

**Avoidance:** Use the following five plans exactly, with explicit dependencies and independent gates. [VERIFIED: project instruction; confirmed prior research]
