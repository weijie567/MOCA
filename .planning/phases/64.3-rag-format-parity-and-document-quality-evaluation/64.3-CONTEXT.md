# Phase 64.3: RAG Format Parity And Document Quality Evaluation - Context

**Gathered:** 2026-08-10
**Status:** Ready for planning

<domain>
## Phase Boundary

Build a reproducible evaluation foundation over exactly three canonical policy groups and their Markdown, digital-PDF, and scanned-PDF variants. The phase defines shared semantic Gold, evaluates the existing production parser directly, evaluates the existing provider-backed ingestion/retrieval path in isolated format rounds, and records a versioned baseline that separates parsing, chunking, retrieval, and provenance failures.

This phase measures current production behavior; it does not tune or redesign the parser, OCR engine, chunker, embeddings, hybrid retrieval, query rewrite, reranker, ContextBuilder, or claim verifier. A truthful, reproducible failing baseline is an acceptable result. Remediation belongs in a named later phase.

</domain>

<decisions>
## Implementation Decisions

### Shared manifest and semantic Gold
- **D-01:** The checked-in `format_parity_manifest.jsonl` remains the physical-fixture authority. A versioned validation layer must verify the exact three parity groups, nine variants, file existence, source-of-truth linkage, allowed formats/source types, checksums, and format metadata before evaluation starts.
- **D-02:** Each canonical policy owns one format-independent fact/anchor definition shared by all three variants. Gold binds canonical policy ID, expected section, evidence anchors, table/header/row anchors, optional locator constraints, question category, and no-answer behavior; it must not bind generated chunk IDs or duplicate full answers per format.
- **D-03:** Gold must cover the roadmap cases (facts, exceptions, amounts/time limits, tables, cross-section questions, and no-answer) with stable IDs and schema tests. Format-specific expectations are additive locator/OCR constraints, not alternate policy truth.
- **D-04:** Fixture, manifest, and Gold hashes are first-class run inputs. Any content change must be visible in the report and cannot silently reuse the prior baseline identity.

### Parser-parity scoring and diagnostics
- **D-05:** Parser parity invokes the existing `ParserRegistry`/production parser DTO path directly and stays independent of tenant, database, embeddings, and retrieval.
- **D-06:** Score distinct dimensions rather than one aggregate: parse status, semantic anchor recall, heading/structure preservation, table/header/row preservation, provenance/location coverage, page coverage for PDFs, OCR diagnostics for scanned PDFs, and warning/failure codes.
- **D-07:** Normalization is evaluation-only and comparison-only. It may normalize whitespace/OCR layout artifacts for anchor matching, but must not mutate source fixtures, parser output, canonical evidence text, or production behavior. Exact numeric, date, percentage, negation, and policy identifiers remain protected anchors.
- **D-08:** Every miss must retain enough safe evidence to attribute it to parser/OCR/structure/provenance without emitting raw unsafe parser payloads. Results must be deterministic and stably ordered.

### Retrieval rounds and reset safety
- **D-09:** Retrieval parity is provider-backed and exercises the real `IngestionService` plus existing `KnowledgeService`/retrieval path. Unit/contract tests may use deterministic fakes, but they cannot be presented as the provider-backed baseline.
- **D-10:** Use one fixed, explicitly evaluation-owned tenant and stable logical `doc_key` values. Run Markdown, digital PDF, and scanned PDF in separate rounds; each round ingests exactly one equivalent variant per canonical policy and asks the identical Gold questions.
- **D-11:** Cleanup is a dedicated evaluation boundary that fails closed unless tenant identity, evaluation ownership marker, allowed `eval_` doc-key set, and expected round/run token all match. Every delete is tenant-scoped and allowlisted; no global table reset, broad prefix delete, production tenant selection, or unqualified repository cleanup is permitted.
- **D-12:** A round must prove both pre-clean and post-clean state. Residual evaluation-owned current rows, blocks, chunks, jobs, or incompatible immutable evidence heads fail the run instead of contaminating the next format. Historical immutable evidence/replay semantics from Phase 64.2 must not be weakened or deleted to make the evaluator convenient.
- **D-13:** Report Hit@1/3/5, MRR, semantic anchor coverage, no-answer/fallback correctness, and locator coverage by case, policy, and format. Capture safe ingestion/retrieval diagnostics and stage attribution without leaking credentials, raw provider payloads, or cross-tenant existence.

### Baseline, thresholds, and reproducibility
- **D-14:** JSON is the canonical machine-readable report; Markdown is a deterministic human-readable projection of the same result. Both record schema version, command/mode, timestamps, manifest/Gold hashes, parser/OCR versions, embedding model/config, retrieval/RRF/rewrite/reranker config, environment prerequisites, per-stage metrics, and failure tables.
- **D-15:** The first baseline may be red. Evaluator correctness, complete attribution, reproducibility, and honest gate status are phase completion criteria; metric misses must remain visible and receive a named target phase (Phase 64.4 only for chunking/token-aware gaps, otherwise a specifically named RAG quality follow-up/backlog item).
- **D-16:** Preserve the initial target thresholds from `docs/quality/rag-quality-plan.md` as explicit evaluated gates, while also reporting the observed baseline. Threshold changes require versioned rationale and old/new values; they cannot be silently edited to make a run pass.
- **D-17:** Deterministic schema/scoring/reset/report tests are CI-safe. Provider/OCR-backed baseline execution has an explicit command and prerequisites, produces checked-in versioned artifacts when run, and must distinguish unavailable prerequisites from quality failure.

### the agent's Discretion
- Exact schema/module/class names and whether parser/retrieval Gold share one envelope or separate versioned files, provided semantic truth remains single-source and schema validation is strict.
- Exact evaluation tenant UUID, run-token format, and repository/service placement for cleanup, provided the allowlisted fail-closed constraints above hold.
- Exact safe snippets and diagnostic reason-code names, deterministic report ordering, CLI flag names, and Markdown table layout.
- Plan and wave composition, subject to the project rule that contract/Gold, parser evaluator, retrieval isolation/runtime, and baseline/gates are separate dependency-ordered plans rather than one oversized plan.

</decisions>

<code_context>
## Existing Code Insights

### Reusable Assets
- `evaluation/rag_sources/` already contains the three Markdown sources of truth, six generated PDFs, a reproducible fixture builder, and the manifest required by the phase.
- `src/rag/parsers/registry.py`, `src/rag/parsers/base.py`, and format parsers expose the production parse DTOs and safe warning/provenance model needed by direct parser parity.
- `src/rag/ingestion.py` already connects parser, block chunking, embeddings, immutable evidence versioning, and safe ingestion reports.
- `scripts/eval_rag.py` and `scripts/eval_rag_ablation.py` provide established CLI/report/scoring patterns, but the former binds expected chunks and the latter is deterministic dry-run metadata rather than the new format-parity baseline.
- `src/knowledge/retrieval.py` and `src/knowledge/service.py` expose the production retrieval and evidence-package path that provider-backed evaluation must exercise.

### Established Patterns
- Evaluation artifacts live under `evaluation/golden/` and `evaluation/reports/`, with deterministic tests under `tests/eval/` and repository test commands using `uv run`.
- Parser/OCR traces and ingestion failures are safe allowlisted projections; raw file paths, bytes, parser dumps, provider payloads, and stack traces must not enter reports.
- Phase 64.2 made evidence versions append-only/current-head aware. Re-ingestion may supersede current material, but evaluation cleanup cannot erase historical identity to simulate a clean round.
- Tenant/scope checks fail closed and must not leak whether another tenant owns matching data.

### Integration Points
- Gold/manifest validation feeds both evaluator CLIs and their tests.
- Parser parity connects at `ParserRegistry.parse(...)` and scores `ParseResult`/`ParsedBlock` without persistence.
- Retrieval parity connects at `IngestionService.ingest_document(...)`, the production retrieval facade, and a new tightly scoped evaluation cleanup/service seam.
- Report generation connects to existing quality documentation/Makefile conventions without replacing the legacy 22-case RAG regression set.

</code_context>

<specifics>
## Specific Ideas

- Treat a red first baseline as useful engineering evidence, not as permission to tune thresholds or production components inside this phase.
- Make stage attribution visible enough that a maintainer can answer “parser, chunking, retrieval, or provenance?” for every failed case.
- Keep the legacy chunk-ID-based RAG golden set unchanged; parity Gold is semantic so Phase 64.4 can compare changed chunk boundaries against the same truth.

</specifics>

<deferred>
## Deferred Ideas

- Token-aware chunk sizing, production/dry-run chunk-path convergence, reindex/cutover/rollback, and A/B selection — Phase 64.4.
- Mixed 20-30 document corpus, version distractors, and mixed retrieval evaluation — a named post-64.4 RAG Mixed Retrieval Corpus phase/backlog item.
- Parser cleaning/table-fidelity remediation discovered by the baseline — a named RAG Parsing, Cleaning And Table Fidelity phase/backlog item; do not fix silently in Phase 64.3.
- Retrieval weight, RRF, query rewrite, or reranker tuning — a named RAG Retrieval Quality Optimization phase/backlog item after the baseline exists.
- DOCX parity and XLSX/PPTX support — DOCX parity after the V1 baseline; XLSX/PPTX remain explicitly out of scope.

</deferred>
