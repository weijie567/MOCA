# Phase 64.5 C0 — Security Audit

> This is a threat-mitigation verdict for the implemented C0 surface in Plans 01–04 only. It does not audit or claim implementation of Plans 05–08, does not authorize provider dispatch, and does not complete SC-64.4-5/6.

## Verdict

The implemented C0 surface has **6/7 consolidated threats closed and 1 open threat**. All 16 prose threat-model rows in Plans 01–04 are classified below. The plans contain no `accept` or `transfer` language, so every row has the implicit disposition `mitigate`.

The open threat is in the implemented review/promotion boundary, not in future live work: current-code and attestation sealing dirty-check only four paths, while the recorded identity is the full committed `HEAD` and `HEAD^{tree}`. Critical implemented provider-dispatch, promotion-checker, request-envelope, and call-graph owners are outside that four-path set. An uncommitted modification to an excluded owner is therefore loaded by Python but is invisible to the current-promotion/attestation dirty check; the committed HEAD/tree still matches the promotion row. This leaves the declared dirty-code and alternate-helper bypass mitigation incomplete.

The checked-in C0 production commands remain hard-disabled, so this finding does **not** assert that the current normal CLI reaches a provider. It must nevertheless be closed before Plan 05 may make either reviewed route reachable, as required by D-14/D-16/D-30.

## Open Threat

### T-64.5-06 — Protected-code identity does not cover the implemented promotion/dispatch boundary

**Impact:** High at the re-enablement gate. A dirty excluded Python owner can change review validation, remove a CLI stop, alter provider construction/retry behavior, change A/B result semantics, or add a provider call while `require_current_promotion()` still observes the promoted commit/tree and the four listed files as clean. Because the checker is itself excluded, a dirty checker can also run altered attestation/promotion logic without `seal-review-attestation` returning `protected_code_dirty`.

**Required mitigation before re-enablement:**

1. Make dirty-state detection and C0→C1 diff identity cover the complete implemented security/runtime closure, at minimum the promotion checker, authority repository/service/schema, both reviewed dispatch CLIs, reviewed build/A-B orchestration, embedder, and every canonical envelope/provider call-graph owner; or use an equivalently fail-closed source-tree integrity mechanism.
2. Ensure the identity being compared to the DB promotion represents the code Python can actually load, not only the committed tree while excluded working-tree files may differ.
3. Add static and runtime negatives proving a dirty change in each security-critical owner (especially `scripts/check_phase64_5_gate.py`, both provider CLIs, and both orchestration modules) refuses attestation/promotion/authority/reservation/dispatch before provider construction.
4. Re-run C0 code/security review and seal new attestations after the protected boundary changes. Do not advance to Plan 05 route re-enablement while this threat remains open.

Implementation files were read-only during this audit, so no mitigation was patched here.
