### CR-01: The authoritative protected graph is still not transitively closed

**Files:** `src/rag/provider_execution_authority.py:33-75`; `src/repositories/provider_execution_authority_repo.py:66-83,524-540`; `scripts/check_phase64_5_gate.py:195-203,309-320,342-359,672-681`; `src/rag/policy_reindex.py:50-64,825-871,982-995`; `tests/architecture/test_phase64_5_gate.py:29-43,86-133`; `tests/architecture/test_rag_chunking_boundaries.py:343-390`

**Issue:** `PROTECTED_PROVIDER_EXECUTION_GRAPH` is now the single tuple consumed by repository and checker dirty/diff gates, but it is not the runtime dependency closure it claims to be. Static import tracing of the tuple finds 24 directly imported local modules absent from the tuple. Security-relevant omissions include `src/repositories/document_block_repo.py`, `src/repositories/policy_corpus_repo.py`, `src/repositories/evidence_version_repo.py`, `src/repositories/policy_chunk_repo.py`, `src/rag/evaluation/parser_parity.py`, and `src/rag/search_text.py`. For example, reviewed-build preflight obtains the exact provider inputs through the unprotected `DocumentBlockRepository`, and both build/A-B validation consume unprotected corpus/evidence repositories. A dirty edit to any omitted owner is loaded by the protected modules but is invisible to every path-limited `git status` and C0→C1 diff hash, so an existing promotion remains current while provider inputs, source checks, retrieval observations, or selection evidence change.

The new parameterized test only dirties paths already present in the tuple, and the provider-constructor inventory scans three hand-picked files. Those tests prove consistent consumption of the manifest, not manifest completeness. This leaves the original review/promotion authorization bypass open.

**Fix:** Make the protected manifest transitively closed over every local runtime import that can affect authority, provider reachability, request bytes/counts, source/parity checks, retrieval observations, or selected evidence. Prefer a broad, stable protected source set if a hand-maintained closure cannot be made fail-closed. Add an architecture test that recursively resolves local imports from the two dispatch/checker roots and rejects every unprotected dependency unless it is in a narrow, documented audited-exclusion set.

runtime_closure = resolve_local_import_closure(PROTECTED_ENTRYPOINTS)
assert runtime_closure <= set(PROTECTED_PROVIDER_EXECUTION_GRAPH) | AUDITED_IMMUTABLE_EXCLUSIONS

## Warnings

### WR-01: Selected-pass can be replayed without binding the current A/B run or complete provider execution

**Files:** `src/rag/evaluation/token_chunk_ab.py:732-758,761-826,880-1015`; `scripts/eval_rag_token_chunk_ab.py:1094-1191`; `tests/eval/test_rag_token_chunk_ab.py:589-693`

**Issue:** `canonical_ab_subject_hash()` binds the candidate owner, inputs, and envelope, but not the canonical A/B `run_id`. `CanonicalABExecutionService.execute()` does not accept an expected run ID, and `require_exact_canonical_ab_lineage()` compares tenant/corpus/provider/parity/binding fields without comparing `report.run_id` or the run-derived round owners. The service also accepts any `actual_request_count` from zero through the envelope maximum for `selected_pass`. Consequently, a previously valid selected report for the same candidate/input/envelope, with a different run ID and even `actual_request_count=0`, passes all pre-persistence checks and can create new selection/activation-authorization bytes plus a successful DB result. That is not the fresh full-provider selected pass required by D-12/D-19.

**Fix:** Pass the expected canonical run identity into the execution service before reservation, include it in the reservation subject hash, and require the report/run-derived namespaces to match it before any file write. For completed full-provider outcomes, require the exact complete call count (currently the envelope maximum), not merely an in-range count. Add negatives for changed `run_id`, changed round owner, and zero/short selected-pass request counts, asserting no terminal, selection, authorization, result, or projection write.

### WR-02: Transient retry evidence is not tied to the DB-recorded actual request count

**Files:** `src/rag/evaluation/token_chunk_ab.py:829-859,933-963`; `src/rag/provider_execution_authority.py:311-358`; `src/repositories/provider_execution_authority_repo.py:247-266,330-416`; `tests/eval/test_rag_token_chunk_ab.py:1350-1478`

**Issue:** The typed mapper grants `transient_execution_error` when the diagnostic claims a positive provider request count and proved rollback. The execution service validates `actual_request_count` independently only as `0 <= count <= maximum`; it never requires the diagnostic count to be supported by that DB count. `ProviderExecutionResultRequestV1` and `record_result()` therefore accept a transient result with `actual_request_count=0`, and ordinal-two authorization later checks only the predecessor result code plus unchanged subject/envelope. A contradictory diagnostic (`provider_request_count=1`) and DB result (`actual_request_count=0`) can thus authorize the sole retry despite lacking truthful immutable transient-request evidence.

**Fix:** Cross-bind diagnostic and DB counts before persistence—for the current semantics, require `0 < diagnostic.provider_request_count <= actual_request_count` for a transient result—and enforce at the domain/repository boundary that `transient_execution_error` cannot record zero actual requests. Add a negative that persists this contradictory pair and proves both result creation and ordinal two are refused.
