# Phase 64.5: Database-Backed Provider Budget And Token Rollout Completion - Context

**Gathered:** 2026-08-12
**Status:** Ready for planning

<domain>
## Phase Boundary

Replace Phase 64.4's file-backed provider/build attempt authority with a PostgreSQL-backed globally unique execution budget, safely re-enable only the reviewed token-candidate build and canonical A/B commands, and use fresh authority to complete one truthful token rollout. Completion requires a fresh candidate, a canonical full-provider `selected_pass`, selected cutover, rollback to the prior corpus, restore of the selected corpus, hash-chained receipts, and fail-closed closeout evidence for SC-64.4-5/6.

This phase does not reinterpret the expired Phase 64.4 authority, execute the abandoned Phase 64.4 Plans 18-20 as written, redesign tokenizer/chunker/parser/OCR/retrieval/reranking, tune quality gates after observing results, replace the embedding model, or build a general provider gateway.

</domain>

<decisions>
## Implementation Decisions

### Database as the sole provider authority
- **D-01:** PostgreSQL rows, constraints, locks, and transactional reservations are the only production authority that may permit provider construction. Files, paths, UUID possession, CLI arguments, environment variables, and self-consistent copied artifacts are never authority.
- **D-02:** One logical execution authority must cover both token-candidate document builds and full-provider A/B runs. Physical table decomposition is discretionary, but every authorization must bind tenant, authority/run, candidate, purpose, subject, ordinal, exact configuration, parity proof, source manifest, source corpus/rollout epoch, evidence rollout version, absolute expiry, and provider request envelope.
- **D-03:** Database uniqueness must serialize reservations across processes, worktrees, retries, crashes, copied artifacts, and alternate paths. Application-only prechecks are insufficient.
- **D-04:** File artifacts remain immutable audit projections of committed database truth. Copying, deleting, or replaying them cannot create, reset, or extend provider authority.

### Reservation, crash, and retry semantics
- **D-05:** A reservation is durably committed in a short transaction before provider construction. Provider work and later candidate/report persistence must not be able to roll back the consumed reservation.
- **D-06:** A crash or ambiguous exit after committed reservation consumes that ordinal. No timeout, lease stealing, manual edit, or reconciliation path may recycle it or infer that no provider request occurred.
- **D-07:** Preserve the closed Phase 64.4 caps: at most two provider executions per ordered candidate document and at most two complete A/B executions. Ordinal two is available only after immutable, allowlisted transient/unavailable evidence and unchanged authority; quality, safety, configuration, parity, source, response, projection, or unknown failures are terminal.
- **D-08:** The provider request envelope must seal a deterministic upper request bound. SDK retries remain zero; reviewed outer retries and batch counts are explicit and budgeted. Reconciliation may publish or recover already committed results, never rerun provider work.

### Fresh authority and time
- **D-09:** Phase 64.5 creates a new run, candidate, fresh parity proof, absolute lease, and database budget. The expired Phase 64.4 descriptor, candidate, file manifests, and ordinals remain historical evidence only and are not imported, renewed, rebound, or credited.
- **D-10:** Effective authority is the intersection of the DB budget expiry, candidate lease, parity expiry, current source manifest/active corpus epoch, and evidence rollout version. A new row cannot extend an older prerequisite.
- **D-11:** Time comes from trusted application/database time, not an operator-supplied timestamp. Freshness is checked when authority is issued, when a reservation is committed, and immediately before provider construction; equality with expiry is refused.
- **D-12:** Any source, evidence, pointer, configuration, parity, tenant, run, candidate, owner, or request-envelope drift fails closed before provider construction and preserves the current character corpus.

### Provider dispatch review gate
- **D-13:** The current production hard-disable remains in place while the DB authority and its adversarial tests are implemented.
- **D-14:** Re-enablement is a late, explicit gate: an interim deep code review, security audit, migration/concurrency verification, and before-provider negative suite must all be clean before either production provider command becomes reachable.
- **D-15:** Only `build-next-reviewed` and the canonical `run-ab` path may be re-enabled. Legacy `build-next` stays unconditionally disabled, and no CLI flag, environment variable, alternate root, direct helper, or test-only seam may bypass the DB authority.
- **D-16:** If the interim audit finds a real blocker, fix and re-review the bounded DB boundary before proceeding. Do not enable provider access while findings remain open.

### Fresh candidate and canonical A/B decision
- **D-17:** Build exactly one fresh token candidate from the sealed Phase 64.3 source set and locked token configuration. Candidate work is inactive and invisible until selected activation.
- **D-18:** Reuse the existing sealed Gold set, same-provider/same-run comparison, exact metrics, hard proofs, and exact-rational non-regression gates without threshold or dataset changes after observation.
- **D-19:** Only a fresh, full-provider `selected_pass` may mint activation authorization. `candidate_failed`, `quality_fail`, `safety_fail`, `unavailable`, or `execution_error` produces truthful immutable evidence and no activation authority.
- **D-20:** The only permitted A/B retry is the predeclared second ordinal under the closed transient/unavailable matrix. A nonpassing quality/safety outcome or exhausted budget stops Phase 64.5 honestly; it does not trigger tuning, another candidate, a larger budget, or a recovery-plan expansion.

### Reversible activation and closeout
- **D-21:** Selected cutover and selected restore must bind the DB reservation/result lineage and revalidate current source/evidence authority immediately before pointer CAS. Emergency rollback to the exact prior complete corpus does not require selection authority.
- **D-22:** The live drill is exactly contiguous selected cutover → prior rollback → selected restore. Each pointer flip uses tenant-scoped CAS, append-only history, unmixed active bindings, and post-commit live re-read.
- **D-23:** Each of the three activation events receives a create-only, hash-chained receipt derived from committed database history. Files are evidence projections; the database history row remains authoritative.
- **D-24:** Closeout must fail closed unless the final pointer is the selected corpus, the prior corpus remains complete/readable, the exact three-event lineage and receipt chain validate, no mixed visibility or stale authority exists, the selected report/selection/authorization hashes match, and required regressions pass.

### Migration and compatibility
- **D-25:** Add authority schema from migration head 031 without importing any Phase 64.4 file authority. Migration/ORM parity and real PostgreSQL concurrency, crash, replay, upgrade, and downgrade tests are required; downgrade refuses once authoritative execution rows exist.
- **D-26:** Existing Phase 64.4 V1 report, selection, authorization, receipt, descriptor, state, and budget bytes/loaders keep their historical meaning. New database lineage is additive and cannot retroactively authorize old artifacts.

### Execution discipline carried forward
- **D-27:** Plans are strictly serial around schema, authority, review gate, live provider execution, activation, and closeout. Freeze the reviewed plan count unless a genuinely new safety boundary appears.
- **D-28:** Each Wave-0 RED is the smallest test that proves the missing contract and is run immediately; do not keep expanding a matrix before observing the first valid failure.
- **D-29:** Do not repeatedly reload already completed full context during later serial plans. Each executor reads only its plan, required upstream summaries, changed authority contracts, and its explicit `read_first` set.
- **D-30:** Expired authority, missing provider prerequisites, nonpassing A/B, exhausted budget, or an unresolved security finding is an honest stop. Schedule pressure never authorizes lease renewal, threshold changes, extra attempts, another candidate, or a longer recovery chain.

### the agent's Discretion
- Exact table names and whether authority, reservation, and result records use one normalized table family or bounded purpose-specific tables.
- Internal DTO/module names, indexes, lock helpers, result projections, and safe diagnostic wording, provided all locked bindings and fail-closed semantics are preserved.
- The exact artifact schema version used to project new DB authority, provided Phase 64.4 V1 bytes remain unchanged.

</decisions>

## Existing Code Insights

### Reusable Assets
- `src/db/models.py` and `src/repositories/policy_corpus_repo.py` already provide tenant corpus generations, active/previous pointer CAS, append-only activation history, leases, source/evidence lineage, and PostgreSQL lock patterns.
- `src/rag/policy_reindex.py` provides fixed-order claim/resume/build/validate/activate state transitions and fresh parity/source checks.
- `src/rag/evaluation/token_chunk_ab.py` provides the sealed A/B metrics, exact-rational gates, terminal report types, selection rules, and rollback-isolated comparison runtime.
- `src/rag/activation_receipt.py` provides create-only receipt projection and hash-chain verification from committed activation history.
- Phase 64.4 file-backed budget DTOs and tests are useful compatibility oracles for caps, retry classification, safe diagnostics, and artifact schemas, but not production authority.

### Established Patterns
- PostgreSQL is authoritative for tenant-visible state; writes use explicit locks, uniqueness, and CAS while files are derived audit evidence.
- Provider clients are constructed only after deterministic preflight, with SDK retries disabled and safe/redacted failure classifications.
- Candidate corpora remain inactive until a single tenant pointer flips atomically; all current retrieval paths project through active corpus bindings.
- Real PostgreSQL migration and concurrency tests are required for authority claims; SQLite or mock-only proofs are insufficient.

### Integration Points
- Migration 032 (or the next repository head) and ORM/repository modules own the new provider execution authority.
- `scripts/reindex_policies.py` and `scripts/eval_rag_token_chunk_ab.py` currently refuse provider-capable dispatch before side effects and are the only production CLI gates to re-enable.
- Selection/activation integration flows through `src/rag/policy_reindex.py`, `src/rag/activation_receipt.py`, and the existing corpus rollout/history tables.
- Architecture guards and focused tests already enumerate forbidden provider bypasses and must be updated only after the reviewed DB gate exists.

</code_context>

<specifics>
## Specific Ideas

- Keep the safety posture strong but the workflow bounded: freeze plan count after review, use minimal RED evidence, execute plans strictly serially, and do not create another recovery chain when an external prerequisite fails.
- A database reservation is comparable to a spent ticket: once committed, ambiguity or crash cannot make it available again.
- The Phase 64.4 retained artifacts remain useful forensic evidence, but Phase 64.5 deliberately starts with fresh authority rather than attempting to salvage them.

</specifics>
