## User Constraints (from CONTEXT.md)

### Locked Decisions

### Database as the sole provider authority
- **D-01:** PostgreSQL rows, constraints, locks, and transactional reservations are the only production authority that may permit provider construction. Files, paths, UUID possession, CLI arguments, environment variables, and self-consistent copied artifacts are never authority.
- **D-02:** One logical execution authority must cover both token-candidate document builds and full-provider A/B runs. Physical table decomposition is discretionary, but every authorization must bind tenant, authority/run, candidate, purpose, subject, ordinal, exact configuration, parity proof, source manifest, source corpus/rollout epoch, evidence rollout version, absolute expiry, and provider request envelope.
- **D-03:** Database uniqueness must serialize reservations across processes, worktrees, retries, crashes, copied artifacts, and alternate paths. Application-only prechecks are insufficient.
- **D-04:** File artifacts remain immutable audit projections of committed database truth. Copying, deleting, or replaying them cannot create, reset, or extend provider authority.

### Reservation, crash, and retry semantics
- **D-05:** A reservation is durably committed in a short transaction before provider construction. Provider work and later candidate/report persistence must not be able to roll back the consumed reservation.
- **D-06:** A crash or ambiguous exit after committed reservation consumes that ordinal. No timeout, lease stealing, manual edit, or reconciliation path may recycle it or infer that no provider request occurred.
- **D-07:** Preserve the closed Phase 64.4 caps: at most two provider executions per ordered candidate document and at most two complete A/B executions. Ordinal two is available only after immutable, allowlisted transient/unavailable evidence and unchanged authority; quality, safety, configuration, parity, source, response, projection, or unknown failures are terminal.
- **D-08:** The provider request envelope must seal a deterministic upper request bound. SDK retries remain zero; reviewed outer retries and batch counts are explicit and budgeted. Reconciliation may publish or recover already committed results, never rerun provider work.

### Fresh authority and time
- **D-09:** Phase 64.5 creates a new run, candidate, fresh parity proof, absolute lease, and database budget. The expired Phase 64.4 descriptor, candidate, file manifests, and ordinals remain historical evidence only and are not imported, renewed, rebound, or credited.
- **D-10:** Effective authority is the intersection of the DB budget expiry, candidate lease, parity expiry, current source manifest/active corpus epoch, and evidence rollout version. A new row cannot extend an older prerequisite.
- **D-11:** Time comes from trusted application/database time, not an operator-supplied timestamp. Freshness is checked when authority is issued, when a reservation is committed, and immediately before provider construction; equality with expiry is refused.
- **D-12:** Any source, evidence, pointer, configuration, parity, tenant, run, candidate, owner, or request-envelope drift fails closed before provider construction and preserves the current character corpus.

### Provider dispatch review gate
- **D-13:** The current production hard-disable remains in place while the DB authority and its adversarial tests are implemented.
- **D-14:** Re-enablement is a late, explicit gate: an interim deep code review, security audit, migration/concurrency verification, and before-provider negative suite must all be clean before either production provider command becomes reachable.
- **D-15:** Only `build-next-reviewed` and the canonical `run-ab` path may be re-enabled. Legacy `build-next` stays unconditionally disabled, and no CLI flag, environment variable, alternate root, direct helper, or test-only seam may bypass the DB authority.
- **D-16:** If the interim audit finds a real blocker, fix and re-review the bounded DB boundary before proceeding. Do not enable provider access while findings remain open.

### Fresh candidate and canonical A/B decision
- **D-17:** Build exactly one fresh token candidate from the sealed Phase 64.3 source set and locked token configuration. Candidate work is inactive and invisible until selected activation.
- **D-18:** Reuse the existing sealed Gold set, same-provider/same-run comparison, exact metrics, hard proofs, and exact-rational non-regression gates without threshold or dataset changes after observation.
- **D-19:** Only a fresh, full-provider `selected_pass` may mint activation authorization. `candidate_failed`, `quality_fail`, `safety_fail`, `unavailable`, or `execution_error` produces truthful immutable evidence and no activation authority.
- **D-20:** The only permitted A/B retry is the predeclared second ordinal under the closed transient/unavailable matrix. A nonpassing quality/safety outcome or exhausted budget stops Phase 64.5 honestly; it does not trigger tuning, another candidate, a larger budget, or a recovery-plan expansion.

### Reversible activation and closeout
- **D-21:** Selected cutover and selected restore must bind the DB reservation/result lineage and revalidate current source/evidence authority immediately before pointer CAS. Emergency rollback to the exact prior complete corpus does not require selection authority.
- **D-22:** The live drill is exactly contiguous selected cutover → prior rollback → selected restore. Each pointer flip uses tenant-scoped CAS, append-only history, unmixed active bindings, and post-commit live re-read.
- **D-23:** Each of the three activation events receives a create-only, hash-chained receipt derived from committed database history. Files are evidence projections; the database history row remains authoritative.
- **D-24:** Closeout must fail closed unless the final pointer is the selected corpus, the prior corpus remains complete/readable, the exact three-event lineage and receipt chain validate, no mixed visibility or stale authority exists, the selected report/selection/authorization hashes match, and required regressions pass.

### Migration and compatibility
- **D-25:** Add authority schema from migration head 031 without importing any Phase 64.4 file authority. Migration/ORM parity and real PostgreSQL concurrency, crash, replay, upgrade, and downgrade tests are required; downgrade refuses once authoritative execution rows exist.
- **D-26:** Existing Phase 64.4 V1 report, selection, authorization, receipt, descriptor, state, and budget bytes/loaders keep their historical meaning. New database lineage is additive and cannot retroactively authorize old artifacts.

### Execution discipline carried forward
- **D-27:** Plans are strictly serial around schema, authority, review gate, live provider execution, activation, and closeout. Freeze the reviewed plan count unless a genuinely new safety boundary appears.
- **D-28:** Each Wave-0 RED is the smallest test that proves the missing contract and is run immediately; do not keep expanding a matrix before observing the first valid failure.
- **D-29:** Do not repeatedly reload already completed full context during later serial plans. Each executor reads only its plan, required upstream summaries, changed authority contracts, and its explicit `read_first` set.
- **D-30:** Expired authority, missing provider prerequisites, nonpassing A/B, exhausted budget, or an unresolved security finding is an honest stop. Schedule pressure never authorizes lease renewal, threshold changes, extra attempts, another candidate, or a longer recovery chain.

## Summary

Phase 64.5 should add migration **032** and a normalized, append-only authority family: one fresh logical authority, committed per-subject reservations, one create-only result per reservation, and DB-backed activation receipt lineage. Database uniqueness is the final concurrency arbiter; existing tenant advisory locks and `FOR UPDATE` locks supply deterministic ordering and a place to validate cross-row invariants. [VERIFIED: migrations `030`/`031`, `src/repositories/policy_corpus_repo.py`, `src/repositories/rag_evaluation_round_repo.py`; CITED: https://www.postgresql.org/docs/current/ddl-constraints.html]

The critical refactor is transaction shape. Current reviewed build work can reserve and call the provider inside one surrounding transaction, while Phase 64.5 requires: deterministic preflight → short reservation transaction and commit → fresh locked recheck immediately before provider construction → provider work outside the transaction → separate result/projection transaction. A crash after reservation is spent; reconciliation may derive a missing result row/file from already committed candidate/report state, but may never call the provider. [VERIFIED: `src/rag/policy_reindex.py`, `scripts/reindex_policies.py`, `src/rag/evaluation/token_chunk_ab.py`; Phase 64.5 D-05..D-08]

No documented provider idempotency guarantee was located in the official DashScope OpenAI-compatible synchronous embeddings reference or the official OpenAI embeddings create reference inspected on 2026-08-12. This is a bounded documentation finding, not a claim that no private capability exists; the design must retain consume-on-reservation. [CITED: https://help.aliyun.com/zh/model-studio/text-embedding-synchronous-api; CITED: https://platform.openai.com/docs/api-reference/embeddings/create]

**Primary recommendation:** freeze an eight-plan, strictly serial delivery after dual review: schema → authority service → build integration → A/B integration → independent dispatch gate/re-enable → fresh candidate → canonical A/B → activation/receipt/closeout. [VERIFIED: Phase 64.5 D-13..D-30; project `AGENTS.md`]

## Architecture Patterns

### System Architecture

```text
reviewed CLI command
  → deterministic preflight (sealed inputs/config/parity/envelope)
  → PostgreSQL authority lock + exact binding checks
      ├─ invalid/drift/expired → refuse, no provider construction
      └─ valid → INSERT unique reservation → COMMIT (ordinal spent)
           → fresh DB-time locked recheck → construct provider
           → bounded provider calls outside transaction
                ├─ crash/unknown → spent, fail closed
                └─ result → DB projection + create-only result in new transaction
                              → immutable file projection
                              → selected_pass only → CAS activation drill
                                  → DB history/receipt chain → closeout
```

### Pattern 1: Normalized immutable authority family

Use four bounded DB concepts. [RECOMMENDATION derived from D-01..D-08 and D-23]

| Record | Required bindings/constraints |
|---|---|
| `provider_execution_authority` | UUID PK; tenant; fresh run token; fresh candidate FK; owner; exact config schema/JSON/fingerprint; parity ID/hash/expiry; manifest revision/hash; source active corpus and rollout epoch; evidence rollout version; absolute expiry; provider/model/dimensions; envelope-contract hash. Unique non-null `(tenant_id, run_token)` and `(tenant_id, candidate_id)`; immutable. |
| `provider_execution_reservation` | Authority FK; purpose (`candidate_build`/`token_chunk_ab`); subject kind/index/hash; ordinal 1..2; exact envelope JSON/hash/max requests; DB `reserved_at`; optional immutable predecessor-result FK. Unique `(authority_id, purpose, subject_hash, ordinal)`; create-only and never released. |
| `provider_execution_result` | Unique reservation FK; closed result-code enum; actual request count constrained by envelope; canonical result/evidence hashes; committed candidate/report/selection references; DB time. Create-only; absence means ambiguous/spent, not reusable. |
| `activation_receipt_lineage` | Activation-history FK; authority/reservation/result/selection hashes; previous receipt hash; current receipt hash; event ordinal. Unique history/event and append-only; file receipt is projected afterward. |

Add a partial unique constraint on existing candidate `(tenant_id, run_token) WHERE run_token IS NOT NULL`; current repository detects duplicate rows after locking but the schema does not prevent them. [VERIFIED: `src/db/models.py`; `src/repositories/policy_corpus_repo.py`]

### Pattern 2: Constraint-backed reservation transaction

Use a tenant transaction-scoped advisory lock plus row locks in one documented order, validate every bound value, derive the only legal next ordinal, insert, flush, and commit. Treat an `IntegrityError` as contention: roll back, reread authoritative state, and return the existing/terminal outcome; never blindly retry the insert or provider. Unique constraints protect even when another worktree bypasses application prechecks. [VERIFIED: existing advisory-lock/CAS pattern in `src/repositories/policy_corpus_repo.py`; CITED: https://www.postgresql.org/docs/current/explicit-locking.html; CITED: https://www.postgresql.org/docs/current/ddl-constraints.html]

Recommended global lock order is: evidence rollout singleton → tenant advisory lock → corpus rollout row → source manifest → candidate → execution authority → prior reservation/result. Do not use `SKIP LOCKED`: authority contention must wait or refuse, never silently choose another ordinal. [RECOMMENDATION derived from existing repository lock order and D-03/D-12]

### Pattern 3: Trusted time and strict expiry

Read `clock_timestamp()` from PostgreSQL for issue/reserve/immediate dispatch checks; `CURRENT_TIMESTAMP`/`now()` is the transaction-start time and can be stale within a long transaction. Persist all prerequisite expiries and set the authority expiry to their minimum; validate `db_now < every_expiry` (equality fails). Operator `--generated-at` remains evidence metadata only. [CITED: https://www.postgresql.org/docs/current/functions-datetime.html; VERIFIED: current CLI accepts generated time; D-10/D-11]

### Pattern 4: Deterministic request envelope

For each build subject freeze ordered input hashes/count, batch size 10, `ceil(input_count / batch_size)`, provider/model/dimensions, SDK retries 0, and exactly one outer attempt per reservation. For A/B freeze both roles, all three formats, exact sealed source/Gold/baseline hashes, candidate/incumbent IDs, query count, deterministic ingestion batch upper bound, and the same retry settings. Execution-time source inspection corrected the research count: 54 is the one-role format-expanded metric-case count, while retrieval embeds each original question plus deterministic rewrites. The sealed set has 18 originals and exactly three single-expansion rewrites, giving `2 roles × 3 formats × 21 query embeddings = 126`, plus deterministically precomputed ingestion batches. The production envelope calculator and test must enumerate every original/rewrite provider call site rather than trust a hand-maintained constant. [VERIFIED: `src/knowledge/retrieval.py`; `src/knowledge/rewrite.py`; `src/rag/evaluation/retrieval_rounds.py`; Phase 64.3 sealed dataset]

`AsyncOpenAI(max_retries=0)` is already used, but `EmbeddingService` has its own outer retry loop and the A/B constructor currently receives its default. Set the reviewed per-reservation outer attempt count explicitly to one and bind it in the envelope. [VERIFIED: `src/rag/embedder.py`; `scripts/eval_rag_token_chunk_ab.py`]

### Pattern 5: Crash/result reconciliation

- Reservation commit succeeds, then process dies: ordinal remains spent; no result is synthesized and no provider retry is permitted. [VERIFIED: D-05/D-06]
- Candidate/report/result transaction commits, then file projection dies: reread DB by reservation ID, verify hashes, and create the missing V2 projection without provider access. [VERIFIED: D-04/D-08]
- Candidate/report commits but result row is missing: reconciliation may create the result only when immutable DB state proves the exact reservation output; otherwise mark/return ambiguous and stop. Prefer committing output projection and result in the same transaction to make this exceptional path unreachable. [RECOMMENDATION derived from D-06/D-08]
- Provider returned only in process memory and persistence failed: the ordinal is spent and the output is not recreated. [VERIFIED: D-06]
- Ordinal two requires an immutable result-one row with an allowlisted transient/unavailable code and byte-identical authority/envelope bindings. Unknown, response, projection, quality, safety, config, parity, and source failures are terminal. [VERIFIED: D-07/D-20]

### Anti-Patterns to Avoid

- File existence, artifact UUIDs, CLI flags, environment values, or copied roots as authority. [VERIFIED: D-01/D-04]
- Holding a transaction across network provider work, or nesting reservation under a transaction that later persists candidate/report data. [VERIFIED: D-05]
- Mutable reservation status that can return a row to “available,” lease stealing, timeout recycling, or deletion-based reset. [VERIFIED: D-06]
- Application-only `SELECT`-then-insert checks without a unique constraint. [VERIFIED: D-03]
- Reusing Phase 64.4 descriptors/budgets/candidate/parity, using operator time for freshness, or minting authority from V1 loaders. [VERIFIED: D-09/D-11/D-26]
- Re-enabling direct helpers or legacy `build-next`, or hiding a bypass behind a test seam. [VERIFIED: D-15]

## Common Pitfalls

1. **Reservation rollback through outer session:** a nested reservation inside the current long transaction disappears when provider/persistence fails. Make reserve-and-commit its own session boundary and assert visibility from a second connection before any provider constructor. [VERIFIED: current build transaction shape; D-05]
2. **TOCTOU before construction:** issue-time validation is insufficient. Lock/recheck every binding with fresh DB time immediately before constructing the client; constructor follows the check in the same short critical section, and network work begins only after commit. [VERIFIED: D-10..D-12]
3. **Ordinal-two drift:** checking only previous failure class permits retry under changed source/config/parity. Compare the complete immutable authority and envelope, under lock, before inserting ordinal two. [VERIFIED: D-07]
4. **Incomplete envelope:** counting logical “A/B executions” while SDK/wrapper batching/retry multiplies HTTP calls defeats the cap. Test the real call graph and assert actual count never exceeds the DB envelope. [VERIFIED: `src/rag/embedder.py`; D-08]
5. **Receipt authority inversion:** a valid copied JSON chain cannot authorize activation. Derive V2 files from committed DB history/lineage; leave V1 bytes/loaders untouched. [VERIFIED: D-04/D-23/D-26]
6. **Review gate bundled with live dispatch:** keep the hard-disable until independent review/security/concurrency/bypass evidence is clean; any real finding returns to bounded fixes and re-review. [VERIFIED: D-13..D-16]
7. **Unsafe downgrade:** dropping nonempty authority tables erases the spent-ticket record and can recreate budget. Downgrade must refuse while any authoritative execution/receipt row exists. [VERIFIED: D-25]
