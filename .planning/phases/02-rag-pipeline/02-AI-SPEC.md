## 1. System Classification

**System Type:** RAG / Knowledge Q&A

**Description:**
中文电商退款规则知识库检索系统。将退款规则、客服 SOP、商家 FAQ 等 Markdown 文档按标题结构切块，通过 DashScope text-embedding-v4 生成向量，存入 pgvector，提供带元数据过滤、置信度分层和 citation 校验的检索端点。下游 Phase 3 LangGraph Agent 通过 tool call 调用此检索服务获取证据。

**Critical Failure Modes:**
1. 编造规则：检索无结果时仍返回看似合理但不存在的退款规则（hallucination）
2. 引用幽灵证据：返回的 doc_id/chunk_id 在检索结果中不存在（citation fabrication）
3. 跨租户泄露：返回其他租户的规则文档（tenant isolation breach）
4. 规则混淆：一个 chunk 混入多条不相关规则，导致 Agent 引用错误条款（chunking corruption）
5. 静默降级：embedding API 失败时不报错，导致文档入库不完整（silent ingestion failure）

## 1b. Domain Context

> Grounds the evaluation strategy in domain expert knowledge.

**Industry Vertical:** E-commerce / Customer Service Operations

**User Population:** 平台客服人员和商家运营人员，在处理退款纠纷时查询规则依据。日常使用场景：客户投诉 → 客服查询适用规则 → 引用规则给出处理建议。

**Stakes Level:** Medium-High

**Output Consequence:** 检索结果直接影响 Agent 给出的退款处理建议。错误的规则引用可能导致：不当退款（平台损失）、拒绝合理退款（用户投诉升级）、违反平台政策（合规风险）。

### What Domain Experts Evaluate Against

| Dimension | Good (expert accepts) | Bad (expert flags) | Stakes |
|-----------|----------------------|-------------------|--------|
| 规则匹配准确性 | 返回的规则条款与用户问题直接相关，能作为处理依据 | 返回无关规则或相似但不适用的条款（如退货规则用于仅退款场景） | 错误处理导致资损或投诉 |
| 条款完整性 | 返回完整的单条规则，包含适用条件和处理方式 | 规则被截断，缺少关键限制条件或例外情况 | 客服遗漏关键约束 |
| 时效性 | 返回当前生效的规则版本 | 返回已废止或未生效的规则 | 按过期规则处理 |
| 证据可追溯 | 每条引用都能定位到具体文档和段落 | 无法确认引用来源，或来源不存在 | 审计和申诉时无法举证 |
| 无证据识别 | 明确告知"知识库中没有相关规则" | 用通用知识编造回答 | 误导客服做出无依据决策 |

### Known Failure Modes in This Domain

1. **规则边界混淆**：退款规则按商品类型、金额区间、时间窗口有不同适用条件，检索可能返回相似但不适用的规则（如"七天无理由"规则被用于定制商品）
2. **SOP 与规则冲突**：SOP 描述操作流程，规则描述判定标准，两者可能返回看似矛盾的内容（如 SOP 说"先退款后追责"但规则说"需审批"）
3. **部分匹配误导**：查询涉及多个条件时（如"已发货+仅退款+超过7天"），检索可能只匹配部分条件的规则
4. **FAQ 噪声**：FAQ 内容通俗但不精确，可能与正式规则措辞不同导致重复或矛盾结果

### Regulatory / Compliance Context

- 电商平台退款规则需符合《消费者权益保护法》和《电子商务法》相关规定
- 本系统为内部辅助工具，不直接面向消费者，合规风险主要在于内部操作是否符合平台已发布的规则
- MVP 阶段使用模拟数据，无真实合规约束；但规则文档内容应反映真实业务逻辑

### Domain Expert Roles for Evaluation

| Role | Responsibility |
|------|---------------|
| 高级客服主管 | Golden set 标注：判断检索结果是否为正确的处理依据 |
| 规则运营专员 | 规则文档质量审核：确认切块后规则完整性和准确性 |
| 风控审核员 | 边界 case 标注：高风险场景的 expected chunks 标注 |

## 2. Framework Decision

**Selected Framework:** Direct (openai Python SDK + SQLAlchemy/pgvector + custom chunker)

**Version:**
- `openai` >= 1.30 (Python SDK, OpenAI-compatible endpoint)
- `pgvector` 0.3.x (SQLAlchemy integration)
- `sqlalchemy` 2.0.x (already in project)

**Rationale:**
CONTEXT.md 定义了高度定制化的切块策略（Markdown heading-based, 稳定 ID, 二次切割）、精确的置信度分层逻辑（三级阈值）和结构化检索合约。这些规格太具体，任何 RAG 框架（LlamaIndex/LangChain）都需要大量 override 才能匹配，反而增加复杂度。Direct 方案：
1. 切块逻辑完全自定义，无框架抽象泄漏
2. Embedding 通过 openai SDK 调用 DashScope OpenAI-compatible API，一行代码切换
3. pgvector 检索直接用 SQLAlchemy，与现有 repository pattern 一致
4. Phase 3 LangGraph Agent 通过 FastAPI endpoint 调用，解耦清晰

**Alternatives Considered:**

| Framework | Ruled Out Because |
|-----------|------------------|
| LlamaIndex | 切块策略（heading-based + 稳定 ID + 二次切割）需要完全自定义 NodeParser；pgvector 集成需要绕过其 VectorStore 抽象来匹配现有 SQLAlchemy models；获得的 RAG eval 指标（faithfulness/relevance）在 Phase 2 不需要（Phase 2 只做 Hit@5） |
| LangChain | TextSplitters 不支持 Markdown heading-based + 稳定 ID 生成；pgvector integration 与现有 SQLAlchemy models 不兼容；Phase 3 会引入 LangGraph，但 retriever 作为独立 tool 调用更解耦 |

**Vendor Lock-In Accepted:** Partial — DashScope embedding API 使用 OpenAI-compatible 接口，切换到其他 embedding provider 只需改 base_url 和 model name。pgvector 锁定 PostgreSQL，但项目已选定 Postgres。

## 3. Framework Quick Reference

> Distilled for this specific use case: DashScope embedding + pgvector retrieval.

### Installation
```bash
uv add openai pgvector sqlalchemy[asyncio] asyncpg
```

### Core Imports
```python
from openai import AsyncOpenAI
from pgvector.sqlalchemy import Vector
from sqlalchemy import select, text
from sqlalchemy.ext.asyncio import AsyncSession
```

### Entry Point Pattern
```python
import os
from openai import AsyncOpenAI

client = AsyncOpenAI(
    api_key=os.environ["DASHSCOPE_API_KEY"],
    base_url="https://dashscope.aliyuncs.com/compatible-mode/v1",
)

async def embed_texts(texts: list[str]) -> list[list[float]]:
    response = await client.embeddings.create(
        model="text-embedding-v4",
        input=texts,
        dimensions=1024,
    )
    return [item.embedding for item in response.data]

async def search_chunks(
    session: AsyncSession,
    query_embedding: list[float],
    tenant_id: str,
    top_k: int = 5,
    min_score: float = 0.55,
) -> list[dict]:
    sql = text("""
        SELECT chunk_id, section, content, doc_id,
               1 - (embedding <=> :embedding::vector) AS score
        FROM policy_chunks
        WHERE tenant_id = :tenant_id
          AND 1 - (embedding <=> :embedding::vector) >= :min_score
        ORDER BY embedding <=> :embedding::vector
        LIMIT :top_k
    """)
    result = await session.execute(sql, {
        "embedding": str(query_embedding),
        "tenant_id": tenant_id,
        "min_score": min_score,
        "top_k": top_k,
    })
    return [dict(row._mapping) for row in result]
```

### Key Abstractions

| Concept | What It Is | When You Use It |
|---------|-----------|-----------------|
| `openai.AsyncOpenAI` | OpenAI-compatible async client | Embedding generation (ingestion + query-time) |
| `pgvector <=>` operator | Cosine distance operator | Vector similarity search in SQL |
| HNSW index | Approximate nearest neighbor index | Speed up vector search at scale |
| `Vector(1024)` | SQLAlchemy column type | Store 1024-dim embeddings in PostgreSQL |

### Common Pitfalls
1. **Batch size 超限**：DashScope 硬限制 max 10 texts/request，超过会 400 error。必须在 ingestion 时分批。
2. **Cosine distance vs similarity**：pgvector `<=>` 返回 distance（0=相同），需要 `1 - distance` 转换为 similarity score。
3. **Vector dimension mismatch**：当前 models.py 定义 `Vector(1536)`，但 text-embedding-v4 默认 1024 维。需要 migration 修正。
4. **中文 token 计算**：8192 token/row 限制对中文约等于 4000-6000 字符，超长 chunk 需要在切块阶段控制。
5. **Async client in sync context**：ingestion CLI 如果用 sync 入口，需要 `asyncio.run()` 包装或使用同步 `OpenAI` client。

## 4. Implementation Guidance

**Model Configuration:**
- Embedding model: `text-embedding-v4` (DashScope)
- Dimensions: 1024
- Base URL: `https://dashscope.aliyuncs.com/compatible-mode/v1`
- Max tokens per text: 8,192
- Batch size: 10 (硬限制)

**Core Pattern:**
Ingestion pipeline: `Markdown files → Heading-based chunker → Batch embedder → pgvector upsert`
Query pipeline: `User query → Single embed → pgvector cosine search → Confidence scoring → Structured response`

**Tool Use:**
- Phase 2 不涉及 LLM tool calling
- Retriever 作为 FastAPI endpoint 暴露，Phase 3 Agent 通过 HTTP tool call 调用
- Ingestion 通过 CLI script 执行（INFR-06）

**State Management:**
- 无会话状态（stateless retrieval）
- 文档版本通过 `policy_documents.version` + `effective_date` 管理
- Ingestion 幂等性通过 delete-and-reinsert per document 实现

**Context Window Strategy:**
- 不适用（Phase 2 无 LLM 对话）
- Chunk 大小控制在 400-800 中文字符（目标），最大 1200-1500
- 确保单个 chunk 不超过 embedding model 的 8192 token 限制

## 4b. AI Systems Best Practices

> Cross-cutting patterns for this RAG pipeline.

### Structured Outputs with Pydantic

```python
from pydantic import BaseModel, Field

class EvidenceItem(BaseModel):
    doc_id: str
    chunk_id: str
    title: str
    section: str
    score: float = Field(ge=0.0, le=1.0)
    text: str

class RetrievalResult(BaseModel):
    query: str
    retrieval_status: str = Field(pattern="^(strong_evidence|partial_evidence|no_evidence)$")
    evidence: list[EvidenceItem]
    best_score: float
    fallback_message: str | None = None

class CitationValidation(BaseModel):
    is_valid: bool
    invalid_citations: list[str] = Field(default_factory=list)
    reason: str | None = None
```

### Async-First Design

- Embedding client 使用 `AsyncOpenAI`，ingestion 时并发批次处理
- Retrieval endpoint 使用 async SQLAlchemy session
- Ingestion CLI 可用 `asyncio.run()` 包装 async 逻辑，或使用 sync `OpenAI` client（简单场景）
- 常见错误：在 async endpoint 中使用 sync embedding client 导致 event loop 阻塞

### Prompt Engineering Discipline

- Phase 2 不涉及 LLM prompt（纯检索）
- 但 embedding query 的质量影响检索效果：
  - 用户原始问题直接作为 embedding input（不做 query rewriting，Phase 2 scope）
  - 未来可加 query expansion（Phase 3+ 由 Agent 决定是否改写 query）

### Context Window Management

- Chunk 大小策略：400-800 中文字符（目标），1200-1500（硬上限）
- 超长 section 二次切割时保留 parent title + section path 作为 context
- Overlap 仅在同 section 内使用（80-150 字符），避免跨规则污染
- Top-5 返回策略：最多 5 个 chunks × ~800 字符 = ~4000 字符 context 给下游 Agent

### Cost and Latency Budget

- Embedding cost: DashScope text-embedding-v4 约 ¥0.0007/1000 tokens
- Ingestion: 15-30 docs × ~20 chunks/doc = 300-600 chunks，单次 ingestion < ¥1
- Query-time: 单条 embedding + pgvector search，预期 < 200ms（embedding ~100ms + DB ~50ms）
- 无 caching（Phase 2 scope），Phase 3+ 可加 Redis 缓存热门 query

## 5. Evaluation Strategy

### Dimensions

| Dimension | Rubric (Pass/Fail) | Measurement Approach | Priority |
|-----------|-------------------|---------------------|----------|
| Hit@5 | Pass: ≥1 expected_chunk_id in top-5 results; Fail: none found | Code-based (exact match) | Critical |
| Fallback accuracy | Pass: no_evidence query returns retrieval_status=no_evidence; Fail: returns high-confidence unrelated results | Code-based (status check + score threshold) | Critical |
| Citation metadata completeness | Pass: every evidence item has non-null doc_id, chunk_id, title, section, score; Fail: any field missing | Code-based (schema validation) | High |
| Tenant isolation | Pass: results only contain chunks with matching tenant_id; Fail: cross-tenant leakage | Code-based (assertion) | Critical |
| Confidence scoring accuracy | Pass: score ≥0.70 → strong, 0.55-0.70 → partial, <0.55 → filtered; Fail: status/score mismatch | Code-based (threshold logic) | High |
| Chunk quality | Pass: chunk contains complete single rule/procedure; Fail: truncated mid-sentence or mixed rules | Human review (sampling) | Medium |

**Primary Tool:** Custom eval script (`scripts/eval_rag_hit_at_5.py`) + Arize Phoenix (tracing)

### Reference Dataset

**Size:** 12-14 examples (Phase 2 baseline; expanded to 25-40 in Phase 6)

**Composition:**
- 退款规则直接匹配: 5 queries（七天无理由、质量问题、已发货仅退款等）
- SOP 流程查询: 3 queries（客服处理步骤、升级流程）
- FAQ 匹配: 2 queries（常见商家问题）
- 边界/多条件: 2 queries（跨规则条件组合）
- No-evidence fallback: 2 queries（超出知识库范围的问题）

**Labeling:**
- Phase 2: 开发者手工标注 expected_doc_ids + expected_chunk_ids（基于已知文档结构）
- Phase 6: 扩展时由 LLM 生成候选 + 人工审核确认

## 6. Guardrails

### Online (Real-Time)

| Guardrail | Trigger | Intervention |
|-----------|---------|--------------|
| No-evidence fallback | best_score < 0.55 | Block: 返回 fallback message，禁止 Agent 用通用知识回答 |
| Citation validator | cited chunk_id not in retrieval results | Block: 标记回答为 invalid，要求 Agent 重新生成 |
| Tenant isolation | query without valid tenant_id | Block: 返回 401/403，不执行检索 |
| Embedding API failure | DashScope 返回 4xx/5xx | Escalate: 返回 service_unavailable error，不返回空结果 |

### Offline (Flywheel)

| Metric | Sampling Strategy | Action on Degradation |
|--------|------------------|----------------------|
| Hit@5 score | 每次 golden set 变更后全量运行 | Hit@5 < 80% → 检查 chunking 质量或 embedding 模型变更 |
| Fallback false positive | 抽样检查 no_evidence 响应 | 频繁误判 → 调低 min_similarity_threshold |
| Chunk coverage | 新文档入库后检查 chunk 数量和大小分布 | 异常大/小 chunks → 检查 chunker 逻辑 |

## 7. Production Monitoring

**Tracing Tool:** Arize Phoenix (open-source, local deployment)

**Key Metrics to Track:**
1. Embedding API latency (p50, p95, p99)
2. Retrieval latency (query → results returned)
3. Hit@5 score (periodic golden set evaluation)
4. Ingestion success rate (chunks embedded / chunks attempted)
5. Score distribution (daily histogram of retrieval scores)

**Alert Thresholds:**
- Embedding API latency p95 > 2000ms → investigate DashScope status
- Ingestion failure rate > 5% → check API key / quota
- Hit@5 drops below 75% → chunking or embedding regression

**Smart Sampling Strategy:**
- Phase 2 为内部工具，暂无 production traffic
- 开发阶段：每次 ingestion 后自动运行 golden set eval
- Phase 3+ 集成后：对 retrieval_status=no_evidence 的 query 100% 记录，用于扩展 golden set
