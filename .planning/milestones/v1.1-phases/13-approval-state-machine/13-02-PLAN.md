## Spec Consistency Findings

- Implemented fact: current `ApprovalRequest` is a single status row with `proposed_action`, `decision`, and `ApprovalStep`; it has no v2 revision/version/hash fields and no level/assignment/decision/event tables.
- Target contract: `docs/contract-spec.md` Section 18.2 defines request/level/assignment/decision/event ownership and cross-table enforcement. `docs/contract-spec.md` Section 15.3 defines `action_safety_snapshots`.
- MVP scope for this plan: create compatible schema and tests. It does not implement transition behavior; Plan 03 owns service writes.
- Schema reconciliation: `approval_requests.risk_level` and `approval_requests.risk_rule_ref` are required now because Plan 03 approval policy writes and Phase 14/17 draft/execution guards need the original risk context.
- Schema reconciliation: `approval_decisions.response_text` and `approval_decisions.edited_action_json` are required in Plan 02, even though Plan 05 implements `respond`/`edit`, so migration 008 does not need a same-phase rewrite.
- Schema reconciliation: `approval_events` must satisfy both Section 18.2 audit fields and the Phase 10 minimal envelope. Include `actor_id` and `metadata_json` for spec compatibility, and include `resource_refs_json` plus `redacted_payload_json` for redacted replay/resource refs.
- Constraint reconciliation: migration 008 must not stop at field existence. It must add executable constraints for unique `(tenant_id, immutable_hash)`, unique `(tenant_id, run_id, revision)`, unique `(approval_request_id, level_number)`, active-revision/active-decision partial uniques, `any_one` winning-accept protection, and status/decision-type check constraints so later Phase 14/15/17 work does not reopen the Phase 13 schema.

## Architecture Alignment

Canonical owner package: `src/approvals`; schema owner: `src/db/models.py` plus Alembic migration `008_approval_state_machine`.
Old-path strategy: v1 `approval_requests` and `approval_steps` stay compatibility/display data and are marked non-executable when v2 hashes/levels/assignments are missing.
Forbidden imports: routers and graph nodes must remain callers only and must not write target rows directly.
Boundary tests: Plan 13-07 verifies callers cannot keep using legacy transition paths after the schema/service cutover.
Non-overlap: Phase 13 creates approval/snapshot/event schema only; Phase 14 owns action draft/executor binding; Phase 15 owns replay enrichment and scanner enablement; Phase 16 owns memory; Phase 17 owns external execution.
This plan creates target rows first so Plan 03 can enforce transactions instead of extending v1 single-row transitions.

## Migration / Read-Switch / Rollback

- Before applying Phase 13 migration tests, run `uv run alembic upgrade head` because research found local current `005_approval_tables` and repo head `007_session_memories`.
- New v2 columns on `approval_requests` are nullable for historical v1 rows but required by service for new active v2 rows.
- Legacy v1 rows must be backfilled with deterministic per-run revisions, not a constant revision. For each `(tenant_id, run_id)` group, assign `revision = row_number() over (partition by tenant_id, run_id order by created_at, id)` and keep every such row `legacy_non_executable=true`.
- Read-switch owner: `src/approvals/repository.py` in Plan 03.
- Fallback: legacy v1 rows may be listed, rejected, cancelled, expired, or superseded, but cannot authorize action.
- Rollback: Alembic downgrade drops new target tables and v2 columns/indexes; no external side effects are introduced.
- Report fields: `alembic_current_before`, `alembic_head_before`, `legacy_v1_count`, `legacy_non_executable_count`, `read_switch_owner`, `fallback_behavior`, `rollback_command`, `verification_commands`.

`approval_decisions.approval_assignment_id -> approval_assignments.id -> approval_levels.approval_request_id -> approval_requests.id` must match the same `tenant_id`, `run_id`, `thread_id`, `request_revision`, `request_version`, `level_version`, and `assignment_version` in one transaction before a decision/event is inserted.

Required mismatch tests:
- wrong assignment id for level.
- wrong level id for request.
- wrong tenant id.
- wrong run id.
- wrong revision.
- stale request version.
- stale level version.
- stale assignment version.
- rollback leaves no `approval_decisions` or `approval_events` rows.
