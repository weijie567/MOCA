<objective>
Build the Phase 10 investigate loop on top of a unified tool dispatch layer, not node-local service branching. The deliverable is:

1. `UnifiedToolManager`: one registry/dispatch facade that exposes the §12.4 investigate allowlist, validates descriptors, routes to business/knowledge/future-memory executors, normalizes every result to `ToolResultV2`, and returns declared-but-unavailable tools through the same path.
2. `investigate`: a single registered node running a bounded, read-only, one-tool-per-iteration loop. The node owns loop control, planner decisions, state accumulation, event emission, and termination, but it does not know how each tool is implemented.
3. Tests proving the guardrails and the unified dispatch contract are executable, not prose.

Purpose: This keeps Phase 10 aligned with the xiaozhi-style unified tool architecture: many executor types may exist, but the agent sees one tool manager for descriptor discovery and execution. Phase 9 `BusinessToolService` remains the business executor dependency; it is no longer the node-facing dispatcher. Policy/RAG and future case-memory tools are routed through the same manager abstraction.
</objective>

## Unified Tool Manager Contract

Add `src/agent/tools/unified.py` with:

- `UnifiedToolResult`: thin local wrapper or direct alias around `ToolResultV2` plus `descriptor` access. Outward execution result remains `ToolResultV2`.
- `ToolExecutor` protocol:
  - `get_tools() -> dict[str, ToolDescriptor]`
  - `has_tool(name: str) -> bool`
  - `execute(name: str, args: dict[str, Any], ctx: ToolCallContext) -> ToolResultV2`
- `BusinessToolExecutor`: wraps `BusinessToolService.with_default_registry(session)` and delegates `get_order`, `get_refund_case`, `get_ticket`, `get_logistics`, `get_merchant_risk` to `BusinessToolService.invoke_tool(...)`.
- `KnowledgeToolExecutor`: owns `search_policy` now and may declare `search_sop` as unavailable if no adapter exists. It builds `KnowledgeSearchRequest` / `KnowledgeContext` from `ToolCallContext`, calls `PolicyKnowledgeService.search(...)`, and adapts the result to `ToolResultV2` with `status` mapped as:
  - `strong_evidence` / `partial_evidence` -> `success`
  - `no_evidence` -> `not_found`
  - `error` -> `error`
  It must put policy refs in `policy_evidence_refs`, never `business_fact_refs`.
- `MemoryToolExecutor`: optional empty executor in this phase; declares `search_case_memory` as unavailable through the same result shape. Do not implement MemoryService.
- `UnifiedToolManager.with_defaults(session)` wires the executors and descriptor source.
- `UnifiedToolManager.descriptors(caller_node="investigate")` returns only descriptors allowed for the caller and suitable for planner prompt/tool selection.
- `UnifiedToolManager.invoke(name, args, ctx) -> ToolResultV2` performs this logical order:
  1. tool exists in unified descriptor map, else `not_found`;
  2. descriptor `caller_allowlist` contains `ctx.caller_node`, else `permission_denied`;
  3. descriptor is not write and side effect is read-only/retrieval, else `permission_denied`;
  4. `descriptor.required_permission in ctx.permissions`, else `permission_denied`;
  5. input schema validation, else `invalid_request`;
  6. matching executor exists and has adapter, else `unavailable`;
  7. executor returns `ToolResultV2`, else `invalid_response`.
- Canonical `ToolResultV2.status` semantics are fixed at the manager boundary:
  - `permission_denied` -> fine-grained permission-denied branch; denied resource stays out of facts;
  - `not_found` -> missing fact / no evidence for the requested resource;
  - `unavailable` -> declared but non-backed tool; not fatal by itself;
  - `invalid_request` -> planner/tool-input bug;
  - `invalid_response` -> executor contract bug;
  - `error` -> runtime/tool failure.
- The manager is the primary source for event family via descriptor metadata. Plan-02 `classify_event_family` may be used only as a fallback when descriptor `event_family` is missing, and tests must prove both sources agree for every §12.4 tool.

## Drift-prevention contract

- `UnifiedToolManager` is the only node-facing tool registry and dispatch path for `investigate`.
- Phase 10 treats `src.business_tools.registry.ToolRegistry().descriptors()` as the temporary canonical descriptor catalog for all §12.4 tools. Do not introduce a second descriptor table or duplicate descriptor schema in this phase. A later cleanup may move descriptor declarations to a neutral `src/agent/tools/catalog.py` while preserving backward-compatible imports for `BusinessToolService`.
- `BusinessToolService` is an executor-internal business facade only. It may keep defensive merchant-scope, permission, and per-tool retry checks, but it must not become a planner-visible registry, maintain an independent investigate allowlist, change descriptor semantics, or emit a competing status taxonomy.
- Retry ownership is split: `BusinessToolService` may perform per-tool adapter retries using the per-call `ToolCallContext.max_attempts`; `investigate` owns passing that cap into tool contexts plus loop-level `max_iterations`, deadline handling, and termination_reason mapping when attempts/deadline are exhausted.

The node-facing rule is strict: `investigate.py` may import `UnifiedToolManager`, `ToolCallContext`, `ToolResultV2`, and event helpers. It must not import `BusinessToolService`, `PolicyKnowledgeService`, raw `get_*` tools, `search_policy`, `src.agent.tools.registry`, or call `BusinessToolService.fetch_context` directly.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| planner output -> tool execution | Planner may request only one tool per iteration and only from manager-visible investigate descriptors. |
| tool manager -> executor | Manager enforces allowlist, permission, schema, and write blocking before executor dispatch. |
| executor output -> state | Only normalized ToolResultV2 enters accumulation; raw executor data never becomes trace/event payload. |
| denied resource -> facts/reply path | Denied resource data must not enter facts and must be dependency-mapped for routing suppression. |
| loop iteration -> resource consumption | max_iterations, deadline_at, and max_attempts bound the loop. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-10-11 | Elevation of Privilege | planner selects write/unknown tool | mitigate | UnifiedToolManager descriptor allowlist + write blocking before executor dispatch; investigate tests assert manager not called for invalid planner output. |
