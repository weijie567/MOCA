Reference used per D-01: classify first, then route to clarification when needed.
Reference used per D-02: structured `ClarificationRequest` shape, no free-string route parsing.
Reference used per D-03: `agent-inbox` boundary idea; ordinary clarification is separate from approval respond/decision lifecycle.
Reference excluded per D-04/D-05/D-16: email prompts, free tool loop, and memory-updated triage preferences.
Safety constraint per D-11/D-14/D-16: ordinary chat cannot create `approval_result`, resume commands, trusted approval versions, or trusted approval decisions.

Target clarification shape from `docs/contract-spec.md` §11.5:
```json
{
  "reason": "missing_required_slots",
  "clarification_request_id": "clarify_123",
  "questions": ["请提供订单号或退款单号。"],
  "blocked_nodes": ["investigate", "action_draft"],
  "resume_policy": "same_thread_only"
}
```
`blocked_nodes` values are contract-level blocked path labels; matching runtime nodes may not all exist yet. Clarification should block investigation plus action/risk/approval-like paths where applicable.

Graph handoff constraint: the live graph keeps `clarification_gate -> final_response`. Therefore `final_response` must detect `clarification_request` and preserve the upstream safe clarification response candidate, including the first question, instead of applying recommendation/approval/action templates. This avoids erasing the ordinary clarification text after the gate has done the safe filtering.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| route -> clarification response | Router reasons become user-visible questions. |
| graph state -> final_response candidate | State may contain errors or denied resources that must not leak; final_response must preserve safe clarification text when clarification_request exists. |
| ordinary clarification -> approval lifecycle | Ordinary chat must stay separate from trusted approval respond/needs_info resume. |
