## Questions And Decisions

### 1. Merchant API Helper Placement

Question: Where should the unified `require_merchant_access(...)` helper live?

Options presented:

1. `src/auth/permissions.py` (recommended) - close to `get_current_user` / `require_roles`, low change surface.
2. New `src/api/authorization.py` - API-specific, but introduces a new module boundary.
3. New `src/domain/access.py` - more domain-oriented, but too heavy for Phase 29.5.

Decision: Option 1, `src/auth/permissions.py`.

User rationale: This is close to `get_current_user`, lets `orders.py`, `refund_cases.py`, and `tickets.py` reuse it directly, and avoids turning Phase 29.5 into a larger authorization architecture refactor.

### 2. Server Merchant Scope Override Failure Mode

Question: How should non-admin wildcard `server_merchant_scope` fail?

Options presented:

1. `TrustedContextFactory.create_from_request(...)` raises `ValueError` (recommended).
2. Raise `HTTPException(403)` directly.
3. Silently narrow.

Decision: Option 1, raise `ValueError`.

User rationale: Platform layer should not depend on FastAPI HTTP semantics. Routes can translate to 403 where needed, and tests can assert the exception directly. This matches the locked reject-not-narrow decision.

### 3. KnowledgeService Policy-Only Behavior

Question: How should `merchant_scope=[]` interact with tenant public policy search?

Options presented:

1. Move the empty-scope early return so only business/merchant-specific filters are denied (recommended).
2. Completely ignore merchant scope for policy search.
3. Block users missing merchant binding from all search.

Decision: Option 1.

User rationale: This directly fixes the known `src/knowledge/service.py` empty-scope no-evidence issue. Policy-only tenant public policy should proceed, while business-scoped or merchant-specific policy filters still deny. Ignoring merchant scope entirely would create a future merchant-specific policy risk.

### 4. Approval Admin-Only Interim

Question: How should Phase 29.5 implement manager approval admin-only / fail-closed behavior?

Options presented:

1. Remove `manager` from `APPROVAL_ROLES` (recommended).
2. Keep `APPROVAL_ROLES` and hand-write manager denies in each endpoint.
3. Only fix approval resume wildcard and leave list/get behavior unchanged.

Decision: Option 1, remove `manager` from `APPROVAL_ROLES`.

User rationale: One role set change is clearer and less leak-prone. This matches the locked admin-only decision; Phase 34 can restore scoped manager reviewer behavior.

### 5. Investigate Trusted Config Fallback

Question: What should happen when `investigate.py` cannot build trusted config?

Options presented:

1. Fail closed: no visible tools / no business tool execution (recommended).
2. Construct deny-all merchant scope but continue policy-only tools.
3. Keep wildcard fallback.

Decision: Option 1, fail closed.

User rationale: This matches Phase 27's decision that missing/invalid trusted context fails closed. Option 2 would unnecessarily couple graph fail-closed behavior to KnowledgeService policy-only behavior.

### 6. Seed And Test Migration Order

Question: In what order should seed, fixtures, code, and tests be migrated?

Options presented:

1. Fixtures/seed first, then production code, then old test expectation updates (recommended).
2. Code first, then repair tests one by one.
3. Only add new tests, leaving old tests unchanged.

Decision: Option 1.

User rationale: Permission model migration should expose real impact early. Binding support/manager users in seed/fixtures first prevents unbound fixture noise from obscuring true permission failures.
