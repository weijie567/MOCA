## Trust Boundaries

| Boundary | Description | Data Crossing |
|----------|-------------|---------------|
| JWT/authenticated user to `TrustedContextFactory` | Persisted user role and merchant binding become the authoritative runtime tenant, permission, and merchant scope. | User id, tenant id, role, merchant id, verified token scopes |
| Server overrides to trusted context | Server-provided tool permissions and merchant scope can only narrow or add tool permissions under explicit controls. | `server_tool_permissions`, `server_merchant_scope` |
| API routers to business resources | Order, refund case, and ticket routes cross from tenant-scoped HTTP identity into merchant-owned records. | Route ids, tenant id, resource merchant id, HTTP 403/404 decisions |
| Tool platform to raw demo business reads | Agent/tool execution crosses into demo business repositories and must recheck persisted user authority. | `ToolCallContext`, tenant id, user id, role, merchant-owned business rows |
| Knowledge and memory retrieval | Tenant-public policy retrieval is separated from merchant-scoped business/case-memory retrieval. | Knowledge filters, merchant filters, memory scopes |
| Approval and run visibility surfaces | Approval review/resume and AgentRun status/evidence/trace/replay expose sensitive operational state. | Approval requests, decisions, run status, evidence refs, trace timelines, replay events |
| Agent graph to tool execution | Investigate converts trusted context into visibility and runtime tool contexts; legacy state/config cannot be authoritative. | Trusted context, legacy AgentState identity, planner-visible tool views |
| Production wildcard construction | Wildcard merchant scope is a privileged platform-admin construct and is statically guarded outside the factory. | Source AST patterns for `merchant_ids=["*"]` and wildcard `server_merchant_scope` |
