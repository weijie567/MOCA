# Golden Set Matching Rules

## Purpose

Defines how Chinese queries in the golden set map to agent intents and routing paths.
These rules serve both FakeLLM deterministic routing and eval case scoring.

## Intent Routing Keywords (Chinese -> Intent)

| Intent | Trigger Keywords (any match) | Examples |
|--------|------------------------------|----------|
| normal_policy_qa | 规则, 政策, 规定, 标准, 流程, 怎么办, 什么情况 | "退款超时规则是什么？" |
| refund_troubleshooting | 退款, 退货, 进度, 卡在, 状态, 为什么没退, 查一下 | "订单ORD-2024-002退款进度如何？" |
| compensation_suggestion | 补偿, 赔付, 赔偿, 补贴, 给.*元, 要求.*块 | "客户要求补偿600元" |
| permission_denied | 权限不足, 无权, 403, token, 没有agent:chat权限 | "没有agent:chat权限的用户想查询订单" |

The runtime classifier currently uses `policy_qa`, `refund_troubleshooting`,
`compensation_suggestion`, `approval_request`, and `unknown`. The golden-set
category `normal_policy_qa` maps to the runtime intent `policy_qa`.

## Risk Level Keywords (Chinese -> Risk Assessment)

| Risk Level | Trigger Patterns | Threshold |
|------------|------------------|-----------|
| high | 补偿/赔付/赔偿 + 金额 > 500 | HR-01: amount > 500 yuan |
| high | 退款.*覆盖/override/超出政策 | HR-02: refund override on delivered order |
| high | 例外/特批/政策豁免/高风险商家 | HR-03: high-risk merchant or policy exception |
| medium | 补偿/赔付 + 金额 >= 100 and <= 500 | MR-02: medium compensation |
| low | 补偿/赔付 + 金额 < 100 | LR-01: within normal parameters |

Risk thresholds follow `rules/risk_rules.yaml`. Golden set cases use Arabic
numerals only so amount extraction remains deterministic.

## Approval Decision Keywords

| Decision | Trigger Keywords |
|----------|------------------|
| approval_required | 审批, 需要批准, 等待审核, 需要批准吗 |
| approval_approved | 已批准, 批准通过, 同意补偿, 继续执行 |
| approval_rejected | 驳回, 拒绝, 不同意, 主管不同意, 审批被驳回 |
| permission_denied | 权限不足, 无权, 403, 没有权限, 过期token |

## Amount Extraction Normalization

Chinese amount expressions that should all resolve to the same numeric value:

- "补偿600元" -> 600
- "赔付600" -> 600
- "给用户600块" -> 600

The eval script uses regex `(\d+)\s*(元|块|¥)?` to extract amounts from queries.
Chinese numerals (一二三...百千万) are out of scope for Phase 6, so all golden set
cases use Arabic numerals only.

## Seed ID Matching

Order, refund, and ticket identifiers in Chinese queries are matched with
ASCII-only lookarounds rather than Unicode word boundaries because IDs are often
adjacent to Chinese characters.

Expected patterns:

- `ORD-*` for order IDs
- `RF-*` or `RFC-*` for refund case IDs
- `TK-*` or `TKT-*` for ticket IDs

Success cases must reference IDs generated by `scripts/seed_demo.py`.
`tool_failure_or_not_found` cases are the only category allowed to reference
deliberately missing IDs such as `ORD-NONEXIST-001`.

## Response Content Matching

`expected_response_contains` and `must_not_contain` use substring matching with
these rules:

- Case-insensitive for ASCII characters
- Exact match for Chinese characters (no synonym expansion)
- Whitespace-normalized (consecutive whitespace collapsed to single space)
- Matching is applied to the `final_response` text field only

## FakeLLM Deterministic Routing Contract

In CI mode, FakeLLM responses are constructed to trigger specific graph routing
paths:

- Intent classification node: returns `expected_intent` from the case
- Risk assessment node: returns `expected_approval_required` based on amount and
  risk-trigger rules above
- Tool selection: returns tool calls matching `expected_tools_called`
- Final response: includes strings from `expected_response_contains`

This means CI mode validates the scoring harness, golden set schema, and graph
routing logic, not the actual LLM's language understanding ability.
