# MOCA 10-Minute Demo Walkthrough

## Overview

This walkthrough demonstrates MOCA's core capabilities in a 10-minute interview format.
Pacing: 1 minute problem statement, 2 minutes architecture, 4 minutes live demo, 2 minutes trace/eval, 1 minute summary.

> **Note:** The canonical automated demo is `scripts/demo_phase6.sh`. Run `bash scripts/demo_phase6.sh` for the reproducible version. This document adds interview context, expected response highlights, and what to point out while walking through the flow.

## Deterministic Demo vs Live Smoke Test

- The demo script is designed for deterministic local data and API behavior. It validates routing, approval logic, permission checks, and trace persistence.
- To run with a real LLM-backed agent path, configure the provider key first, for example `export DASHSCOPE_API_KEY=...`, then run the same local stack and smoke/eval commands.
- `scripts/seed_demo.py --reset` guarantees the same business data, demo accounts, order numbers, refund cases, and policy documents every time.

## Prerequisites

- Docker Compose stack running: `docker compose up --build` or `make up` if available.
- Database migrated and seeded: `make migrate` and `make seed`.
- `jq` installed for formatted JSON output.
- API reachable at `MOCA_BASE_URL`, defaulting to `http://localhost:8000`.

## Scenario 1: Authentication

> **Interview talking point:** RBAC with JWT and OAuth2 scopes ensures each role can only access appropriate endpoints. The same password is used only for synthetic demo accounts.

Endpoint: `POST /api/v1/auth/token`

```bash
curl -s -X POST "$BASE_URL/api/v1/auth/token" \
  -H "Content-Type: application/x-www-form-urlencoded" \
  -d "username=cs_zhang&password=moca2024" | jq '{access_token, token_type}'
```

Expected response highlights:

- `access_token` exists for `cs_zhang`.
- `token_type` is `bearer`.
- A manager token can be obtained with `username=mgr_li`.

What to point out:

- Support users receive chat and read scopes, not approval authority.
- Managers receive `approvals:review`, which is required by the approval API.

## Scenario 2: Policy QA

> **Interview talking point:** The agent retrieves policy evidence and cites stored knowledge chunks. This is evidence-backed support, not free-form hallucination.

Endpoint: `POST /api/v1/agent/chat`

```bash
curl -s -X POST "$BASE_URL/api/v1/agent/chat" \
  -H "Authorization: Bearer $AGENT_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"query":"平台的退款超时处理规则是什么？","thread_id":"demo-thread-01"}' | jq .
```

Expected response highlights:

- `success: true`
- `data.response` contains a policy answer.
- `data.trace_summary.intent` is a policy or refund-rule intent.
- `data.trace_summary.evidence_count` is greater than zero.

What to point out:

- Evidence references are generated by retrieval and persisted in trace steps.
- The demo query is Chinese because the seeded policy corpus and business scenario are Chinese.

## Scenario 3: Refund Troubleshooting

> **Interview talking point:** The agent calls structured tools before answering. It loads order/refund business context instead of relying only on policy text.

Endpoint: `POST /api/v1/agent/chat`

```bash
curl -s -X POST "$BASE_URL/api/v1/agent/chat" \
  -H "Authorization: Bearer $AGENT_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"query":"订单ORD-2024-001的退款进度如何？","thread_id":"demo-thread-02"}' | jq .
```

Expected response highlights:

- `data.trace_summary.tools_called` includes order or refund lookup tools.
- `data.trace_summary.evidence_count` shows policy evidence was retrieved.
- `data.trace_summary.final_status` is normally `completed`.

What to point out:

- Business context and policy evidence are separate inputs to the recommendation flow.
- The audit trail records both tool usage and evidence refs, so the answer can be reviewed later.

## Scenario 4: Compensation Suggestion (High Risk)

> **Interview talking point:** Risk assessment is deterministic. `rules/risk_rules.yaml` defines thresholds, and a 600 CNY compensation request triggers mandatory approval.

Endpoint: `POST /api/v1/agent/chat`

```bash
curl -s -X POST "$BASE_URL/api/v1/agent/chat" \
  -H "Authorization: Bearer $AGENT_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"query":"客户投诉订单ORD-2024-002延迟发货，要求补偿600元","thread_id":"demo-thread-03"}' | jq .
```

Expected response highlights:

- `data.status` is `interrupted`.
- `data.approval_id` is present.
- `data.risk_level` is `high`.
- `data.proposed_action` describes the pending action.

What to point out:

- The agent does not execute high-risk actions directly.
- The approval request becomes a durable object that a reviewer can decide on later.
- Capture `approval_id` and `run_id` for the next scenarios.

## Scenario 5: Permission Denied

> **Interview talking point:** Defense in depth matters. Even with an approval ID, a support agent cannot approve high-risk work because the API checks scopes and role permissions.

Endpoint: `POST /api/v1/approvals/{approval_id}/decide`

```bash
curl -s -X POST "$BASE_URL/api/v1/approvals/$APPROVAL_ID/decide" \
  -H "Authorization: Bearer $AGENT_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"decision":"approve","reason":"测试"}' | jq .
```

Expected response highlights:

- HTTP status is `403` in the automated script.
- Error details identify insufficient scope or insufficient role.

What to point out:

- `cs_zhang` can submit agent questions but cannot approve.
- Authorization is enforced at the API boundary, independent of what the agent suggested.

## Scenario 6: Approval Rejected

> **Interview talking point:** Human decisions resume the graph through LangGraph `Command(resume=...)`. A rejection stops execution and records the reviewer reason.

Endpoint: `POST /api/v1/approvals/{approval_id}/decide`

```bash
curl -s -X POST "$BASE_URL/api/v1/approvals/$APPROVAL_ID/decide" \
  -H "Authorization: Bearer $MANAGER_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"decision":"reject","reason":"补偿金额超出合理范围，建议降至200元"}' | jq .
```

Expected response highlights:

- `success: true`
- `data.status` changes from `pending` to a rejected state.
- `data.decision` is `reject`.
- `data.reason` preserves the manager's explanation.

What to point out:

- The agent workflow resumes after the approval decision.
- Rejection does not execute the proposed action.
- Reviewer, timestamp, decision, and reason are auditable.

## Scenario 7: Trace Query

> **Interview talking point:** The system is observable by design. Every node traversed, tool called, evidence item retrieved, risk decision, and final status is recorded.

Endpoint: `GET /api/v1/agent-runs/{run_id}/trace`

```bash
curl -s "$BASE_URL/api/v1/agent-runs/$LAST_RUN_ID/trace" \
  -H "Authorization: Bearer $AGENT_TOKEN" | jq .
```

Expected response highlights:

- `data.run_id` matches the captured run.
- `data.final_status` shows the final outcome.
- `data.timeline` contains node-level events.
- Trace entries include tools, evidence refs, approval status, and latency fields where available.

What to point out:

- Trace replay is useful for debugging, compliance review, and interview explanation.
- The trace endpoint intentionally exposes summarized operational data, not raw secrets or provider credentials.

## What This Demonstrates

- Evidence-first answers: RAG citations ground policy responses in stored documents.
- Tool orchestration: the agent reads orders, refunds, tickets, and policy evidence before responding.
- Deterministic safety: high-risk thresholds live in `rules/risk_rules.yaml`, not in an LLM prompt.
- Human-in-the-loop control: approval interruption and resume are first-class graph behavior.
- Auditability: every run can be inspected through persisted trace and approval records.
